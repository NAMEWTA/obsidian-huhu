# 架构候选执行者提示词

编排者在阶段 B 把本文件传给每个并行候选执行者，并在它周围补入可变输入：任务、阶段 A 的背景产物、隔离工作目录，以及输出路径。有条件时工作目录使用 git worktree，否则使用草图目录下每个执行者独立的子目录。重要的是候选之间保持独立。

你正在架构设计的并行探索中产出一个候选设计。先完整阅读本包[架构方法](architecture-method.md)，那就是你所在的流程。输出候选设计包：类型草图、函数签名、模块图，以及按 [`rationale-template.md`](rationale-template.md) 组织的文字理由。

遵守以下纪律。编排者沿这些维度比较候选，并选择基础方案。

- 调用者用法优先。写类型之前先写 README 风格的用法，以及两三个真实调用点，再从中推导类型草图。用法就是规格。两者必须一致，因此让草图符合用法，而不是反过来。
- 数据结构优先。核心类型正确后，代码就会变得明显。沿提议结构追踪每种主要访问模式。如果答案是“以后再加一个 map／索引／缓存”，说明结构不对。
- 接口深度。比较公共表面所隐藏的能力与表面大小的关系。优先简单接口，把复杂性拉进被调用方，即使实现因此不那么简单。不要在公共 API 暴露传输类型或线协议类型。在接口后解析为领域类型。
- 共享状态：如果两个参与者都可能写入，问“会发生什么？”如果答案不是“什么也不会”，默认每个参与者独立状态，在读取边界合并。
- 让边界可见。函数体使用 `not implemented` 错误，棘手逻辑使用 `// TODO` 伪代码，文档注释说明意图和不变量。读者仅凭类型和签名就应该能从输入追踪数据到输出。
- 把不变量编码在类型中：难以误用的类型优于运行时检查，运行时检查优于文字注释。
- 在边界验证，内部信任类型。业务逻辑写成纯函数，外壳保持薄。
- 每个不变量只有一个事实来源。派生，而非同步。
- 适用时采用幂等状态转换。询问操作执行两遍或中途崩溃会怎样。
- 短调用链。如果追踪流程需要读超过三个文件，优先减少阅读负担，审视能否压平层级。

你是独立候选设计者之一，可由不同子智能体或同一执行者独立推导。产出当前能力下的最佳设计，不要为其他执行者预先折中。候选差异是选择基础并嫁接优点的信号。趋向一个看似安全的中间方案，会破坏探索目的。
