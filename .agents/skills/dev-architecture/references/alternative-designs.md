# 设计两次

用户希望为选定的加深候选对象探索替代接口时，采用这种并行子智能体模式。通过真正不同的结构检验第一个想法，而不是假定第一个方案最好。

使用 [模块设计](module-design.md) 中的词汇：**模块**、**接口**、**接缝**、**适配器**、**效能**。

## 流程

### 1. 界定问题空间

启动子智能体前，面向用户说明选定候选对象的问题空间：

- 任何新接口都必须满足的约束。
- 它依赖哪些东西，各属哪种依赖类别，见 [依赖与加深](dependency-design.md)。
- 一份帮助理解约束的粗略代码示意；它不是提案，只是让约束具体化。

向用户展示后立即进入第 2 步。用户可以在子智能体并行工作时阅读和思考。

### 2. 启动子智能体

有并行能力时让独立子智能体使用全新上下文提出候选；没有则自行依次推导。为存在重要取舍的设计至少比较两个**结构不同**的接口，下面列出三到四种可选优化方向，不强制固定代理数量。

给每个子智能体一份独立技术简报，包括文件路径、耦合细节、[依赖与加深](dependency-design.md) 中的依赖类别，以及接缝后面包含什么。这份简报独立于第 1 步面向用户的问题空间说明。给每个智能体不同设计约束：

- 智能体 1：“最小化接口：最多争取 1—3 个入口。最大化每个入口的效能。”
- 智能体 2：“最大化灵活性：支持多种用例和扩展。”
- 智能体 3：“针对最常见调用方优化：让默认情况极其简单。”
- 智能体 4，如适用：“围绕端口与适配器设计跨接缝依赖。”

简报同时包含 [模块设计](module-design.md) 的架构词汇和 glossary.md 的领域词汇，让每个子智能体的命名与架构语言、项目领域语言一致。

每个子智能体输出：

1. 接口：类型、方法、参数，以及不变量、顺序和错误模式。
2. 使用示例，展示调用方如何使用它。
3. 实现在接缝后隐藏什么。
4. 依赖策略和适配器，见 [依赖与加深](dependency-design.md)。
5. 取舍：哪里效能高，哪里效能薄弱。

### 3. 展示与比较

按顺序展示各个设计，让用户逐个理解，再用文字比较。比较**深度**，即接口效能；**局部性**，即变更集中在哪里；以及**接缝位置**。

比较后给出自己的推荐：认为哪种设计最强，以及为什么。如果不同设计中的元素适合组合，提出混合方案。形成明确判断：用户要的是有力度的分析，而不是一张菜单。
