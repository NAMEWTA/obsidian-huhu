# 架构设计

先在设计文档中以签名、类型和伪代码勾勒形态；确需代码骨架时才创建带 `not implemented` 函数体的临时实现，并明确其未完成状态。比较独立候选视角，再按照选定的草图填入代码。

## 开始

开始前按任务需要记录当前阶段；简单任务可用短清单，不要求专用待办工具。

1. 理解背景
2. 绘制草图
3. 达成一致
4. 实现
5. 推倒重来

## 阶段 A：理解问题背景

对新代码接触的每个系统建立真实的心智模型。追踪相关子系统的入口、调用链、状态所有者、外部边界与输出，并附当前代码路径、符号及证据。仅仅说出文件名不算理解背景。产出可串起输入到结果的架构解释。若重新定义所有权或分层，也检查现有代码、决定记录及必要提交历史，区分已证实理由与未知原因，让实际约束进入设计。

只有工作确实是全新开发、无需与周围系统集成时，才跳过阶段 A。

## 阶段 B：绘制草图

带着设计任务和阶段 A 背景，按[替代设计](alternative-designs.md)独立探索候选。将[候选任务提示](alternative-brief.md)交给每个执行者。

有可用子智能体时分配独立上下文与隔离写入位置；没有时自行依次推导不同结构。使用当前已提供能力，不要求指定模型、宿主配置或额外执行器。

设计两次。综合前至少要求两个结构不同的候选方案，即使第一个看起来已足够。通过比较覆盖真正不同的设计空间。需要整体形态的替代方案，而非同一形态内部的局部修补。

综合前，按 [设计危险信号](design-red-flags.md) 筛查每个候选。假设下一位贡献者是一个只看到自己打开过的文件、复制最近的示例、选择能编译的最短路径的智能体。优先选择那种从单个文件看正确的修改，对整个仓库也正确的设计。

比较可行候选的接口深度。优先选择能通过更小、更简单的公共接口隐藏更多复杂性的设计。能力丰富的接口可以通过集中能力而非把能力分散在多层来缩短调用链。

比较后形成一个综合设计包。其综合决策填入理由文档的“综合决策”一节。

## 阶段 C：达成一致（按需启用）

已有实施授权时，默认根据综合设计继续实现，无需额外人工检查点；用户只要求架构分析时，交付设计而不扩展为实现任务。

调用者明确要求时才启用检查点，例如“先检查设计”“先停下来展示给我，再实现”等。此时展示综合设计，并暂停等待认可。

综合结果可单独保存为设计文档；项目需要代码骨架时才创建，提交遵循已有授权。实现期间有计划、范围受控的暂时不完整可以存在，但不能当作完成交付。若设计存在重大争议，按[设计危险信号](design-red-flags.md)从调用者、数据所有权、失败路径和真实约束反向质询草图。

如果人在检查点或事后反对结构，把反馈视为阶段 A 的证据。重新理解背景并重新执行阶段 B，然后再继续写代码。

## 阶段 D：按照草图实现

把 `not implemented` 函数体替换为代码，把伪代码替换为逻辑。综合草图就是契约。偏离草图是需要显式指出的信号，不是应该默默消化的摩擦。若某个函数需要草图未预见的参数，判断究竟是草图错误、需求遗漏，还是实现越界。

## 阶段 E：架构错误时推倒重来

如果实现持续产生草图无法吸收的摩擦，就丢弃草图。从新约束重新推导结构，修正根因，不把修补措施堆在错误设计上。

信号是某种*模式*，而非单个实例。迹象包括：

- 无关代码中反复出现同形状的变通办法。
- 多个互不相关的边界情况都需要特殊分支。
- 类型必须依赖逃生口（`any`、类型强转、实践中总会赋值的可选字段）才能编译。
- 草图认为状态不共享，却本能地说“我们需要一把锁”。
- 调用者必须知道抽象内部规则才能使用它。
- 整个实现中，出现两次或更多同形状、相互独立的阶段 D 偏离。

运用判断力。少量边界情况不能判定架构有罪。有些问题确实复杂。数据的复杂性不等于设计的复杂性。

推倒重来时：

1. 重新追踪已构建内容的实际运行路径与状态所有权。
2. 假定新约束从第一天就存在，重新设计。
3. 先删后加。新草图在增长前应比旧草图更小。
4. 回到阶段 B，重新生成并比较结构不同的候选。

## 输出

先写调用者用法，再从中推导类型草图。小改动用一个文件列出新类型与签名。较大工作提供模块图和类型定义。理由文档一同交付，遵循[设计理由模板](rationale-template.md)，包含使用草图和综合决策。

以调用者行为、设计决定与验收约束指导实现，按任务组合 TDD、行为回归及结构检查。项目知识只保存不可从代码直接读出的理由和术语映射，当前结构用可复核代码指针表达。
