# 加深模块

如何结合依赖，安全地把一簇浅模块加深。本文假定使用 [模块设计](module-design.md) 中的词汇：**模块**、**接口**、**接缝**、**适配器**。

## 依赖类别

评估某个加深候选对象时，先对其依赖分类。类别决定如何跨接缝测试加深后的模块。

### 1. 进程内

纯计算、内存状态、无 I/O。始终可以加深：合并模块，直接通过新接口测试。无需适配器。

### 2. 可本地替代

拥有本地测试替身的依赖，例如用 PGLite 替代 Postgres、使用内存文件系统。存在替身就可以加深。测试套件运行替身，并以它测试加深后的模块。接缝是内部的，不在模块外部接口暴露端口。

### 3. 远程但自有，采用端口与适配器

跨网络边界的自有服务，例如微服务、内部 API。在接缝处定义**端口**，即接口。深模块拥有逻辑，传输层作为**适配器**注入。测试使用内存适配器；生产使用 HTTP／gRPC／队列适配器。

建议的形态：“在接缝处定义端口，为生产实现 HTTP 适配器，为测试实现内存适配器，这样即使跨网络部署，逻辑仍位于一个深模块中。”

### 4. 真正的外部依赖，采用模拟

无法控制的第三方服务，例如 Stripe、Twilio 等。加深后的模块通过注入端口接收外部依赖；测试提供模拟适配器。

## 接缝纪律

- **一个适配器意味着假设的接缝，两个意味着真实接缝。** 除非至少两个适配器都有正当理由，通常为生产和测试，否则不要引入端口。只有一个适配器的接缝只是增加间接层。
- **内部接缝与外部接缝。** 深模块可以有属于实现私有部分、由自身测试使用的内部接缝，也有接口处的外部接缝。不能仅因为测试使用内部接缝，就把它暴露到对外接口。

## 测试策略：替换，不叠加

- 加深后模块的接口验证覆盖相关行为后，识别浅模块旧测试是否重复或绑定已删除实现；确认没有独有行为覆盖再删除，保留仍保护真实风险的检查。
- 围绕加深后模块的接口编写行为测试。可根据已有覆盖采用测试先行、修改前特征测试或实现后验证。**接口就是测试表面。**
- 测试断言经由接口可观察到的结果，而不是内部状态。
- 测试描述行为，不描述实现，因此应该经得起内部重构。如果实现改变就必须修改测试，说明测试越过了接口。

本方法先明确调用契约，再根据任务选择实现顺序；测试先行和实现后回归都应围绕真实行为与边界。
