# 设计检查与依赖策略

## 深度、局部性与接口

深模块以较小接口隐藏大量业务复杂度。深调用链则把理解分散到多层，二者不同。

检查调用者为了完成一个操作必须知道多少事情：调用顺序、状态字段、协议结构、失败恢复、生命周期管理。如果调用者仍必须了解实现内部规则，接口没有承担足够职责。

**删除检验**：假设删除此模块。若复杂度随之消失，它可能只是多余转发；若复杂度会散落到许多调用者，它正在承担真实责任。

## 候选设计的危险信号

| 信号 | 要查的具体问题 | 典型调整 |
| --- | --- | --- |
| 浅模块 | 大接口只转发少量行为 | 合并责任或缩小公开面 |
| 信息泄漏 | 多处依赖同一内部表示、协议或存储决定 | 在领域边界解析，隐藏传输与存储形状 |
| 按时序拆分 | load / validate / save 各自重复保护同一不变量 | 围绕知识所有权组织 |
| 直通转发 | 一层仅传同样参数给下一层 | 删除转发，或让它承担真实策略与适配 |
| 状态多人写 | 不同模块各改同一事实或保存副本 | 确定一个所有者，通过接口修改 |
| 多条完成路径 | 同一行为有多个并行入口不断增加调用者 | 迁移调用者后删除多余路径 |
| 可导入内部实现 | 外部能越过公开接口引用私有状态 | 用实际语言 / 构建边界限制导入 |
| 手工同步清单 | 加一项要同时改多个重复列表 | 单一登记源推导其余；无法推导时做一致性检查 |
| 只为未来存在的接口 | 只有一个实现且没有实际替换需求 | 留在实现内部，等变化真实出现 |
| 类型逃生口 | 相似场景反复依赖不安全转换或永远存在的可选字段 | 重新表达领域状态与数据关系 |

这些是设计判断，不是禁止所有层次、缓存、接口或适配器。要解释当前实例的实际代价。

## 按真实依赖选择接口

- **进程内逻辑**：直接通过公开接口调用；纯计算和内存状态无需额外网络式接口。
- **有本地替代的依赖**：沿用项目可用的本地存储或替代服务，在合适位置替换；不因此向业务调用者暴露测试结构。
- **跨网络但由项目控制的服务**：领域模块拥有业务规则，传输可由适配器满足接口。
- **真正外部的第三方**：在边界集中解析、失败语义和协议适配；验证时使用可信替代或受控真实环境。

内部可存在局部替换点；它们不必都成为模块的公开 API。两种真实使用方式通常比一个假想实现更能证明接口值得存在。

## 比较候选

每个候选至少给出调用示例、接口语义、内部隐藏的责任、依赖策略和代价。避免把“类还是函数”“命名不同”包装成两种整体架构。

可让独立设计者分别优化最小公开面、常见调用体验和真实扩展需求。比较后选定基底，只吸收能改善具体问题的部分，不机械拼合全部方案。
