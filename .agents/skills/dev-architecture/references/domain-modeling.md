# 领域建模

在设计过程中主动建立并打磨项目的领域模型。这是一项**主动**实践：质疑术语、构造边界场景，并在术语与决定成形时立即写入词汇表和决策记录。仅为了解用词而**阅读** `glossary.md` 不属于本技能，那只是任何技能都能采用的一行习惯。本技能用于改变模型，而不仅是使用模型。

## 文件结构

先按真实位置查阅已有词汇表与决定。新增资料统一使用 `.agents/dev/notes/glossary.md` 和 `.agents/dev/notes/decisions/`，通过必要引用连接既有记录。以下树形结构说明单一上下文的职责关系：

```text
/
├── .agents/dev/notes/
│   ├── glossary.md
│   └── decisions/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果项目已有 `glossary-map.md` 或等效领域索引，说明仓库有多个上下文。映射文件指出各上下文所在位置；没有则按需要在 `.agents/dev/notes/` 创建，不为目录格式迁移现有文件：

```text
/
├── .agents/dev/notes/
│   ├── glossary-map.md
│   ├── decisions/                    ← 跨领域决定
│   └── context/
│       ├── ordering/
│       │   ├── glossary.md
│       │   └── decisions/            ← 订购领域决定
│       └── billing/
│           ├── glossary.md
│           └── decisions/
└── src/
```

延迟创建文件：只有有内容可写时才创建。如果还没有 `glossary.md`，在第一个术语确定时于 `.agents/dev/notes/glossary.md` 创建；如果没有 `.agents/dev/notes/decisions/`，在需要第一份 ADR 时创建。

## 会话期间

### 对照词汇表提出质疑

如果用户使用的术语与 `glossary.md` 已有语言冲突，立即指出：“词汇表把‘取消’定义为 X，但你现在似乎指 Y。应以哪个为准？”

### 使模糊语言准确

用户使用模糊或多义术语时，提出准确的规范术语：“你说‘账号’，指的是 Customer 还是 User？这是两个不同的东西。”

### 讨论具体场景

讨论领域关系时，用具体场景做压力检验。构造能探查边界情况的场景，迫使用户精确说明概念之间的边界。

### 与代码交叉核对

用户描述某事如何运行时，检查代码是否一致。如果发现矛盾就指出：“代码当前取消整份 Order，你描述的是部分取消。若这是新的目标，就把差异写入规格；若是在描述现状，则核实哪种理解正确。”

### 即时更新 glossary.md

术语一旦确定，立即更新 `glossary.md`。不要攒成一批，发生时就记录。采用 `dev-archive`（词汇表格式） 的格式。

`glossary.md` 应完全没有实现细节。不要把它当作规格、草稿纸或实现决策仓库。它只是一份词汇表。

### 克制地建议 ADR

只有以下三项都成立，才建议创建 ADR：

1. **难以逆转**：未来改变主意的成本确实显著。
2. **缺少背景就难以理解**：未来读者会问“为什么这样做？”
3. **真实取舍的结果**：确实存在其他可行选择，并因明确理由选定了其中一种。

任何一项不成立，就跳过 ADR。使用 `dev-archive`（决定记录格式） 中的格式。

术语定义旁保留用户说法到规范概念的别名映射，以及适用领域。代码定位另放现状证据，用相对路径和符号定位；归档时读取最新代码复核，不把历史文件位置当作永恒事实。

未同时满足正式 ADR 的三项条件，但仍有长期价值的背景和约束，统一保存到 `.agents/dev/notes/context/`，按真实位置引用已有背景；错误与恢复方法进 `errors/`，术语进 `glossary.md`。不因未达到 ADR 门槛删除有效知识，也不强制迁移项目已有记录。
