设计**深模块**：大量行为藏在小接口后面，接口位于清楚的接缝上，并可通过该接口测试。在设计或重组代码的任何地方采用这些术语和原则。目标是给调用方以效能、给维护者以局部性，并让所有人都能测试。

## 词汇表

在设计讨论中准确区分以下术语；项目已有领域词汇时明确映射，避免把“组件”“服务”“API”或“边界”的不同含义混用。统一语义是关键。

**模块（Module）**：任何具有接口和实现的东西。有意不限定尺度：可以是函数、类、包，或跨层切片。_避免使用_：单元、组件、服务。

**接口（Interface）**：调用方正确使用模块必须知道的全部内容，不仅是类型签名，还包括不变量、顺序限制、错误模式、必要配置和性能特征。_避免使用_：API、签名；这些词过窄，只指类型层表面。

**实现（Implementation）**：模块内部的代码主体。与**适配器**不同：一个东西可以是小适配器却有大实现，例如 Postgres 仓库；也可以是大适配器却只有小实现，例如内存假实现。讨论接缝时用“适配器”，其他时候用“实现”。

**深度（Depth）**：接口带来的效能。调用方或测试每学习一单位接口，就能使用多少行为。大量行为位于小接口后面时，模块是**深**的；接口几乎和实现一样复杂时，模块是**浅**的。

**接缝（Seam）**：无需修改该处代码就能改变行为的位置；模块接口所在的**位置**。接缝放在哪里本身是一项设计决定，与接缝后放什么不同。_避免使用_：边界；它与领域驱动设计的限界上下文产生多义。

**适配器（Adapter）**：在某个接缝处满足接口的具体事物。描述的是**角色**，即填入哪个槽位，而不是其内部是什么。

**效能（Leverage）**：调用方从深度获得的收益。每学习一单位接口，就能得到更多能力。一份实现在 N 个调用点和 M 个测试中持续产生回报。

**局部性（Locality）**：维护者从深度获得的收益。变更、缺陷、知识和验证集中在一处，而不是散布在各个调用方。修一处，处处修复。

## 深与浅

**深模块** = 小接口 + 大量实现：

```text
┌─────────────────────┐
│       小接口        │  ← 方法少、参数简单
├─────────────────────┤
│                     │
│       深实现        │  ← 复杂逻辑被隐藏
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现，应避免：

```text
┌─────────────────────────────────┐
│             大接口              │  ← 方法多、参数复杂
├─────────────────────────────────┤
│             薄实现              │  ← 仅作透传
└─────────────────────────────────┘
```

设计接口时询问：

- 能否减少方法数量？
- 能否简化参数？
- 能否把更多复杂性隐藏在内部？

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部可以由小型、可模拟、可替换的部件组成，只是这些部件不是对外接口。模块既可以在自身实现中有由自身测试使用的**内部接缝**，也可以在接口处有**外部接缝**。
- **删除检验。** 想象把模块删掉。如果复杂性消失了，它只是透传；如果复杂性重新出现在 N 个调用方中，它就有存在价值。
- **接口就是测试表面。** 调用方和测试穿过同一接缝。如果想越过接口测试内部，模块形状很可能不对。
- **一个适配器意味着假设的接缝，两个适配器意味着真实接缝。** 除非确有东西会跨接缝发生变化，否则不引入接缝。

## 为可测试性设计

好的接口让测试自然发生：

1. **接收依赖，不自行创建依赖。**

   ```typescript
   // 易测试
   function processOrder(order, paymentGateway) {}

   // 难测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不制造副作用。**

   ```typescript
   // 易测试
   function calculateDiscount(cart): Discount {}

   // 难测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面。** 方法越少，需要的测试越少；参数越少，测试准备越简单。

## 关系

- 一个**模块**恰有一个**接口**，即它向调用方和测试呈现的表面。
- **深度**是**模块**的属性，以其**接口**为参照衡量。
- **接缝**是**模块**的**接口**所在的位置。
- **适配器**位于**接缝**处，并满足**接口**。
- **深度**为调用方带来**效能**，为维护者带来**局部性**。

## 不采用的表述

- **用实现行数与接口行数之比描述深度**：这会奖励填充实现。这里改用接口效能衡量深度。
- **把“接口”等同于 TypeScript `interface` 关键字或类的公开方法**：过窄；这里接口包括调用方必须知道的每项事实。
- **“边界”**：与领域驱动设计的限界上下文产生多义。使用**接缝**或**接口**。
