# 设计理由模板

与类型草图一同交付的说明文字。一页。标题使用正常句式，不要套话。把斜体提示替换为实际内容。

## 问题

*一段。我们试图做什么，现有系统或约束的哪些方面让结构选择不显然。若[理解背景](architecture-method.md#阶段-a理解问题背景)发现设计必须遵循的约束（需要互操作的现有类型、不能破坏的调用者、跨越边界的不变量），在这里点明，让读者看到你看到的相同约束。*

## 用法（调用者视角）

*先写这一节，再写类型草图。展示使用者会阅读的 README 或快速入门，以及两三个在其自身代码中的真实调用点。导入什么、调用什么、返回什么。[形态](#形态)中的类型草图从这里推导。两者必须一致。出现分歧时，调整草图以符合用法，而非反过来。调用者体验就是规格；类型服务于它。*

## 形态

*推荐的架构。先写数据结构，再写数据如何通过签名流动。指出承担关键作用的决策。说明哪些不变量编码在类型中、校验位于哪里，以及系统明确不做什么。明确评价接口深度。说明公共接口隐藏哪些复杂性、哪些仍暴露给调用者，以及为什么接口没有超过必要大小。引用每项决策背后的本地设计规则，例如[边界与接口](module-design.md)，不要重复抄写规则。*

## 综合决策

*依据[候选比较](alternative-designs.md)填写。记录哪个候选成为基础及其原因，从其他候选分别借鉴了什么，以及拒绝了什么、为什么拒绝。*

## 接受的权衡

*所选形态的每项权衡各占一条。形式为：“我们接受 X，以换取 Y。”指出未来读者可能误以为是疏漏的内容，包括看起来像过早优化或过早简化的选择。*

## 考虑过的替代方案

*必填。至少指出一种具体的替代形态，用一句话解释为什么未选。评价每种替代方案的接口深度，而非只看实现简单性。说明它向调用者暴露哪些复杂性、隐藏哪些复杂性。若设计空间中确有竞争者，这里应写两三个替代方案。若约束迫使答案唯一，一个也可以，但结论应表述为“这是唯一可行的形态，因为……”。不要罗列同一形态的不同口味。本节涵盖所选形态考虑并拒绝的设计替代方案，而非其他执行者的候选方案。*

## 开放问题与风险

*绘制草图时注意到、需要人作判断的事项，以及值得在实现前提示的风险。写成问题而非断言，让人的回答成为问题的解决，而非一条评论。*

## 下一步实现

*按照草图首先构建什么。一句话。综合后（若启用了检查点，则在阶段 D 获得认可后）会立即开始编写什么。*
