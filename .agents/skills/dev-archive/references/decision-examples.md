# 决策记录示例

以下是完整的示例模型，帮助判断记录应保留哪些信息。示例不是当前项目已经采用的架构；实际项目必须替换为真实实现位置、符号与验证证据。

## 示例一：事件日志作为会话事实来源

### 问题

一个会话系统需要严格的事件追踪与日志，会话必须完全可回放。

### 决定

`Session` 是带类型的 `SessionEvent` 只追加日志，也是唯一事实来源。模型消息历史由日志派生（`deriveMessages()`）；原始流式分块保留 token 级重放精度，组装后的 `assistant/message` 事件负责派生。重放或分叉就是用既有日志初始化新会话。

追加同步完成，热路径不阻塞于 I/O；`session/event` 同步通知。持久化插件缓存延后写入，并在每轮结束触发、且被等待的 `session/flush` 检查点排空。

顺序约定：循环在 `agent/pre-step` 前领取收件箱消息，只有决定进入后才开启 `step/start`，再于派生请求前追加 `user/message` 批次。提供方输出在工具分派前组装并追加为 `assistant/message`，使持久日志记录工具随后遵循的准确消息。项目应以实际已有验证或实现后回归证据证明顺序。

### 考虑过的方案

**可变消息数组加通知事件。** 它更简单，但状态与日志可能分离；事件日志本身就是状态时，结构上消除这种分离。

### 后果

- 重放、追踪与遥测由结构提供，而非事后附加。
- 持久化由独立模块负责，内存存储有明确拥有者。
- 事件可以由插件扩展；一旦落成持久格式，就需要兼容策略。
- 派生成本随日志增长。采用上下文压缩等明确机制缓解，不随意改写历史日志。

### 在真实项目中引用什么

指向事件类型、追加入口、消息派生函数、flush 调用点、持久化实现和对应验证。说明当前代码是否实际符合此设计；不要只引用这篇示例来证明项目架构。

## 示例二：一个根目录事实由一个解析器负责

### 问题

同一应用有两个用户数据目录解析器。两者优先级近似，一个展开 `~`，另一个不展开；跨包重复未被检测，已产生分歧。同一跨领域事实没有统一策略。

### 决定

单一解析器负责应用根目录，按以下顺序解析：

```
显式配置路径 > 应用专用环境变量 > 用户默认目录
```

空字符串或纯空白环境变量按未设置处理，避免 `resolve('')` 把数据放进当前工作目录。数据集中在一个明确根目录，不在没有需求时自行拆分配置、数据和缓存根。

路径辅助函数只拼接部署负责的子路径。应用启动在挂载组件前提供已解析路径，使会话和存储使用同一规则。面向用户展示符号化目录，不在标签中泄露机器绝对路径。根目录是进程策略，不允许某个消费者另行覆盖，造成指令、会话、技能和存储分别读取不同位置。

确实与其他工具共享的 Agent 配置目录独立存在，但使用一致的优先级、波浪号展开与符号展示规则。个别组件确需独立选择资源根时，字段必须显式声明，仍通过同一解析逻辑处理。

缓存辅助函数在根目录的 `cache` 子树下派生路径，显式覆盖选项保持有效。它只解析，不创建目录；调用者负责创建。可重新生成的请求图像变体属于缓存，持久附件留在带版本的存储树；清缓存不得删除附件。旧缓存可原位保留且不再读取，未命中时由持久附件重新生成，无需搬运全部旧缓存。

删除重复解析器，所有负责根目录的提供方与启动模块引用同一个入口，组合配置只保存解析结果。已经退役的遥测或工具链不保留一套独立主目录政策。

### 考虑过的方案

**保留两个解析器。** 两者已经分化，并重复编码同一跨领域事实。公共工具层应消除这种重复，否则它是潜在分歧缺陷。

**采用 XDG 并拆成配置、数据和缓存目录。** 这是有效备选，但该示例选择单一明显根目录，避免逐一重新分类现有消费者及协调解析差异。真实项目若已有 XDG 约定，应按现有约定作出选择，不照搬示例结论。

### 后果

一个根目录事实、一个解析器、一个负责模块。缓存与持久数据的寿命分开；路径解析与目录创建的责任分开。真实项目须引用解析器、启动调用、各消费者、缓存与持久目录以及相关验证，而不是复制一份可能过时的目录树。
