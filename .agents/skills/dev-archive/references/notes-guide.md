# 知识目录与笔记格式

项目笔记记录影响代码库的决定或提案，尤其是为什么这样做、放弃什么，以及代码本身不能承载的领域词义和约束。只记录有长期价值的内容；当前实现细节尽量指向代码。

## 目录与命名

新增项目笔记统一以 `.agents/dev/` 为根，按需要创建以下内容。已有资料按真实位置查阅引用；明确迁移时保留内容、命名与编号，并修复相关链接，不擅自搬迁目标项目文件：

| 内容 | 路径 | 维护方式 |
| --- | --- | --- |
| 当前需求、提案、验证 | `.agents/dev/changes/<YYYY-MM-DD-topic>/` | 随本次需求更新 |
| 领域用语和别名 | `.agents/dev/notes/glossary.md` | 指向真实实体和所属领域 |
| 模块背景 | `.agents/dev/notes/context/<topic>.md` | 当前职责、约束和代码入口 |
| 决策理由 | `.agents/dev/notes/decisions/<YYYY-MM-DD-topic>.md` | 保留真实取舍，更新实现事实 |
| 错误经验 | `.agents/dev/notes/errors/<topic>.md` | 症状、条件、证据、处理与验证 |
| 学习导读 | `.agents/dev/notes/learning/<topic>.md` | 串联完整业务路径 |
| 需求历史 | `.agents/dev/archive/changes/<result>/<type>_<YYYY-MM-DD>-<slug>/` | 按[收尾方法](change-closure.md)保留交付或明确不实施事实，旧历史不自动迁移 |
| 退役笔记 | `.agents/dev/archive/notes/` | 保留独立历史价值 |
| 环境记录 | `.agents/dev/deploy/<environment>/` | 运行手册与发布证据分开 |

知识笔记日期表示首次提出主题的时间，依据真实记录；归档 change 日期沿用原任务的创建日期。不要为已有笔记批量重新命名。跨文档使用项目内相对 Markdown 链接。当前源码位置还应提供可搜索符号，不能只依靠容易漂移的行号。

目录与关键词搜索已经能定位时不建中央目录。内容增长后可增加 `.agents/dev/notes/index.md`，只记录主题、何时读取和链接，不复制正文，不把索引当作事实数据库。根 `AGENTS.md` 保持简短，只存高频约束和读取入口。

## 决策的当前状态

用自然语言说明状态即可，不建立机器状态流：

- **提议中**：仍值得推进、尚未完成的计划，留在当前需求中。部分实现不冒充完整交付。
- **已实施**：决定已交付；路径、名称、默认值和机制随实际代码更新。只更新事实，不把决定改成另一个决定。
- **已拒绝或已取消**：明确真实理由。拒绝说明只有仍能防止合理误判时才进入长期知识；取消需求仍可保留为需求历史。
- **历史记录**：实质决定已退出当前指导，但还有独立历史价值。显式标记历史身份和当前替代位置。

现役知识按主题选择文件夹，不维护封闭类别枚举；这与 change 归档时的五类主目标不同，不将归档分类扩散到 notes。笔记需要区分时，可用功能、缺陷修复、简化、架构、流程、验证等普通标签：架构讨论交付源码及模块关系，流程讨论周边工具、政策和工作方式。文件不因缺少标签而失效。

## 正式 ADR 与其他项目笔记

正式 ADR 通常同时满足难以逆转、缺少背景难理解和真实取舍三项条件。未满足三项、但仍有长期价值的机制或业务约束写入 context，错误与恢复经验写入 errors，术语写入 glossary。不要据此删除有价值知识，也不强制把项目已有有效记录迁移目录。以下记录与替代规则适用于全部有价值项目笔记。

## 何时新增或更新

只有代码、测试和现有文档不能解释的长期理由，才新建或更新笔记。机械搬迁、局部界面调整和执行流水通常不需要永久记录；但小改动仍可能承载长期命名、兼容性或所有权决定，不能只看 diff 大小。

已有记录负责同一决定时，更新它，不再创建副本。每篇新笔记都触发同主题替代关系检查：搜索同一决定、机制、旧名、新名和被拒绝方案，在同一次变更中处理已知冲突与重叠，不拖到未来全库清理。

### 实现事实变了

路径、符号、默认值、包名称或机制变化时，在同一变更中更新相关现役说明。原地改正旧事实，不在末尾追加时间流水。注明实际核对范围和提交或工作区状态。

### 决策反转

新建后继决定，说明新理由、替代范围、实际后果和重新考虑条件。旧记录保留当时的结论并交叉链接；不能把过去改写成与原决定相反的内容。

### 完整替代

只有旧记录每项有效内容都已被承接或确实失效，才可合并退出。当前负责记录须保存每项独特理由、备选方案、后果、否定保证、必要验证、命名覆盖缺口和恢复义务。修复全部入站链接；不能只依靠 Git 历史保存独有理由。

功能新增笔记只有在功能已从生产代码、配置、数据结构、持久化与传输格式、迁移和兼容行为中全部消失，没有当前文档声称可用，也没有测试将它当作受支持行为时，才可并入后来的移除记录。移除记录保留原始动机、为何不再成立、完全移除之外的方案、放弃的能力、重新引入条件，以及确认彻底移除的证据。验证不存在的测试仍有价值；只验证已删除行为的测试不是当前证据。

### 部分替代

移除一个传输、默认值、呈现或实现方式，不等于整个决定失效。旧数据、另一种消费者或兼容逻辑尚存时，保留相应解释和约束。两篇相互链接，明确哪些部分被承接、哪些继续约束现实。

## 保留、归档与删除

先判断是否只是小型界面调整或纯机械记录，且没有独有理由；这类内容可删除冗余说明，原需求证据按需求生命周期保留。

其他已实施笔记按未来决策价值判断。基础职责边界、持久化与传输语义、安全约束、反复出现的设计诱惑和重新引入条件仍可能指导未来修改时，保持现役，不看字数与年龄。决定已完整结束、未来指导有限但仍有历史价值时归档。既无未来指导也无独立历史价值的重复内容可以删除。

提议中工作不通过归档变成已实施。过时提案写明放弃原因；有意义的未完成任务留下下一步。已拒绝方案若不再合理、不可能重现或前提消失，就不继续占用当前检索。

## 文件格式

使用普通中文 Markdown，下面是可删减的写作骨架。没有真实内容的栏目删除；不要为满足模板编造历史。每份记录应能说明问题、结论和证据。

### 提案

```markdown
# <主题>

状态：提议中；首次提出：<日期>

## 问题
<独立说明动机，不预设解决方案。>

## 提案
<预期行为、实现约束、迁移步骤和待决问题。>

## 考虑过的方案
<真实方案及其取舍，不编造未考虑的方案。>

## 完成条件
<可观察的结果。>

## 风险与放弃的能力
<可能出错之处，以及已知代价。>
```

### 已实施决定

```markdown
# <决定>

状态：已实施；核对：<日期、提交或工作区状态、范围>

## 问题
<为什么需要作出决定。>

## 决定
<用现在时说明已经交付的行为。>

## 考虑过的方案
<真实选择及落选原因；没有记录时明确未知。>

## 后果
<获得什么、放弃什么、谁负责、何时应重新考虑。>

## 依据与覆盖缺口
<当前代码位置、符号、实际验证、尚未验证事项。>
```

真实备选方案对以后仍有用时必须保留；历史没有记录就写未知，不为模板补造。实现后把计划改写为已交付事实，将验收结果、风险和剩余缺口写入后果或验证，不保留误导性的待做清单。未完成部分留在当前需求。

### 已拒绝方案

保留原问题和方案，在开头说明拒绝理由。仍可能诱人重复犯错时，解释为什么不用、适用条件是否改变，以及重新考虑的触发条件。没有防误用价值时，不创建永久拒绝文件。

### 历史记录

记录归档日期、当时适用版本和当前替代位置。移动前检查目标冲突和入站链接；保持历史正文，不为当前代码重命名、格式偏好或新文档标准不断重写。历史不充当当前行为依据。独立的删密或事实纠错有明确需要时记录修订事实，不伪装成从未发生。

## 维护与复核

当前笔记检查现有路径与符号、逻辑事实、实际验证及入站链接。默认检索只读当前知识和代码，查历史时才明确进入 `.agents/dev/archive/`。归档资料出站链接可能已经过时，不给历史做无止境的链接追赶。

只更新亲自复核的范围，不批量刷新整库日期。没有运行环境就写“源码分析，运行未验证”；上线需要对应环境与版本的发布证据。当前代码说明实际行为，最新明确需求说明预期行为，两者不一致时并列说明差距。

文字的条件、主体、责任与失败不能在精简中丢失，详见[项目文字规范](writing-guide.md)。需要一个完整示例时，阅读[决策示例](decision-examples.md)。
