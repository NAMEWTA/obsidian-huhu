# 哪些知识值得长期保留

评估本次需求或独立复盘的知识是否应进入当前项目知识。默认只提取有持续用途的内容；其余留在来源需求或复盘中，不因暂不提升就删除证据。

## 三类识别信号

满足任意一类就值得进一步判断：

1. **稳定机制。** 长期架构模式、设计原则或系统约束，而非临时实现或过渡方案。例如“认证使用访问令牌与刷新令牌”可能是稳定机制；“暂时绕过限流，等待另一个修改合入”属于临时过程。
2. **重复教训。** 相同洞察在多个独立需求或会话中出现。按真实来源去重，多份报告引用同一事故只算一次。例如三个不同功能都暴露时区存储与展示转换问题。单个事件仍可能符合下一类，不机械等待复发。
3. **接手者必知。** 缺失该知识会导致后续开发错误选择或重复争论。例如数据库选择需要何种事务与查询能力；一般行长偏好通常没有这种价值。

这些是项目知识的识别标准。正式 ADR 另按[决策格式](decision-format.md)的三项条件判断；未达 ADR 条件不等于知识无价值。

## 通常不提取的内容

- 只对一次需求有效的实现细节，例如临时变量、中间搬迁步骤或孤立行号。
- 已被正式修复取代的临时绕路。
- 原始调试日志与排查流水，除非能提炼出可复用诊断方法。
- 脱离完整需求上下文就会误导的说法。
- 没有项目约束力的个人偏好。
- 尚未核实的猜测，或重复代码已经明确表达的事实。

原始证据依其生命周期保留；不要为追求“知识整洁”删除仍能解释问题的材料。

## 去重与证据

同一决定已被一篇 ADR 充分捕获时，它是唯一候选；日志和验证只补充其依据。仍须判断是否应进入长期知识，不能因为已经有当次 ADR 就跳过维护。

同一设计规则已由当前设计说明负责时，不从原型、日志与截图再生成三个候选。只有可定位的生产实现才能支持“已实施”；设计批准或需求完成状态不能代替实现证据。

## 判断顺序

1. 是否有持续用途？没有就留在原需求或复盘。
2. 是否仅为临时、误导或未证实内容？是则保留原范围，不提升为当前事实。
3. 是否已有负责记录？有则更新、补证据或保持不变；没有再按类型选择最小归属。
4. 是否与现有知识冲突？先核对当前代码、用户意图与历史依据，分清事实纠错与真正决策反转。

## 类型与默认归属

| 类型 | 判定特征 | 默认位置 |
| --- | --- | --- |
| 正式 ADR | 难逆转、缺背景难懂、真实取舍同时成立 | `.agents/dev/notes/decisions/` |
| 领域用语 | 本项目特有概念、用户别名与易混对象 | `.agents/dev/notes/glossary.md` |
| 模块背景和规则 | 当前稳定机制、责任和业务约束 | `.agents/dev/notes/context/` |
| 可复用错误与恢复 | 真实症状、触发条件、原因、处置和验证 | `.agents/dev/notes/errors/` |
| 跨页面设计规则 | 有实现依据的组件与交互约束 | 现有设计说明或模块背景 |
| 学习导读 | 能帮助接手的完整运行路径 | `.agents/dev/notes/learning/` |

新增资料统一位于 `.agents/dev/`，既有记录先按真实位置查阅引用，不擅自批量迁移或重命名。暂时性内容留在对应需求，明确归档时按[收尾方法](change-closure.md)保存到 `.agents/dev/archive/changes/<result>/<type>_<YYYY-MM-DD>-<slug>/`，result 为 implemented 或 rejected；保留原创建日期、内容与历史身份并修复链接，旧历史不自动迁移。已有独立复盘按真实位置引用。
