# 会话复盘与环境改进

用户要求进行一次**复盘**。你要提出对编码代理**环境**的改进建议，以改善未来的执行。

## 步骤

1. 阅读本地`dev-writing`（面向 Agent 的写作方法），获取写作指导。

2. 阅读用户指定会话的一手资料。这可能意味着搜索本机的会话日志。如果用户没有指定会话，默认使用当前会话。

3. 在以下类别中寻找改进候选。

- **导航**：代理找到正确文件有多容易？文件之间是否存在隐藏依赖？增加一个**导航指针**会不会更容易？当本次会话花了很长时间寻找一条信息时使用这一类。
- **自动检查**：能否通过自动检查发现代理犯过的错误？例如 lint、类型检查、测试、文件系统校验。先阅读仓库自己的检查命令，包括 `package.json` 或构建工具中的 `lint` / `check` 脚本及 CI 工作流；如果已有检查尚未接线或悄悄失效，发现应当是这一点，而不是重新发明检查。仓库缺少能够捕获已观察问题的防护检查时，将其作为具体发现。按项目类型选择 lint、类型检查、链接校验或实现后行为验证，不为纯文档小修改建立无收益的门禁。当代理犯了自动检查能够发现的错误，或者仓库根本没有防护检查时使用这一类。
- **编码规范**：是否应该给**审查代理**增加一条要执行的规则？是否应删除或澄清现有规则？先判断违规类型：**机械性**违规，例如固定语法模式、禁用 API、导入形式或文件位置规则，必须使用确定性检查。可以在仓库已有 linter 中增加自定义规则，也可以增加提交前钩子或 CI 任务；选择当前语言和现有检查体系中成本最低的方式。默认应建立检查，而不是增加文字规则。`CODING_STANDARDS.md` 仅用于真正需要**判断**的问题，例如跨文件一致性、是否符合周围风格，以及任何检查都无法替代的内容。当审查代理未能发现错误时使用这一类。
- **全局 AGENTS.md**：是否有引导指令应该移到编码规范或自动检查中？当仓库或用户全局范围的 AGENTS.md 特别大时使用这一类。
- **工具经济性**：代理是否执行了可以简化的昂贵工具调用？是否有自定义 CLI 或 MCP 工具特别消耗 token？当代理执行了昂贵工具调用时使用这一类。
- **无效指令**：寻找引导文件中不会改变代理行为的指令。当引导文件过大、难以维护时使用这一类。
- **信息访问**：寻找让代理更容易获取信息的机会，例如同时输出开发服务器日志、提供第三方服务的只读访问。当代理缺少关键信息时使用这一类。

4. 按严重程度向用户展示这些候选。

## 参考

### 实施与审查

记住，所有工作都经过实施和审查两个阶段。实施代理承受最大的**上下文压力**，因为它负责探索、编写代码和调试失败。

审查代理的上下文压力最小：它收到的是差异，因此不需要进行探索。它通常也不需要编写代码或调试。

评审时重点检查需要判断的编码规范；实施仍须遵守规格与已知约束。机械规则优先交已有自动检查。

### 文件

你可以访问仓库中的几类文件：

- `CLAUDE.md` / `AGENTS.md`：这些文件会被加入所有在该仓库工作的代理的上下文窗口。使用时应极其克制，通常只放指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：这一文件在审查时阅读，而不是实施时阅读。如果规范文件超过 1,000 行，增加指向文档目录的**导航指针**。
- 文档：将文档用作由其他文件指向的参考资料。在编写新文档前，先寻找已有文档。
- 技能：可以将技能用于文档，因为其描述会进入代理上下文窗口；也可以用于由用户触发的命令。遵循本地`dev-writing`（面向 Agent 的写作方法）。
