# 项目文字规范

写足以保留约定的内容，然后删除推理过程实录、重复与装饰。约定是调用者、被调用者、实现者、生产者或消费者所依赖的义务、不变量、前置条件、后置条件或兼容性承诺。本规范负责编辑判断及必要文字覆盖；知识位置和维护方法见[知识目录与笔记格式](notes-guide.md)。删除与结果无关的思考流水、重复和装饰，保留可核验事实、真实理由和必要约定。这是指导，不是脚本。

将 `contract`、`boundary`、`shape`、`surface`、`seam`、`gate` 和 `vocabulary` 视为使用前需要检查的术语，而不是禁用词。先问：直接写出准确规则、API、字段集、类型、校验、时点、组件拆分或失败，是否能更好表达事实？当术语确实指向准确技术对象时保留，包括调用者与被调用者的约定，以及安全或进程边界。

注释说明代码无法表达的不明显约定或理由，不重复代码已暗示的内容。

## 输入与排除项

从用户请求和当前变更确定范围，已经明确时直接执行。只有无法定位目标时才补问；不要把局部任务自行扩成全仓库。

接受 `mode: automatic | interactive`，默认为 `automatic`。只有用户明确要求提问或校准时才进入交互模式。

`mode` 控制是否提问，不控制写入权限。评审与审计任务只报告发现，不编辑；明确要求撰写、修复或精简的任务才执行清楚的修改。

发现、评审和编辑默认排除第三方目录 `vendor/`，即使请求范围是整个仓库也一样；用户明确要求维护已纳管副本时，按其范围处理。不通过符号链接进入它。排除条件放在包含通配符之后，避免后续包含规则将其重新纳入。例如 ripgrep 命令以 `--glob '!vendor/**'` 结束，Git 命令显式加入 `:(exclude)vendor/**` 路径限定。如果请求范围只包含 `vendor/`，报告没有符合条件的文件。

文字评审与编辑也排除 `.agents/dev/archive/notes/`。归档 项目笔记 是冻结快照；只有为理解指向历史的入站引用时才检查明确目标，不为了使正文或出站链接现代化而查看。

生成的目录、快照和样例属于派生物。编辑前追踪每个消费者：源 JSDoc 也可能供模型可见的生成目录使用。先编辑负责内容的源文件或场景，再重新生成全部派生物。生成器从源正文提取摘要时，要让提取后的句子在目标界面上语义完整。双语对没有永久主语言：更新时任一语言都可作为原创一侧。项目需要双语时，按相同结构最小更新对应语言；普通中文项目不建立配对文件或哈希台账。

## 保留完整命题

编辑前识别段落中的每个命题。保留所有相关的：

- 行为主体与动作。
- 条件、时机和顺序。
- 必须、可以、绝不等约束强度。
- 否定保证与例外。
- 责任归属、副作用、失败方式和后果。

只有所有事实分句都被保留、结果也更清楚时，才删除形容词、重复和叙述。字数减少本身不等于改进。

在使用位置保留完整的局部约定：调用者或维护者在那里需要知道的行为、失败、责任和后果。架构、理由、算法、历史或扩展示例尽量链接到负责解释的文档。一份解释只有一个归属处；必要约定事实可以在局部重复。

省略某个不明显理由可能造成误用或错误简化时，保留它。否则说明后果，并链接理由所在处。

## 不同文字位置的必需覆盖

这不是单向压缩。如果代码、类型和结构无法表达下列必要约定，就增加或恢复文字。当地已经显而易见的事实不加注释。

- **公开 JSDoc：** 说明调用者可见的返回值区别、抛出或拒绝、副作用、责任归属、时机、取消和持久性。
- **内部注释：** 解释非局部结构，以及明显复杂的局部结构，包括不变量、竞态顺序、责任归属、安全边界和意外失败行为。删除控制流旁白与代码复述。
- **模块注释：** 说明模块角色、依赖、责任，以及不明显的架构选择；架构选择链接到其负责解释的文档。
- **测试：** 只解释不明显的测试设计，例如为什么需要某个样例、断言、平台适配、真实入口路径或间接观察。删除逐步讲解和清单罗列。
- **操作指南：** 包含前提、必需动作、真实入口路径、可观察验证，以及简明警示。
- **README：** 包含消费者约定：配置、语义、失败、限制、扩展点和对模型可见的影响。引用包拥有的稳定模型可见文本；链接生成目录和跨包负责者。保留长期缺口和维护陷阱，不保留日常清理清单。按实际消费者需要选择章节，不创建空栏目。
- **项目笔记：** 保留独特理由、机制、备选方案、后果、已经交付的验证证据，以及明确指出的覆盖缺口。已实施 项目笔记 用现在时陈述交付现实；删除规划清单，但不删除支撑决策的证据。
- **事后复盘：** 保留事件顺序、证据、因果链、影响和预防措施。删除重复劝服，以及无法建立因果关系的实现细节。
- **技能和 Agent 指令：** 说明行为限制及明确范围约束，例如“这是指导，不是脚本或清单”。工作流程简洁，并链接其事实来源。
- **示例与配置注释：** 解释访问限制、不明显的接线或加载顺序、安全立场、重放行为、例外和可能的误用。不旁白配置本已展示的条目。
- **提示词与可见字符串：** 把措辞视为行为。客户端界面文字属于有类型的语言字典，通过显式本地化属性传入不依赖宿主框架的基础组件；一起检查正文、无障碍名称、提示、占位文字和格式模板，然后运行项目已有的相关本地化与界面检查。英文界面文案，包括插件 `meta.title` 和 `meta.description`，使用句首大写：仅首词、专有名词以及 `Chrome DevTools`、`Git` 或 `MCP` 等产品名大写，例如 `Git worktrees`，不写 `Git Worktrees`。中文文案遵循自身习惯。为模型可见文本更新负责该文本的可运行快照，以及仓库要求的图形界面证据。如果授权范围内没有负责此内容的场景，保持措辞不变并报告延后；不要悄悄把它夹进纯文字编辑。
- **诊断信息：** 明确失败主体或路径、违反的规则，以及不明显的修正方法。删除内部执行过程旁白。

保留可搜索的机制名称，以及有意义的语气、时序或否定强调。只规范装饰性强调。

## 工作流程

1. 确认范围、模式、当前分支或 PR 基准，以及适用的 `AGENTS.md`。不检查无关分支。
2. 判断段落前，阅读[知识目录与笔记格式](notes-guide.md)和负责该事实的代码或文档。需要校准或遇到陌生情形时，阅读[决策示例](decision-examples.md)。
3. 检查请求范围，不只检查最大的文件。用搜索和字数发现候选项，再按语义判断段落。
4. 将候选项分类为保留、增加、精简、恢复、重组或延后。仅在任务授权编辑时执行清楚的修改；不为达到删除目标而制造改动。
5. 先更新负责内容的源文件，再更新派生产物。学到新规则后，重新检查相似段落。
6. 运行相关的窄范围检查、文档检查、`git diff --check`，以及可见字符串的行为测试。确认最终差异没有 `vendor/` 路径；如曾意外匹配 vendor，要报告，而不是声称整个过程始终排除干净。
7. 报告检查范围、明确修改、有意保留、延后案例，以及实际运行的检查。

## 难以取舍的决定

只有至少两个版本都满足完整命题规则，却在公认原则间有取舍，而且本技能尚未解决该取舍时，才算难以取舍。只有一个保留完整命题的改写方案时，不属于此类。

自动模式下，得到授权后执行清楚的编辑，并报告真正难以取舍的案例，不提问。不要为了推进而削弱命题。

交互模式下，按支配原则归组相似段落。给出两到三个可行版本，推荐一个，并说明事实或结构差异。不提供明显较差的陪衬项。使用用户要求的渠道；通过行内评论校准 PR 时，在差异中放置推荐的暂定版本，将其他方案附到准确对应行。

用户决定后，将原则与版本提炼到项目当前有关说明，不包含 PR 历史或评审者旁白，并把学到的规则应用到范围内每个相似段落。
