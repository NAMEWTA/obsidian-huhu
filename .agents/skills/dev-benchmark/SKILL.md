# 性能数字必须能被解释

先写清待作决定、真实工作负载、指标、预期方向和能改变决定的差异，再测量。一次观察、统计比较、持续优化与只读取证有不同交付边界。

性能目标由本技能持续处理，已有调试中的负载、基线和复现证据直接复用。输出错误、崩溃等功能缺陷以 `dev-debug` 为主；本技能按需要核对测量中的正确性。

用户只要快速数量级估计，可以一次运行，仍核对错误与工作确实完成，并明确局限。选型、回退判断和优化成效不能伪装成快速估计来绕过比较。

## 核心纪律

- **核对测量本身。** 计时区域、完成工作量、错误数、输出正确性和限制因素都要有证据。剖析影响时间，诊断运行与正式计时分开。
- **公平比较。** 使用对应生产配置与现实数据，声明冷暖缓存、版本、并发和机器负载。不能调优的一侧，不包装成公平的实现优劣结论。
- **处理噪声。** 比较时交错运行两侧，记录次数、中位数与范围。差异小于自然波动，就报告没有可测差异，不强行选赢家。
- **核对整体。** 微基准改善与用户等待的端到端路径一起解释。用工作量与物理上限排除缓存、空操作和未完成任务。
- **一次改变一个可解释因素。** 持续优化冻结测量契约后再试验；修改驱动就重取可比较基线。只保留有证据且不破坏行为的结果。
- **沿用授权与范围。** 只读调查不修改应用或生产进程；负载、探针、临时观测、部署和外部写入都须在已有授权内。没有环境就说明证据缺口，不编造运行结果。

## 支撑方法与产物

`dev-guardrails`（真实证据）检查实际产物；`dev-guardrails`（可重跑工具）使测量可复查；`dev-guardrails`（可验证单元）安排迭代；`dev-guardrails`（共享状态隔离）避免试验污染；`dev-guardrails`（上下文预算）处理大型捕获；`dev-guardrails`（最小改动）与`dev-guardrails`（结构化经验）限制额外负担。

按[测量记录](assets/measurement.md)保存目标、环境、命令、样本、错误、工作量、限制因素和结论。持续优化可用[试验日志](assets/experiments.md)。新增测量记录和可持久化的结果放在 `.agents/dev/changes/<日期-主题>/`；已有产物按真实位置引用，私有原始数据留在受控位置。不记录凭据或无关业务数据。

长时间性能实验按`dev-workflow`（决策证据方法）记录重要选择并对照真实产物复核，可参考`dev-workflow`（决策记录）。试验日志已包含同样信息时复用它，不再维护重复账本。Markdown 为默认；TSV 与本地追加脚本只是该方法中的可选输出。通用开发任务的决策审计由 `dev-workflow` 承接。

## 报告

先说更快、更慢、没有可测差异或无结论，再给单位、样本次数、范围、限制因素和端到端影响。保存实际命令与证据位置，说明未验证条件。只读取证交付原因证据或最强假设；用户同时授权修复时才继续实现。
