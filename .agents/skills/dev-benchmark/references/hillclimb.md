# 围绕一个指标持续优化

负责指标与实验完整性。适用于持续迭代一个可测对象；一次性缺陷或性能修复使用[性能问题](performance-issue.md)。核心纪律是一次改动、一次测量、保留或回滚，不叠加尚未验证的改动，不凭读代码宣称收益。

## 完整循环

1. **先理解负载，再选指标。** 读取真实入口和架构，指出影响结果的数据量、历史、状态、并发等维度，选择能复现用户问题的场景。复现不了先修测量或澄清目标，不盲目优化。随后写清一个主指标、方向、成本预算与可检查停止条件。用户给出目标就沿用；没有时依据已有任务作合理可逆假设并说明，真正影响预算或方向的选择才补问。可以设置最低尝试数量防止早期偶然收益，但示例“提高 50% 且至少 10 轮”不是通用要求。
2. **证明驱动敏感性，再冻结测量契约。** 按`dev-guardrails`（可重跑工具）复用或构建最小驱动，确认目标负载能复现症状、简单场景能按预期区分。无法区分就修改负载或指标。冻结前运行[测量检查](measurement-checklist.md)，让驱动输出错误数、正确输出和完成工作量。冻结后，一条可重复命令产生指标，足够采样排除噪声，例如多次中位数。任何修改前记录真实基线和必须保持通过的回归检查；不是强制引入新的测试体系。
3. **维护试验日志。** 使用[试验记录](../assets/experiments.md)，每次一行：编号、假设、改动、之前、之后、变化、检查、保留/回滚、备注。已有日志格式优先，Markdown 或简单 TSV 均可，不建立状态引擎。原始工作日志可放代码树外或忽略目录；长期结论按项目知识约定保留。每轮先读已有结果，避免重复无效尝试。
4. **让假设指向机制。** 点名具体路径，例如“把 X 移出启动路径，因为它阻塞首次绘制”，不写“试着缓存一些东西”。性能问题按[性能问题方法](performance-issue.md)第 2 步的顺序排列假设，但持续优化使用自己的停止条件。
5. **每轮只检验一个假设。**
   - 限定文件、行为与可写边界。有独立代理能力时可委派；没有就直接实施并复核。多个独立试验各用隔离工作区和独立数据，按`dev-guardrails`（共享状态隔离）处理，禁止混用同一计时资源造成污染。
   - 用冻结驱动测量前后，并运行相关回归检查。比较顺序、负载与环境保持可解释。
   - 只有改善超过噪声且行为仍正确才接受；否则撤销本轮自身改动，保留证据。不要回滚用户或其他执行者的工作。
   - 接受的变化按已有交付授权形成聚焦提交，只暂存自己的文件，不使用会夹带无关改动的全量暂存。无论保留或回滚，都记录一行。每轮以检查结束，再进入下一轮。
   无人值守持续运行只使用实际可用且已获授权的调度能力；没有就当前会话执行、保存恢复点，不虚构后台循环。
6. **突破第一个平台期。** 多次停滞或拒绝时，换一类机制、重读源码，或在隔离试验中验证组合假设。更激进方案仍受范围和预算约束。正确性与简单性高于数字；破坏行为的收益撤销，数字不变但确实简化的改动可以按原任务保留，并明确它不是性能收益。
7. **按证据停止。** 达到目标、预算耗尽、环境受阻，或剩余收益不值得成本时结束。不要放宽指标假装达标，也不在还有便宜关键假设时无故退出。说明平台期后的探索和剩余未知，受阻不空转。修改驱动、负载或验收口径时，明确建立新的比较基线，不与旧数字直接拼接。
8. **交付接受的结果。** 按任务授权提交、推送或提出 PR，顺序体现被验证的改进。没有 PR 要求时不强制创建；用户指定不发布就停在该边界。

## 报告

说明指标与目标、基线到最终值、适用的百分比变化、轮次及保留/回滚数量、每个接受变化、日志与证据位置，以及继续时最值得验证的想法。分清更快、无可测差异、单纯简化和未确认假设。
