# 修复具体性能问题

负责测量依据、方案、审查和数字核验。每个修复关联真实测量，不用阅读源码替代测量。只要求调查时，停在有证据的诊断；明确授权修复时继续实施。

1. **捕获基线。** 用当前可用、与目标界面相符的工具记录真实场景。按[测量检查清单](measurement-checklist.md)核验基线及之后每个数字。正式计时与剖析运行分开；不能运行时说明缺口，不声称已找到性能上限。
2. **建立机制假设。** 沿入口、处理、存储、返回与等待路径理解代码，把热点映射到符号。按下列顺序先尝试成本低的办法：
   1. 不做它：停止结果无人使用的工作，不只是使它更便宜。
   2. 做，但不重复做。
   3. 少做。
   4. 晚些做。
   5. 在用户不等待时做。
   6. 并发做。
   7. 更便宜地做。
   较早方法已达到目标时停止，不为穷尽清单引入复杂度。
3. **依据轨迹修复。** 跨函数或模块且存在实质取舍时，先比较接口、状态和所有权方案；局部明确修改直接实施。有独立范围及可用代理时可以委派，模型与推理能力使用当前工具真实支持的设置，无代理就直接完成。审查差异，再捕获修复后的同一场景。按`dev-guardrails`（可验证单元）完成本轮检查，再试下一次。
4. **解析并比较。** 使用适合产物的解析器、查询或差异比较，例如把大 JSON 转为可查询表。保留测量契约、工作量、错误、样本范围与限制因素；无结论或错误界面不是通过。源码证据、微基准与端到端效果分开陈述。
5. **保留结果证据。** 将新增的实际测量与命令放 `.agents/dev/changes/<日期-主题>/`，引用已有证据，按[测量记录](../assets/measurement.md)组织。涉及 PR 时正文引用主要结果，完整样本与诊断放本地可复查产物；其他交付方式同样保存证据。
6. **按当前授权交付。** 用户要求的提交、推送或 PR 流程继续完成；不把性能修复自动扩为发布，也不为了套流程强制新建 PR。

围绕指标持续改进而非一次修复时，使用[持续优化](hillclimb.md)。报告基线、修复后数字、变化、端到端意义、产物位置与剩余不确定性。
