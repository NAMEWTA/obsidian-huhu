# 委派与整合

## 委派简报

给代理足够的任务上下文，而非整段对话：

```markdown
目标：<用户想达到的结果>
本项交付：<一个完整切片>
契约：<spec / task 的精确路径或已读取内容>
已确认约束：<包括本次授权边界>
可写范围：<模块、文件或分支>
其他人拥有：<不可覆盖的共享内容>
前置产物：<依赖路径与已验证提交>
完成证据：<运行场景、命令或可检查产物>
持久化：<进度与结果写在哪里>
实施方式：按任务目标、风险和反馈成本选择规格推进、测试先行或直接实现；说明公共接口与完成证据。
```

能共享文件系统时用路径；不能共享时给必要的原始材料，不能假设代理能看到另一个代理的对话。不要在独立审查任务里暗示应找到什么结论。

## 唯一写入者

一个文件、分支或共享状态由一个明确所有者负责。优先按独立产物拆分；存在紧密耦合的变更交给同一实施者。

工作树是隔离不同分支的一种方式，不是每项任务必建的仪式。创建前检查已有工作树与未提交修改；不重置或覆盖不属于本次任务的内容。

单独上下文适合独立实现和审查。若后续任务确实依赖昂贵的运行状态，可以继续让原代理完成相关工作；不为固定“新代理”规则丢失事实或重启整个环境。

## 整合

先确认依赖版本，再阅读实际 diff、产物与检查结果。共享契约发生变化时，整合者负责通知受影响的实现者并验证接口。

合并后验证组合行为。两个切片各自通过并不证明它们一起工作。重复验证以具体剩余风险为理由；不要不加判断重跑所有成本高昂的检查。

采用本项目已经约定的分支、提交和交付流程。仅在任务确有需要时创建整合分支；不要自动把直接推送请求改成 PR 流程，也不要把用户要求的 PR 跳过。

## 结果简报

每项结果写清：实际改了什么、满足哪条契约、在哪里验证、当前产物版本、还有什么未完成。完成依据是可检查产物，不是代理的状态文字。

最终负责者仍需核对远端或交付面，区分“本地提交”“已推送”“PR 已创建”“已合并”“已上线”。这些不是同一个结果。
