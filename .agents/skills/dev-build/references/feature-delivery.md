### 功能开发

**你负责设计、规划、审查与验证。** 有独立工作和可用代理能力时委派实现；单人任务直接实施，同时保留独立复核步骤。

1. 读取受影响子系统的真实入口和行为；非平凡变化按本包模块探索方法建立完整运行路径。
2. 存在实质接口、状态或模块取舍时，按本包架构方法比较不同结构；已有明确局部形态的小改动直接实现。
3. 非平凡多步骤工作检查以下四个维度，只记录实际影响执行的决定；单文件或没有并行机会时用一句话说明即可，不建立空待办。
   - **阻塞性前置步骤。** 在扇出之前完成门禁。
   - **独立工作流。** 不重叠的文件、服务或层可以并行；共享写入必须串行。
   - **共享可变状态。** 默认拆分目标（**先隔离共享状态** 工程原则）。只有真实不变量要求时才串行。
   - **最小安全拆分。** 如果一个执行者最好，说明原因。
4. 先命名数据形态和组织结构：用状态机替代分散布尔量，用表或注册表替代重复分支，用类型模型替代跨文件形状假设。存在独立可写范围且有子智能体能力时，给实施者明确文件路径、契约、数据结构和成功标准，默认继承当前可用模型。实现有多种重要有效形态，如错误处理、抽象层或验证结构时，按本地执行支持的方案比选流程独立探索并交叉评判。没有并行工具或拆分收益时，直接实施并在完成后另做复核；不能伪称独立审查。不要通过等待嵌套代理的“待命”回复提前结束。注释按本地技术写作规则，只说明非显然原因。做精准修改；对依赖代码先读取当前真实版本。共享原语改进同步到所有相关消费者，并验证每个受影响的接口。提交按用户授权与项目流程进行。
5. 在匹配的界面上验证。“无结论”或在错误界面验证都不算通过，必须指出。
6. 按可验证单元组织实现和提交，每个小单元完成后验证再继续。需要 PR 堆叠时按真实依赖排列；只有实际分支状态需要且授权覆盖时才变基，保护已有用户工作，不为小改动强制整理提交。
7. 设计有争议时，交付前运行 `对抗审查`。
8. 交付目标包含 PR 时执行 **PR 交付流程**，否则按当前授权的提交或交付方式收束。

代码耦合工作（一个功能、一次迁移）交给单一负责人，检查点直接放在其任务中。负责人在阻塞阶段结束后自行扇出。父级扇出用于产出独立成果的切片（审计、跨子系统调查、竞争性实验）。在阶段边界重写检查点。创建新的负责人，不要串联中断。

**回复：** 构建了什么、选择了什么及原因、吞吐检查点、开放决策。设计替代方案用表格。
