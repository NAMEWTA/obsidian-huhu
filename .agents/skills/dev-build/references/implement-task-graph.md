# 按任务图实现

你已收到一份规格。这份规格应关联一些工单，说明如何实现规格。

应当已经向你提供问题跟踪器。如果没有，使用当前项目的 Markdown 任务记录或已连接跟踪器；没有远端跟踪器不阻塞本地工作。

目标是在同一条**整合分支**上实现整份规格，并按当前授权和跟踪器约定标记完成；关闭外部工单须有授权。

这些工单不是步骤列表，而是一张具有阻塞关系的**任务图**。这意味着始终存在一组可以开始处理的工单，即**工作前沿**。

每个子代理启动时都使用新的上下文窗口。

与子代理之间的通信应当稀疏。主要通过**上下文指针**通信：指向规格、工单、研究笔记和先前提交。不要重复已经可以通过指针获取的信息。

尽可能让**实施子代理**在后台运行，以获得最大的并发度。

## 步骤

1. 阅读规格与工单，理解任务图。

2. （可选）使用一个**探索子代理**完成工单需要的探索，例如相关代码文件或外部文档。确保探索子代理可以保存文件：它应将 Markdown 笔记保存到仓库之外、后续所有子代理都能访问的目录。这样**实施子代理**就能专注于实现，而不是探索。

3. 创建整合分支。如果问题跟踪器通过 PR 关闭工作，或者用户要求 PR，在第 5 步第一次合并之后创建草稿 PR，并标记其将关闭规格与工单；没有领先 main 的提交时无法创建 PR。

4. 每个工单使用一个新的**实施子代理**，各自在自己的工作树和分支中工作。每个实施子代理都应：
   - 开始前确认自己的工作树基于整合分支；如果不是，先保留其已有工作，再创建或切换到正确基线的隔离工作树，不硬重置他人修改；
   - 明确工单契约，按目标与风险选择实现方法；适合测试先行时使用`dev-tdd`（测试驱动方法），取得真实验收证据；
   - 报告完成前，将整合分支的最新提交合并到自己的分支。

5. **实施子代理**完成后，使用一个**合并子代理**将其工作合并到整合分支。

6. 如果这改变了可处理工单的**工作前沿**，启动更多**实施子代理**处理新工单，以获得最大的并发度。

7. 所有工单完成后，对整合分支按本地 `dev-review`（两轴审查）。用一个新的**实施子代理**核实代码审查问题，修复已确认且属于本次范围的问题。

8. 如果存在草稿 PR，将其标记为可供审查。否则按当前授权和跟踪器约定标记完成；关闭外部工单须有授权，并报告整合分支。

9. 只清理本次创建、工作已保存并确认不再使用的**实施子代理**工作树。
