# UI 原型

## 阅读导航

在同一路由生成**几种截然不同的 UI 变体**，通过底部浮动栏切换。用户在浏览器切换，选一个或从各个变体取其所长，然后丢弃其他方案。

如果问题涉及逻辑或状态而不是外观，选错了分支。使用 [逻辑原型](logic-prototype.md)。

## 何时适用

- “这个页面应该是什么样？”
- “定稿前我想先看几个仪表盘选项。”
- “给设置界面试一个不同布局。”
- 任何用户否则会花一天在脑中三个模糊草图之间选择的情况。

## 两种子形态：强烈优先采用 A

UI 原型**紧挨应用其余部分**时更容易判断：真实页头、真实侧栏、真实数据、真实密度。独立的一次性路由如同真空，每个变体孤立看都不错。只要存在合理的已有承载页面，默认选 A。只有确实没有邻近落点时，才选 B。

### 子形态 A：调整已有页面，优先采用

路由已经存在。变体渲染在**同一路由**，由仅在开发环境生效的 `?variant=` URL 查询参数控制。已有数据获取、参数和认证都保留，只切换渲染。这是默认选择，除非有具体理由不这样做。

如果原型对象暂时没有自己的页面，但**自然应该位于某个页面内部**，例如仪表盘新增一节、设置界面新增卡片、现有流程新增一步，它仍属于 A。把变体挂在承载页面内。

### 子形态 B：新页面，最后手段

只有对象确实没有可容纳它的已有页面才使用，例如全新顶层界面，或无法合理嵌入现有位置的流程。

按项目现有路由惯例创建**一次性路由**。不发明新顶层结构。名称要明显是原型，例如路径或文件名包含 `prototype`。同样使用 `?variant=` 模式。

决定选 B 前再检查：真的没有已有页面可嵌入吗？空路由会掩盖有内容页面能暴露的设计问题。

两种子形态使用相同的底部浮动栏。

## 流程

### 1. 说明问题并选择数量 N

默认 **3 个变体**。超过 5 个就开始变成噪声，难以保持截然不同，因此最多 5 个。

在原型所在位置或文件顶部注释中，用一行写下计划：

> “在已有 `/settings` 路由中提供三个设置页面变体，通过 `?variant=` 切换。”

无论用户是否在场提出意见，这样都有效。

### 2. 生成截然不同的变体

起草每个变体。各自都要符合：

- 页面的目的和可访问的数据。
- 项目的组件库或样式系统，例如 TailwindCSS、shadcn、MUI、普通 CSS 等。
- 清楚的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构不同**：布局不同、信息层级不同、主要操作入口不同，而不仅是颜色不同。三份略微调整的卡片网格不是 UI 原型，只是壁纸。如果两个草稿太相似，就明确加上“不要使用卡片网格”的指示重做一个。

### 3. 连接变体

在路由上创建单一切换组件：

```tsx
// 伪代码，按项目框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于 A，即已有页面：把全部已有数据获取保留在切换器上方，各变体只改变渲染子树。

对于 B，即新页面：`/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 构建浮动切换器

在屏幕底部中央放一个小型固定位置栏，包含三部分：

- **左箭头**：循环切到上一个变体，到头后回绕。
- **变体标签**：显示当前变体键值；如变体导出名称，也显示名称，例如 `B（侧栏布局）`。
- **右箭头**：循环切到下一个变体，到头后回绕。

行为：

- 点击箭头更新 URL 查询参数，使用框架路由器，例如 Next 的 `router.replace`、React Router 的 `navigate`，让变体可分享且刷新后保持。
- 键盘 `←`、`→` 也能循环切换。焦点位于 `<input>`、`<textarea>` 或 `[contenteditable]` 时，不拦截方向键。
- 与页面在视觉上明显不同，例如高对比胶囊形和轻微阴影，让人看出它不是被评估设计的一部分。
- 生产构建中隐藏：用 `process.env.NODE_ENV !== 'production'` 或等效检查控制，避免意外合并原型时把控制栏发布给用户。

把切换器放在单个共享组件中，供两种子形态复用。位置遵循项目共享 UI 所在目录。

### 5. 交给用户

给出 URL 和 `?variant=` 的键值。用户有空时会切换查看。最有价值的反馈通常是**“我要 B 的页头配 C 的侧栏”**，那才是他们真正想要的设计。

### 6. 记录答案并清理

某个变体胜出后，记录答案，包括哪个变体和原因，再按 [原型方法](prototype-method.md) 的方式保留原型。把胜出方案融入真实代码，其余移动到隔离原型目录或分支，不进入主分支：

- **子形态 A**：把胜出方案融入已有页面；从主分支移除未选变体和切换器。
- **子形态 B**：把胜出变体提升为真实路由；从主分支移除临时路由和切换器。

完整变体集是一手资料，所以应该进入隔离原型目录或分支而不是垃圾桶；把变体组件和切换器留在主分支会迅速腐化，并让下一个读者困惑。

## 反模式

- **只在颜色或文案上不同的变体。** 那是微调，不是原型。真正的变体在结构上有不同主张。
- **变体之间共享太多代码。** 共享 `<Header>` 可以，共享 `<Layout>` 会破坏目标。每个变体都应能自由抛弃布局。
- **把变体连到真实写操作。** 只读原型可以；需要修改时使用桩。问题是“应该长什么样”，不是“后端能不能工作”。
- **直接把原型升为生产代码。** 变体在原型约束下编写，没有测试且错误处理很少。正式融入时需要按生产要求重新编写。

原型仅回答问题，不等于正式交付。正式实现根据已明确的行为选择测试先行、实现后验证或组合方法；保持原型数据隔离，不让生产构建暴露原型分支或选择器。
