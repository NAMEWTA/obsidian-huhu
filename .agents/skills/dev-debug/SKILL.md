# 根因诊断与修复

以紧凑反馈路径、最小复现、可证伪假设与针对性观测开展科学排查，并在同一交付面复核。诊断先确定发生了什么；修复按明确的预期行为完成。

普通报告可来自聊天、Issue、UI、HTTP 或 CLI，不要求来源线程自动化。已配置来源适配器、可信分诊及真实 UI 控制的报告处理可使用 `dev-issue-fix`；来源平台不限定为 Slack。调查发现目标实为性能改善时，优先使用已安装的 `dev-benchmark`，沿用已有基线和证据，不重启调查。

明确期望、建立反馈路径、调查事实，再按目标与风险选择修复方式。存在能触发真实缺陷的公共接口时，可以先用失败回归测试锁定问题，再完成最小修复；低成本测试路径采用已安装的 `dev-tdd` 的缺陷回归分支，不再运行新功能的完整测试先行流程。调用返回的失败→最小修复→通过证据直接并入当前诊断。真实运行复现更合适时继续沿实际入口验证，不把自动化测试作为每个故障的先决条件。

完整主线使用[缺陷修复手册](references/bug-repair.md)。需要缩短反馈路径或选择诊断工具时，补充[科学诊断方法](references/diagnostic-method.md)，不是重新启动第二次调查。

## 建立有效观察路径

先读取报告、预期行为、环境、版本和相关领域词汇。已有代码与 ADR 有助于定位，但不能替代观察用户实际遇到的症状。

尽早找到可以由自己运行的观察路径：原应用操作、HTTP 请求、CLI 输入、现有检查、捕获数据重放或一次性诊断探针。选择能观察**同一问题**的入口，不能用“程序没崩溃”代替具体症状。

把路径做得尽可能快、稳定、可重复：缩小启动范围、固定输入与时间、隔离文件、标记网络依赖。对间歇性问题记录触发次数与失败次数，用压力或受控时序提高可观察率；不承诺单次运行能证明消失。

阅读 [诊断手段与记录](references/diagnostic-loop.md) 选择适合的问题观察方式。无法直接触及目标环境时，先推进能做的只读分析，明确尚不能证实的结论，并具体索取缺失的环境或脱敏材料。

## 缩小并解释故障

确认观察到的是用户报告的故障，而非另一个相邻错误。保存相关输入、环境、原始现象和必要日志；输出前脱敏，避免把凭据写进命令、截图或工作记录。

逐项缩小输入、配置、调用路径和时序，每次只改一个条件。保留复现所需的最小场景，同时保留原始场景供修复后复核。

列出真正有依据的候选机制，按可能性排序。每项写一个可证伪预测：“如果 X 导致问题，观察或改变 Y 应当产生 Z”。不要为了凑数量编造假设。

优先做能排除最多候选的探针。适用时用二分、调试器或针对性日志；不无目的地打印全部状态。临时观测使用唯一标记，便于最终删除。

证据否定某个假设时，撤掉仅为它添加的修补，再选下一项。出现多次相同失败时检查共同前提，不在错误前提上继续堆保护分支。

## 按契约修复

找到根因后明确修复后的行为和边界。小修复写在当前记录即可；涉及权限、数据丢失、持久化格式或交互语义时，把决定补到规格。

在正确入口建立反馈并完成修复。合适的回归测试应先在缺陷仍存在时失败，修复后通过；检查必须覆盖真实触发模式，多调用者或时序问题不能用单个浅层断言冒充覆盖。没有合适自动化入口时说明缺口，使用真实运行证据，并评估是否需要调整结构。

仅保留证据支持且解决本次目标的改动。与问题无关的重构或“可能也有用”的兜底另行处理。

## 验证与收尾

重走原始场景及最小场景，核对相同症状是否得到解决。UI 故障回到实际界面，CLI 故障回到命令，服务故障回到原接口；其他层的检查不能代替。

故障涉及性能时使用一致负载、环境与测量定义比较基线和结果，记录波动及约束；完整过程见`dev-benchmark`（性能问题）。不用不同场景的数值计算提升比例。间歇性问题报告运行次数与观察结果，而非“再也不会发生”。

删除本次临时观测与探针，或将仍有复用价值的工具明确归位。只清理自己创建的内容。运行相关现有检查，必要时补回归验证，充分证明后停止无目的重复。

输出症状、证实的根因、实际修复、同路径证据和剩余限制。新增记录统一保存在 `.agents/dev/changes/<YYYY-MM-DD-slug>/evidence.md`；已有证据按真实位置引用。仅有跨迭代价值的陷阱才进入 `.agents/dev/notes/errors/`，包含适用条件、最新代码指针与复核日期，避免把单次日志长期堆积。
