### 缺陷修复

**你负责本任务。规划、审查、验证。** 存在独立调查或实现范围且具备代理工具时委派，自己主导；否则直接调查和实现，并另做证据复核。按本包执行支持选择当前工具实际提供的能力；无独立代理时顺序完成并说明限制。

保持科学。每行交付代码都追溯到运行证据。“也许有用”的双保险是假设，不是修复，不交付。证据反驳假设时，回滚它促成的改动。只交付证据支持的最小变化。

1. 通过控制技能在匹配界面亲自复现，见不可妥协项，即使调试或观测协议让你请用户复现。只有给出明确具体理由，说明控制界面无法触及目标，且已驱动到能力边界后，才询问用户。不能直接复现时，合成触发条件、收紧条件或加入观测，争取获得可复现信号。确实缺少目标环境或访问时，记录尝试与不可达原因，请求最小补充材料，不无限循环或编造复现。
2. 二分定位原因。形成候选假设，再逐项排除直到仅剩一个。先调用 `dev-learn` 理解受影响子系统，用 `dev-why` 查回归历史。每轮选能切掉最多剩余问题空间的分割，获取运行证据并排除。程序状态不清时加观测或日志，运行中读它，不猜。长期或顽固排查持续迭代；需要后台观察时只使用宿主实际提供的调度或事件能力，没有时保存恢复点并在当前会话推进。步骤 3 的架构设计或对抗审查前，先用运行证据确认剩余的*机制*。
3. 规划修复。跨函数边界且存在设计取舍时先调用 `dev-architecture`。缺陷有低成本本地测试路径，或用户明确要求失败测试时，先调用 `dev-tdd` 的六步回归修复，保留失败在先的证据；测试昂贵、依赖大量集成或路径不清时，使用当前最接近症状的运行检查。用已配置缺陷修复模型，默认继承当前会话模型，有代理能力时给出具体范围并委派实现；否则由当前执行者完成同样的契约实现与复核。
4. 在同一界面验证。原始复现现在通过。“无结论”或错误界面不算通过，必须指出。单元测试显示分支行为，不能证明缺陷不存在。
5. 按能够自证的顺序整理已完成的复现与修复证据。仓库允许时，让失败复现位于修复之前的提交；不允许中间失败提交时，在同一可落地单元中保留前后运行证据。这里整理的是第 3 步已有证据，不重新调用测试流程或再修复一遍。可验证单元原则由 `dev-guardrails` 维护。
6. 交付目标包含 PR 时调用 `dev-deploy` 的 PR 准备方法，否则按当前授权的提交或交付方式收束。

**回复：** 什么坏了、根因、修复、如何验证。原样粘贴先失败后通过的复现输出。
