# 诊断手段与记录

## 选择观察方式

按问题的真实表面选择最小充分方式。测试先行和真实运行复现都可使用：

| 方式 | 适合的现象 | 需要保留的事实 |
| --- | --- | --- |
| 实际应用操作 | UI 状态、交互、桌面集成 | 操作路径、画面、相关控制台或网络信号 |
| HTTP / API 调用 | 服务行为、鉴权、请求处理 | 脱敏请求、响应、版本与环境 |
| CLI + 固定输入 | 输出、退出码、文件产物 | 输入、stdout / stderr、退出码、结果文件 |
| 行为测试 | 已有检查或新回归测试能观察同一故障 | 公共接口、原问题造成的失败、覆盖边界 |
| 捕获数据重放 | 难以实时重现的请求或事件序列 | 脱敏数据、重放条件、版本 |
| 一次性诊断探针 | 大系统中可隔离的小路径 | 真实依赖与调用、明确观察值 |
| 受控压力或随机输入 | 间歇性错误、竞争、边界输入 | 种子、次数、负载、失败比例 |
| 提交或数据二分 | 已知好坏两个版本之间的回归 | 好坏端点、相同观察方法、定位结果 |
| 差分运行 | 旧新版本或配置行为不同 | 相同输入、可比环境、差异 |
| 人协助复现 | 当前环境确实无法触达的表面 | 缺失能力、明确步骤、所需脱敏输出 |

诊断探针是收集证据的工具。有价值且稳定的最小复现可在修复前转为失败回归测试，再观察修复后通过；临时探针不必全部长期保留。

## 简短记录

可以写入已有 `evidence.md`，不强制独立文件或 JSON。

```markdown
## 故障现象
环境 / 版本：<实际观察>
期望：<用户或规格要求>
实际：<具体症状>
原始复现：<命令或操作>

## 最小场景
<已经实际运行的输入与条件>
结果：<脱敏输出或截图引用>

## 假设与证据
- 假设：<可证伪机制>
- 预测：<改变或观察什么，应该看到什么>
- 结果：<实际证据>
- 结论：<支持 / 排除 / 还不足>

## 修复
<根因，契约，实际代码变更>

## 实现后的验证
<原始场景、最小场景、重要回归；命令与真实结果>

## 剩余限制
<还没有观察到的环境、低复现率、缺少入口等>

## 清理
<本次临时探针、日志及需要保留的工具>
```

## 间歇性问题

固定可控制的变量，记录剩余不可控制因素。提高触发率可以帮助定位，但受控环境结果不能直接推广为所有生产情形。

修复后使用相同负载与次数复核。报告“在 N 次运行中未观察到故障”，不要写成数学意义的永久保证。

## 性能问题

先说明测量代表什么：用户等待时间、某段计算、I/O、吞吐还是内存峰值。使用同样场景比较，关注缓存、热身、后台负载和测量本身的开销。

问题是查询变慢就读查询计划与真实数据分布；问题是持续 CPU 就抓取相关性能样本。大量日志可能改变时序和开销，不能默认是合适的性能探针。

## 可复用错误知识

只有能改变未来行动的经验才进入长期记录：

- 在什么条件下发生。
- 如何识别及排除相似现象。
- 真实根因与当前修复入口。
- 观察日期 / 提交，何时需要重新验证。

原始大日志、已被否定的猜测和一次性操作流水留在本次记录，归档时引用即可。
