# 缺陷诊断

用于困难缺陷的一套纪律。只有明确说明理由时才跳过阶段。

探索代码库时，阅读项目已有术语表（例如 `GLOSSARY.md` 或 `.agents/dev/notes/glossary.md`），建立相关模块的清晰心智模型，并检查所涉及区域的 ADR。

## 脱敏

本技能要求展示命令、输出与捕获产物。**先对每一个秘密脱敏**，以 `<REDACTED>` 替代。围绕环境变量建立循环，使凭据留在环境中，而不是进入展示内容。捕获产物可能携带认证头，只引用能够提供信号的行。

如果脱敏后的输出不足以诊断，说明情况并询问用户。

## 阶段 1：建立反馈循环

**这就是本技能的核心。** 其余内容都是机械操作。如果针对缺陷建立了**紧凑**的成功/失败信号，而且它会在这个缺陷出现时变红，就能找到原因；二分、假设检验和观测工具都只是消费这一信号。没有这样的信号，盯着代码看再久也救不了你。

在这里投入不成比例的精力。**积极尝试，发挥创造力，不要轻易放弃。**

### 构造方式，大致按以下顺序

1. 在真实公共接口写一个能捕获准确症状的**失败测试**，或运行已经存在的失败测试。若此处没有合适接口，继续选择下面能观察同一故障的反馈方式，不用浅层断言冒充复现。
2. 对正在运行的开发服务器执行 **curl / HTTP 脚本**。
3. 用固定输入执行 **CLI 调用**，将 stdout 与已知正确快照比较。
4. 用 **无头浏览器脚本**（Playwright / Puppeteer）驱动界面，并对 DOM、控制台或网络做断言。
5. **重放捕获的轨迹。** 将真实网络请求、负载或事件日志保存到磁盘，在隔离条件下沿代码路径重放。
6. **一次性执行环境。** 启动系统的最小子集，例如一个服务和模拟依赖，通过一次函数调用触发缺陷代码路径。
7. **属性 / 模糊输入循环。** 如果问题是“有时输出错误”，运行 1,000 个随机输入并寻找失败模式。
8. **二分执行环境。** 如果缺陷出现在两个已知状态之间，例如提交、数据集或版本，自动执行“在状态 X 启动、检查、重复”，以便用 `git bisect run` 运行它。
9. **差异循环。** 将同一输入分别交给旧版与新版，或两组配置，比较输出。
10. **人工参与的 bash 脚本。** 这是最后手段。如果必须有人点击，用 `manual-reproduction.md` 引导其操作，使循环仍有结构，再把捕获输出反馈给你。

建立正确反馈循环后，缺陷就已经解决了 90%。

### 收紧循环

把循环当成一个产品。获得某个循环之后，继续**收紧**它：

- 能否更快？例如缓存准备过程、跳过无关初始化、缩小测试范围。
- 信号能否更清晰？例如针对具体症状断言，而不是只检查“没有崩溃”。
- 能否更确定？例如固定时间、随机种子，隔离文件系统，冻结网络。

一个耗时 30 秒且不稳定的循环，几乎不比没有循环更好；一个两秒完成且确定的循环足够紧凑，是调试中的强大能力。

### 非确定性缺陷

目标不是完美复现，而是**提高复现率**。循环触发 100 次、并行执行、增加压力、缩小时序窗口或注入等待。50% 概率发生的缺陷可以调试，1% 不行，因此应持续提高概率，直到足以调试。

### 确实无法建立循环时

停下来并明确说明，列出已经尝试的办法。请用户提供：(a) 可以复现的环境访问权限；(b) 已脱敏的捕获产物，例如 HAR、日志转储、core dump 或带时间戳的录屏；或 (c) 添加临时生产观测的权限。**不要**在没有循环的情况下继续假设。

### 完成标准：紧凑且能够失败的循环

当循环足够**紧凑**并且**能够变红**时，阶段 1 完成。你应能够给出**一条命令**，例如脚本路径、测试调用或 curl，而且这条命令已至少运行过一次；展示脱敏后的调用和输出。它需要满足：

- [ ] **能够变红**：驱动实际缺陷代码路径，断言**用户描述的准确症状**，从而在存在缺陷时失败、修复后成功。不能只验证“运行时没有报错”；必须能够捕获这个具体缺陷。
- [ ] **确定性**：每次运行得到相同判断；不稳定缺陷则按前述方法固定较高复现率。
- [ ] **快速**：以秒而不是分钟计。
- [ ] **代理可运行**：能够无人值守运行；人工只通过 `manual-reproduction.md` 参与。

如果发现自己在这条命令存在之前就开始阅读代码构造理论，**停下来：直接跳到假设正是本技能要防止的失败。** 没有能够失败的命令，就不能进入阶段 2。

## 阶段 2：复现并最小化

运行循环，观察缺陷出现时它变红。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是附近另一个偶然失败。缺陷找错，修复就会错误。
- [ ] 失败可以在多次运行中复现；对于非确定性缺陷，复现率足够高，能够据此调试。
- [ ] 已捕获准确症状，例如错误信息、错误输出或缓慢耗时，以便后续确认修复确实针对该问题。

### 最小化

出现失败后，将复现缩小为**仍然能够失败的最小场景**。输入、调用者、配置、数据、步骤都**一次削减一项**；每次削减后重跑循环，只保留对失败不可或缺的内容。

这样做是因为最小复现会缩小阶段 3 的假设空间，剩下的可疑变化因素更少；它也可成为阶段 5 中有价值的回归测试，先锁定失败再证明修复。

当**每个剩余元素都不可或缺**时完成：删除其中任一元素都会让循环成功。

未完成复现和最小化前，不要继续。

## 阶段 3：提出假设

在测试任何假设前，先生成 **3–5 个按优先级排列的假设**。只生成一个假设，会使注意力锚定在第一个貌似合理的想法上。

每个假设必须**可证伪**，说明它预测什么。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会让缺陷消失，或 <改变 Z> 会使它更严重。”

无法说明预测的假设只是感觉，应该丢弃或使其更明确。

**在测试前向用户展示排序后的列表。** 用户常有领域知识，能够立即改变排序，例如“我们刚部署了第 3 项的相关改动”，或者知道哪些假设已经排除。这是成本很低、却能节省大量时间的检查点。不要阻塞等待；用户不在线时就按当前排序继续。

## 阶段 4：增加观测

每个探针都必须对应阶段 3 的一个具体预测。**每次只改变一个变量。**

工具优先级：

1. 环境支持时使用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能够区分假设的边界添加**针对性日志**。
3. 不要“把所有内容记进日志再搜索”。

为**每条调试日志加唯一前缀**，例如 `[DEBUG-a4f2]`，最后一次搜索即可完成清理。没有标签的日志容易残留，有标签的日志容易删除。

**性能分支。** 性能回归通常不适合用日志排查，应先建立测量基线，例如计时执行环境、`performance.now()`、分析器或查询计划，再进行二分。先测量，后修复。

## 阶段 5：修复与回归测试

根据反馈成本和缺陷风险选择方法。存在**正确的衔接处**、能可靠锁定缺陷时，在**修复之前**编写回归测试；没有合适自动化入口时，保留真实运行复现并沿同一路径修复和验证。测试先行的完整规则见 `dev-tdd`（测试驱动方法）。

正确的衔接处，是测试能够按照真实调用位置的方式触发**真实缺陷模式**。如果唯一可用入口太浅，例如问题需要多个调用者却只有单调用者测试，或单元测试无法复现触发问题的调用链，在这种位置建立回归测试会产生虚假信心。

**没有正确衔接处，本身就是发现。** 将其记下：代码架构阻碍了锁定缺陷，并为下一阶段标记这一问题。

存在正确衔接处并采用回归测试时：

1. 将最小复现转成该位置的失败测试。
2. 观察它失败。如果通过修改代码或夹具做对照实验，先与原始副本进行 `diff`，确认修改确实生效，再信任结果；不能用人为制造的其他故障冒充原问题。
3. 应用修复。
4. 观察测试通过。
5. 对原始、未经最小化的场景重新运行阶段 1 的反馈循环。

## 阶段 6：清理

声称完成前必须满足：

- [ ] 原始复现不再出现，重新运行阶段 1 的循环。
- [ ] 回归测试通过，或已经记录缺少合适衔接处。
- [ ] 删除所有 `[DEBUG-...]` 观测内容，搜索此前缀确认。
- [ ] 删除一次性原型，或移动到清楚标记的调试位置。
- [ ] 在提交或 PR 信息中说明最终证实的假设，让下一个调试者能够学习。
