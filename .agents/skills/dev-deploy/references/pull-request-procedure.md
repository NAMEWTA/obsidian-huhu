# 打开 PR

交付目标包含 PR 时调用。

**工作树。** 先查看当前分支、工作树和未提交修改。需要隔离时从明确基线创建独立工作树；共享分支由唯一写入者负责。无关工作完整保留，先记录与导出必要补丁再迁移。不要执行硬重置来整理用户工作。子智能体使用分配给自己的工作树和范围。

**提交。** 按可审查单元和已有授权保存提交。项目需要整理历史时，先确认当前分支所有权、共享状态和授权，再决定是否重排或变基；不因开 PR 自动改写已共享历史。每个提交尽量独立说明一个完整改动。仅本任务拥有且允许改写的提交可以 amend，否则新建修正提交。提交正文不重复主题。

**PR。** 用实际 diff 与项目已有检查整理本次差异；注释调整只按项目实际选择的策略，不默认删除注释。标题、描述与提交正文按`dev-writing`（技术写作）处理，除文档类型划分外，其余句子规范均适用；保持一个动作一个词、必要冠词和普通动词，再按`dev-writing`（清晰写作）复核。没有专用清理工具时直接审查差异，不虚构调用。

**标题。** 遵循项目已有格式；无约定时可采用 Conventional Commits 格式 `type(scope): subject`，结尾无句号。类型如 `feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`perf`。scope 是领域，如 `dev`、`workflow`。主题简短、祈使式，真实符号承载改动时写符号，例如 `fix(workflow): correct pull-request follow-up trigger`。

**描述。** PR 正文是给已经有差异的审查者的一分钟简报，不是实验笔记。说明为何改、排除什么、可能破坏什么、如何证明有效。用简短简单句，少标识符，不堆长墙。项目采用 squash 时，正文可能成为提交正文，可把约 40 行当精简目标，不为行数删掉必要风险或证据。用 `##` 标题而非加粗引导语，按下列顺序，没有内容的章节删除：

- `## Why`：问题与方法，1 至 3 句短句。不放 SHA、变基谱系或“基于 main”前言。
- `## What changed`：1 至 3 个短条目。只有真实符号或路径承载改动时才点名。重命名或改目标需写两端。
- `## Scope`：始终保留。1 至 3 条说明覆盖与刻意排除内容，如后续项、已知缺口。不写符号、路径或逐文件长文。
- `## Tradeoffs`：只写审查者否则会追问的未选方案。没有真实选择就省略。
- `## Blast Radius`：1 至 2 句说明触及谁或什么，以及为何安全或危险。main 为红时说明让它继续红的代价。
- `## Verification`：1 至 3 条，每条一个真实运行路径及结果。性能给一个带单位主数字、`before → after`，其余链接到 方案比选 或 并行验证 目录。不写样本方法、群体过程复述、指标表。

这些章节之后，视频或截图能够证明主张时附上。完整 SHA、群体或比选通道复述、工具校正长文、逐文件清单、`CLEAN` 裁决放链接产物，不放正文。

**托管工具。** 第一次 PR 操作前确认当前实际可用、已认证且能解析目标仓库的连接器或 CLI，后续尽量保持一致。已有 GitHub CLI 时可以使用 `gh pr`；项目明确使用另一工具时读取其真实帮助和语义，不因一个同名命令存在就推定它支持 PR。缺少权限或工具时先完成本地可审查结果。

**内置 PR 工具。** 宿主明确要求由其工具跟踪 PR 时按该集成方式执行；未覆盖功能使用已确认的托管工具。不要把其他宿主的限制推广到当前环境。无论工具类型，创建、改目标或标记就绪都必须在已授权范围内。

**大小与堆叠。** 拆分可独立审查的变更，不强制 PR 数量。存在真实依赖时才用基础分支链：根项指主干，子项以实际依赖的父项为基础并明确提交。父项合并后按[验证后落地](verified-landing.md)处理子项；改基础、变基和推送先核对所有权及授权。GitHub CLI 的典型形态是 `gh pr create --base <parent-branch>` 与 `gh pr edit <pr> --base <parent-branch>`，以当前帮助为准。独立工作从明确主干基线开始；基线变化是否需要更新取决于实际冲突和受影响检查，不无条件变基。

**就绪性。** 按用户要求和项目流程选择草稿或就绪。只有实际满足审查条件时才标就绪；工具默认行为不代表用户决定。创建后回读状态，若不符合已授权目标，使用内置工具或 `gh pr ready <number>` 等可用命令修正。未被要求 PR 时不自动把直接推送流程改成 PR。

**跟进。** 开 PR 本身不新增持续跟进授权。一般先完成阶段或堆叠，避免每开一个 PR 就阻塞等待、把检查花在随后会重启的提交上。原任务或委派已包含持续跟进时，负责人按既定职责执行，不要求用户等到整个堆叠完成后再次提出。反馈偏离意图时提出异议。

开 PR 的执行者完成本次差异与项目约定检查，回报地址后返回父级；已有委派要求包含持续跟进时，按[PR 跟进](babysit.md)执行，不再重复请求同一授权。负责人在代码就绪报告后开始循环，报告可合并；它不受此处及 babysit 中“整个堆叠构建完才跟进”的限制。


能力、授权和记录约定见 `dev-workflow`（本地执行支持）。
