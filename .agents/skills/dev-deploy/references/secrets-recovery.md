# 凭据、备份与恢复

## 账号与秘密分开存放

部署手册可以记录服务名称、账号用途、账号标识、权限范围和秘密所在位置。密码、API token、私钥、数据库 URL 中的认证部分以及带签名的下载 URL 都不写进普通 Markdown、提交、截图或日志。

优先使用项目已在用的 Secret Manager、CI secrets、系统钥匙串或用户指定的凭据系统。没有这类系统时，在用户允许的位置使用受限本地配置，例如项目已忽略的 `.env.local` 或受限部署目录下的环境文件。用实际文件权限/ACL 限定访问，检查 `.gitignore` 和 `git ls-files -- <文件>`；忽略规则不能移除已被跟踪的秘密。

对运行中的服务检查配置键是否存在、权限是否足够和连接是否成功，不输出秘密值来证明配置完成。导出诊断时先脱敏。用户要求保管账密时，记录真实保管位置与读取方式，不能只写一个不存在的 `secret://` 引用冒充保存成功。

## 计划恢复

为这一次变更定义恢复触发条件、可用旧版本、操作顺序、数据兼容性和成功检查。应用版本、数据库 schema、业务数据和外部副作用分别考虑；不能把删除新增表当成通用回滚。

备份至少记录实际位置、时间、对应版本和可读性/恢复检查。未演练完整恢复就如实写明，不能承诺“可完整恢复”。对跨主机或共享服务记录哪些操作已完成及仍受影响的消费者。

执行已在授权范围内的安全恢复；需要覆盖业务数据、撤销不可逆迁移或扩大目标时，先给出具体影响和已准备好的方案再请求缺失决定。运行出错时保留当前环境，不用反复重试掩盖未知状态。

## 发布记录与长期经验

发布记录保存当时发生的事实；当前 runbook 跟随环境变化更新。一次性错误留在 release evidence；会再次踩到的原因与修复条件才写入 `.agents/dev/notes/errors/`。不要把一次部署的临时状态写成永久规则。
