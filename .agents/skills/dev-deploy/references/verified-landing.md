# 验证后落地

仅在用户已经授权相应 PR 合并与必要分支操作时执行。验证结论先保存在项目本地；只有明确授权发布审查反馈时才写外部评论。

**你负责落地内容。逐个独立验证 PR，只落地从根部连续验证通过的部分，随后别碰堆叠。**

1. **确定托管工具，落地前逐个独立验证 PR。** 使用当前实际可用且已认证的托管工具，核对其合并、队列与改目标语义；不能从命令同名推定支持。每个 PR 按风险配置实际可用的独立验证，使用真实浏览器、终端或项目驱动按用户路径检查父项与头提交，记录 `PASS`、`PASS+NOTES`、`FAIL`。要求独立复核却没有相应能力时，记录缺口，不把作者自证冒称独立裁决。绿色 CI 和机器人批准都不是裁决，因为两者都没按用户方式运行改动。
2. **只落地从底部开始连续验证通过的部分。** 从最低未合并 PR 向上走，到第一个没有 `PASS` 或 `PASS+NOTES` 的停止。它下方就是本轮范围，最高项是上限。已验证 PR 若位于未验证项之上必须等，因为无法不带下方代码落地。某分支既不包含也不需要下方代码时，可以移到主干独立落地，但先要新裁决，因为旧裁决运行时下方有那些代码，主干却没有。
3. **再次检查裁决仍描述当前代码。** 裁决覆盖补丁，链式变基会让上方每个 PR 变成新 SHA，而不让任何检查失败。信任旧裁决前，在 Git 可用时比较裁决 SHA 与当前头的 `git patch-id`，并核对实际差异、基线、依赖和构建或运行证据；patch-id 只是辅助比较，不能单独证明行为等价。没有该命令时用实际补丁、文件与产物对照，无法证明等价就重跑受影响验证。补丁只在测试、文档、lint 配置上有差异时，如果通道运行的内容在两 SHA 构建相同、只差噪声，其结果可延续。噪声指裁决 SHA 自己两次构建也出现的差异，或嵌入的提交 SHA。报告每种噪声和文件，让读者能检查判断。变化本身仍需新检查和审查，因为旧裁决没看过。没有构建产物的通道，如开发服务器，无法证明这一点，应重跑；其他漂移也重新验证。
4. **自下而上，一次一个 PR。** 始终处理本轮最低未合并项，使用已确认的目标平台合并动作及项目选择的合并策略。GitHub CLI 已可用且项目采用 squash 时，命令示例为 `gh pr merge <pr> --squash`；其他平台必须先核对它是否会连带合并下方项，不能从命令名称推定语义。确认 PR 的实际目标是主干：目标仍为父分支时，合并可能只进入父分支。回读平台结果，例如可用的 `gh pr view <pr> --json state,mergedAt,baseRefName`；命令成功、进入合并队列或申请自动合并都不等于已合并。只有授权涵盖自动合并、裁决覆盖当前头且后续头变化仍受相应检查约束时，才启用平台实际支持的自动合并。父项确实合并后，核对原先依赖它的子项是否已经由平台改为主干；需要时在原授权内调整基础，并验证只包含预期补丁。确有必要更新历史时，按仓库策略和分支所有权选择操作；只有本任务独占、已有授权允许改写且绑定已知远端提交时，才使用 `--force-with-lease`。不覆盖共享或未知变更。第 3 步决定哪些裁决能够延续；受影响检查通过且裁决仍有效后再合并。
5. **落地期间别动堆叠。** 第 4 步必要的子项调整是本轮允许的分支或基础变更，因为合并会落地当时分支与基础上的内容，不论是否有旧裁决。使用实际 PR 工具、事件订阅或已确认可用的 `gh pr checks <pr> --watch` 观察；每次观察返回后重新读取当前 PR、必要检查和实际合并状态，直到本轮上限确已合并或遇到真实阻塞。没有观察器时直接进行有界状态检查，不等待专有状态协议，也不把当前会话回读称作后台监听。父项合并后的正常基础更新不是要修复的损坏。合并停滞时先找具体原因，再决定范围内的下一步；不因等待而无条件改写分支。
6. **到上限停止。** 扩展范围需要新裁决，因此要新一轮从第 1 步开始。

**回复：** 已验证范围与上限，每个 PR 裁决及给出者，落地内容和确认方式，以及下一缺口需要什么。


执行 PR 的创建与跟进分别见[PR 准备](pull-request-procedure.md)和[PR 跟进](babysit.md)。工具例子仅适用于已实际确认安装、认证和语义一致的环境；采用其他工具时保留同等检查，不尝试不存在的命令。
