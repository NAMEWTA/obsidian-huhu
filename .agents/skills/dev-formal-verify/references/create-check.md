# 创建形式化验证技能

测试检查人们想到编写的那些用例。形式化验证检查明确范围内的每一种情况：模型中每一种步骤顺序、边界以内的每一个输入，或全部输入。本技能找出仓库中最值得这样做的部分，验证它的一个属性，并留下包含真实命令、模型与证据的项目本地技能，让下一个智能体能够对照该属性检查改动。编写时应假定这个智能体在修改途中第一次读到它，从未看过你的工作。用户无需学习验证语言，也必须能够信任结果并据此行动。

## 从代码中选择目标

从代码库回答问题，只向用户询问无法观察的内容。如果用户指定了区域或缺陷，从那里开始。

好的目标是代码作出的某个承诺：一旦被破坏就会伤害用户，而普通测试很难覆盖到触发破坏的情形。选择仓库中最符合这一条件的目标，而非最容易验证的目标。

## 由问题决定工具

选择能以最低代价回答问题的工具：模型检查器、证明助手、基于 SMT 的验证器，或其他工具。事件能否以错误顺序发生，通常适合用模型检查器检查一个小型设计模型；对于任意语言，TLA+ 是这类问题的默认选择。代码本身是否对每个输入都表现正确，例如内存安全、溢出或数据结构不变量，通常适合直接对代码运行的验证器。如果没有验证器支持这门语言，就直说，并使用生成的输入测试真实代码，不要手工重写一个函数模型。必须对任意规模都成立、有限边界不够用的属性，可能需要证明。优先选择仓库开发者能够安装并运行的工具，并告诉用户为什么选择它。

## 优质验证的条件

- **忠于代码。** 模型或证明的每个部分都指向审查者能够打开的代码。验证中视为不可分割的一步，在代码中也必须是不可分割的一步。名称来自本仓库。
- **确实能够失败。** 从未见过失败的检查不能证明什么。针对被保护代码的故障变体，展示每个属性确实失败，例如移除检查或调换步骤顺序。
- **发现仍是发现。** 当前代码破坏属性时，用代码中的术语报告问题与反例。不要削弱属性或模型直到它通过，除非用户要求，否则不要修改产品代码。
- **诚实说明范围。** 说明验证了什么、使用哪些边界与假设、遗漏了什么。通过只覆盖模型或指定边界，不覆盖整个系统。
- **不懂工具也能读懂。** 分别用一句朴素的话说明属性及其被破坏的危害。用代码中的词，把反例讲成一段简短的步骤序列。
- **重新运行成本低。** 一条命令、可复现的工具版本，以及足够短的运行时间，让下一个智能体愿意在每次相关修改时使用它。
- **与代码同步。** 记录每个检查覆盖的文件和函数，以及上次确认验证确实描述这些代码时的提交。覆盖代码在该提交之后变更时，下一个智能体能看出验证需要再次检查。

## 生成验证技能

编写项目本地技能，在头部元数据中指出所覆盖的区域和使用时机。没有头部元数据，技能不会注册。仅凭这个技能，下一个智能体就必须能够判断某次改动是否触及被验证代码、运行检查、区分真实缺陷与建模错误，并在改动有意发生时更新验证。把覆盖记录和同步提交写进技能，并要求下一个智能体仅在确认验证仍描述新提交中的代码之后，才把同步提交向前更新。使用本仓库的真实命令、路径和名词，不留下占位内容。

如果检查使用 TLA+ 模型，按[本地 TLA+ 执行与反例阅读](tla-guide.md)解释每次结果。把实际模型、配置、代码映射和[运行脚本模板](../assets/run-tlc.mjs)复制进生成的项目验证包，填写真实路径。可以在安装了 `dev-statechart` 时使用其状态图辅助解释，但这个项目验证包必须在没有它时仍能运行 TLC 并读出反例；不要把兄弟技能路径写成必需依赖。

## 交付前证明它有效

像下一个智能体那样，遵循生成的技能运行一次，使用一份临时改动，在真实代码中破坏该属性。检查必须抓到这次破坏。然后撤掉临时改动，确认检查回到原先状态：通过，或只在你将报告的问题上失败。从未运行过的验证技能仍是草稿。如果技能漏掉破坏，或者某一步无法运行，修复技能或验证，不要修改临时故障来迎合它。

## 交付

告诉用户验证了什么、用了什么工具以及原因、边界是什么、检查用朴素语言发现了什么、如何运行，以及没有覆盖什么。只有发现了另一个价值接近的目标时，才建议第二个目标。未经重新检查的修改之后，按本包的[维护流程](maintain-check.md)使验证重新与代码一致。

## 本项目落地约定

项目已有验证包或目录时直接维护它。确需新建项目技能时，名称使用 `dev-verify-<area>` 并安装在 `.agents/skills/`；取实际业务领域名，避免空泛的 verify-everything。根据[技能模板](../assets/verify-skill.md)和[检查记录模板](../assets/check-record.md)填写真实内容，完成前移除所有占位项。每个被生成的技能带齐自身脚本与模型，不依赖本技能仍安装在同一机器。

提交只能标识已提交代码。存在未提交改动时，记录基准提交、工作区差异或被覆盖文件摘要，不能把 HEAD 当作全部当前代码的版本。没有 Git 时，以文件摘要和检查日期建立同步基线。

故障注入在隔离目录、临时工作树或可可靠恢复的受控副本中进行。先保存原有差异，验证结束后核对恢复结果；不要丢弃用户原有修改。用户已授权产品修复时，可把确认的缺陷交给相应修复任务，独立保留验证结论。
