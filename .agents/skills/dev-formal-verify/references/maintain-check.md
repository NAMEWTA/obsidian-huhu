# 维护形式化验证技能

形式化检查证明的是它所描述对象的某项属性。代码改变而验证未改变时，检查可能持续通过，却描述着已经不存在的代码。这种通过是危险情况，因为它看起来像证明。本技能是 [创建流程](create-check.md)生成的验证技能的维护循环，也适用于任何针对具名代码运行模型检查器、证明器或代码级验证器的项目本地技能。项目本地技能处理智能体使用该技能时所作的改动。本技能处理绕过它的改动：合并、未使用技能的编辑，以及跨越多个提交累积的漂移。

## 结果

为每项检查给出一个结果，并说明是哪一种：

- **同步（in sync）**：从上次同步以来，没有改动影响检查所描述的内容，检查通过。
- **已更新（updated）**：代码改变了，验证现在描述新代码，检查通过。
- **缺陷（bug）**：验证描述当前代码，而代码破坏了属性。这是代码发现，不是漂移。
- **阻塞（blocked）**：无法使检查重新一致，或无法运行。准确说明原因。

一项检查可以同时为“已更新”和“缺陷”：更新使验证重新描述代码，随后属性在该代码上失败。

## 编辑范围

只编辑验证相关内容：模型、验证框架、属性文件，以及验证技能本身。除非用户要求，运行期间绝不编辑产品代码。属性在当前代码上失败时，不要削弱属性或模型来让它通过。报告失败。

## 执行一轮

1. **找到检查。** 验证技能没有固定名称，因此按功能寻找：针对具名代码运行模型检查器、证明器或其他验证器的项目技能。阅读找到的每个技能，或用户指定的那个。对每项检查，收集属性、覆盖代码、边界与假设、运行命令，以及上次确认它描述代码时的提交。如果不存在验证技能，说明没有可维护对象；当前请求包含建立验证时直接进入[创建流程](create-check.md)，否则给出明确的创建入口。如果技能未记录同步提交，使用上次修改验证文件的提交，并说明采用了这个替代基线。

2. **先按原样运行。** 修改任何内容之前，把每项检查运行一次并记录结果。此时通过不代表代码正确，只表示旧描述仍然成立。此时失败可能是漂移，也可能是缺陷。到第 5 步之前不要下结论。

3. **阅读被覆盖代码的每项改动。** 对比同步提交与当前提交中覆盖文件的差异，阅读每条提交说明。也要寻找移动过的代码：被覆盖函数改名、拆分或移动到其他文件后，仍然是被覆盖代码。还要寻找触及受保护状态的新代码，例如写入相同字段的新函数。逐项判断改动属于以下哪一类：
   - **无影响。** 改动不改变验证所描述的任何内容，例如格式、注释或验证未覆盖的代码路径。对照模型或验证框架判断，而非只看提交说明。
   - **验证不再描述代码。** 原来不可分割的一步现在变成两步，分支增删，检查位置改变，新路径到达受保护状态，或某个值现在具有不同范围。模型或验证框架必须变化。
   - **承诺被有意改变。** 改动改变了代码的承诺，且改动中存在意图证据：文档注释、测试、变更日志或提交说明。属性必须变化，而且必须引用该证据。
   - **承诺可能被破坏。** 代码改变，没有证据说明承诺也改变。把随后出现的失败视为缺陷候选。

4. **根据代码更新，不根据结果更新。** 修改模型或验证框架，使每个变化部分重新指向审查者能够打开的代码，且保持代码中不可分割的一步对应验证中的一步。重新运行之前，先根据代码写出更新，不要按怎样让检查通过来塑造它。只对有意变化的承诺修改属性。记录旧表述、新表述及证据。保留边界，除非改动使原边界不再正确。如果必须缩小边界，在报告中说明。

5. **重新运行并判断每个结果。**
   - **通过：** 检查可能在一个失去失败能力的描述上通过。按属性所防护的方式破坏新代码，例如移除新增检查或调换新增步骤，确认检查能抓到它，然后撤掉故障。
   - **失败：** 在真实代码上逐步重放反例。如果某一步在代码中不可能发生，验证有误。修复验证并说明错在哪里。如果每一步都能发生，就是缺陷。指出引入它的提交，用代码自己的词汇讲述反例步骤，并用一句话说明危害。如果低成本测试或真实代码复现能够证明缺陷，把它作为证据加入报告，不要把它提交进产品代码。

6. **更新验证技能。** 更新每项检查覆盖的代码、命令、边界、假设和同步提交。把同步提交设为你检查过的提交。阻塞的检查不要推进同步提交，并在报告中说明。然后像下一个智能体那样再完整遵循一次验证技能，以确认其步骤仍然可运行。

## 报告

对每项检查告诉用户：

- 结果，以及阅读过的提交；
- 验证中改了什么、为什么，每项改动附简短原因：代码结构改变，或承诺有意改变（附证据）；
- 重新运行的结果，以及用来证明更新后的检查仍能失败的故障；
- 每个缺陷，用朴素语言给出代码术语的反例步骤、危害、引入它的提交；
- 验证仍未覆盖什么，包括应该覆盖但尚未覆盖的新代码。

直接说明哪些失败属于验证漂移，哪些属于代码缺陷。某项检查在更新前通过、更新后失败时，要说明旧通过建立在过时描述之上。

把验证更新放在独立改动中，与产品修复分开。

## 工作区与维护证据

同步记录必须覆盖本次实际检查的代码：提交、未提交差异或文件摘要。除提交范围外，也读取本次未提交且触及覆盖区域的变动，以及新增写入同一状态的路径。仅有 Git 提交号而工作区有变时，不得声称模型已与全部当前代码同步。

正式报告使用[检查记录](../assets/check-record.md)，逐项保留“同步 / 已更新 / 缺陷 / 阻塞”及组合结果。达到状态、时间或内存边界的检查标为未完成；不能推进该项同步基线，也不能把它当作通过。

按[工具选择与边界](tool-choice.md)补充代码级证据。TLA+ 检查遵循[执行与反例阅读](tla-guide.md)。独立审查适合高风险变动，但不为普通维护增加固定审批或强制工作流状态。
