# 需求澄清

把模糊想法变成双方一致的行为契约。使用**决策树与问题前沿**：先解决前置决策，再展开依赖它的下一轮问题。

澄清后的行为与边界指导后续开发；按任务选择规格驱动、TDD 或原型验证，复用已经解决的产品决定。

## 建立已有共识

读取用户请求、已给出的文档，以及指定 issue / PR 的正文、讨论和相关代码。先列出已经明确的目标、约束、授权和不做的内容。已回答的问题不再问；已授权的执行不再设置确认仪式。

区分三件事：

- **事实**：系统现在如何工作、某接口是否存在、某方案能否运行。通过代码、配置、运行结果或一手文档查证。
- **决策**：谁使用、哪种体验更合适、可接受什么代价。结合用户偏好给出推荐，必要时请用户决定。
- **假设**：暂时缺少证据。标明依据和影响；不要把它写成用户已经确认的要求。

有实际含糊点才进入提问。需求已经足够清楚时，直接整理共识并进入下一步。

## 按决策树展开

把问题组织为依赖关系。例如“谁能分享项目”依赖“项目的拥有者与协作者是什么关系”；不要在后一项未定时假定前一项的答案。

**问题前沿**是前置条件已经明确、现在就能回答的决策集合。每轮提出当前前沿的问题，编号，说明为什么影响方案，并给出推荐答案与代价。让“是”能明确接受推荐；涉及多项选择时把含义写清楚。

每轮用户的回答都会改变决策树。更新共识，重新计算前沿。依赖本轮其他答案的问题留到下一轮。

事实调查可以并行进行。一个调查未结束，只阻塞依赖它的问题；其他问题照常推进。不要要求用户手动提供自己可以查到的文件、行为或配置。

## 追问有价值的分支

围绕当前需求选择适用的方向：

- 谁触发、解决什么问题、完成后用户能观察到什么。
- 正常路径、失败路径、取消与重试、权限边界。
- 数据属于谁，什么需要持久化，哪些已有数据必须保留。
- 本次交付范围、明确不做的功能、上线环境与成功标准。
- 如果涉及 UI，关键场景、现有设计系统、参考图中要保留的具体特征。

术语含糊时给出具体场景。例如“用户账户”和“账号”是否同一概念，还是登录身份与计费账户不同。查证代码后，把新增的已确认映射写入 `.agents/dev/notes/glossary.md`；已有词汇表先按真实位置核对引用，避免创建重复条目。保留领域限定，避免不同模块里同名词被错误合并。

范围过大时只展开当前能定义的问题。把尚不能精确定义的部分记为“待澄清”，与“明确不做”分开；不要预先编造完整任务树。阅读 [澄清记录示例](references/clarification.md) 处理这类需求。

## 记录与交接

先查阅已有需求文档并保留引用；新增目标、来源、共识、待决问题和关键理由统一写入 `.agents/dev/changes/<YYYY-MM-DD-slug>/brief.md`；小需求可在该目录已有记录中补一节。相同决策只存一处，其他位置引用它。

当所有影响实现的产品决策已经明确，且不存在被隐藏的假设时，给出一份简短的共识。用户仅要求讨论时停在讨论结果；用户已经要求实施时，在既有授权内继续。仍有不可代决的问题时，指出它具体阻塞哪部分。

输出应让接手者知道：要实现什么、为何这样取舍、哪里仍不确定、去哪里查证。澄清完成且目标包含实施时交给 `dev-spec`，不重复访谈。

## 本地完整方法

| 当前需要 | 本包材料 |
| --- | --- |
| 深入访谈的轮次、前沿、问答格式和结束条件 | [决策访谈全文](references/decision-interview.md)；单纯访谈可用[直接入口](references/interview-entry.md) |
| 术语冲突、领域关系和代码对照 | `dev-architecture`（领域建模） |
| 保存用户别名与规范概念 | `dev-archive`（词汇表格式） |
| 保存真正重要的设计取舍 | `dev-archive`（决定记录格式） |
| 纸面讨论无法决定，先做可运行证据 | `dev-build`（原型方法） |
| 检查业务逻辑、状态或数据形状 | `dev-build`（逻辑原型完整流程） |
| 比较布局、信息层级和交互入口 | `dev-build`（界面原型完整流程） |
| 决定依赖未知技术事实 | `dev-plan`（研究方法） |

这些资源按需读取。原型回答问题后更新同一份共识；研究只解除所依赖的问题，不阻塞其他已明确工作。
