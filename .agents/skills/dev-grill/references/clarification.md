# 澄清记录与大需求展开

下面是写法示例，具体产品与代码位置必须重新查证。记录可以直接合并到现有 `brief.md`，不强制额外文件。

## 记录骨架

```markdown
# <需求名称>

## 来源与目标
- 来源：<用户指令、issue 或文档链接及时间>
- 要解决的问题：<谁在什么场景遇到什么阻碍>
- 本次完成表现：<用户能观察到的结果>

## 已确认
- <决策>：<关键理由；原始来源>
- <授权或交付边界>

## 术语
- <用户说法> → <项目规范词>；适用领域 <领域>；代码定位 <路径 / 符号>

## 当前问题前沿
1. <问题>；推荐 <选项>；影响 <具体差异>
2. <与问题 1 无依赖的问题>

## 待前置决定后再问
- <依赖哪个决定，为什么现在不能确定>

## 明确不做
- <范围边界>

## 待查证事实
- <事实>；查证入口 <代码、命令或资料>；阻塞 <哪个决定>
```

## 一轮提问

“分享项目”可能涉及组织所有权、访客权限、审计和计费。先查已有身份与项目模型。

若组织所有权尚未确定，第一轮可以问“组织还是个人拥有项目”，并问一个与其无关的品牌呈现偏好。访客能否继承组织角色留到下一轮；不要把依赖关系伪装成一次几十题的问卷。

每个问题给出推荐及代价：

> Q1：项目是否由组织拥有？推荐是，成员变动时项目仍由组织保留；个人草稿可继续归个人。这个决定会影响邀请与退出后的数据归属。

用户已经说“所有内容只保存在本地 vault”时，把它作为既定约束，而非再问是否采用云存储。

## 大需求的可见范围

只记录三种不同的信息：

- **能明确表达的问题**：即使暂时不能回答，也可以写出依赖和调查目标。
- **还无法精确定义的部分**：保留一个区域提示，等前置证据出现再展开。
- **明确不做的内容**：不自动变成下一轮待办。

例如已明确“需要离线编辑”，但尚不清楚是否多设备合并。可以先精确定义“是否需要合并并发修改”这一决策；不要在它没确定前排出完整冲突解决算法工单。

## 结束条件

接手者能从记录明确读出目标、关键场景、数据归属、范围、验收方式和仍未决定的事情。无需把所有未来问题问完，只需消除本次实现会依赖的未说明假设。
