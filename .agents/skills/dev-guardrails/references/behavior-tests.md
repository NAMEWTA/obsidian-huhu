# 测试行为，不测试实现

适用：编写、修改或保留测试时使用。断言代码使用者能观察到的内容，使测试在行为损坏时失败、仅内部结构变化时继续通过。

测试是关于代码为使用者做了什么的一项主张：使用者可以是调用者、最终用户或另一个服务。行为是这些使用者通过其使用的接口能够观察到的内容，包括返回值、错误、能够读回的状态，以及对代码外部系统产生的效果，例如发送请求、写入一行数据或发出消息。实现是他们无法观察的内容：私有辅助函数、内部调用顺序、中间数据，以及究竟由哪个内部协作者完成工作。

用两种假想编辑判断每个测试：

- **破坏行为。** 让代码返回错误值、跳过一个效果，或将该效果执行两次。如果测试仍通过，它什么也没证明。常见原因是断言弱于契约、期望值由被测代码计算、只复述一个常量或提示词字符串却从不运行读取它的代码，以及对测试自己构造的数据进行断言。
- **改变内部实现。** 保持所有可观察结果不变，重组下面的代码。如果测试此时失败，它绑定的是实现。每次重构都需要重写它，却仍然没有捕获任何缺陷。

保留能捕获第一种编辑、又能经受第二种编辑的测试。重写或删除其余测试。要同时做到这两点，通过使用者的接口，用一个具体输入驱动代码。根据需求推导期望值，而不是根据代码的一次运行。只断言契约承诺的内容，既不少也不多。

决定标准的是契约，不是断言的形状。如果承诺是“空购物车绝不扣款”，那么断言没有调用支付客户端属于行为。搭配一个确实扣款的场景，让测试表明它能看到调用。被模拟的外部服务收到的载荷属于行为，因为那个服务会观察它。内部辅助函数的调用属于实现，因为任何使用者都看不到。没有记录匹配时，空列表就是精确答案；测试只需要任意结果时，它又可能是空洞的检查。精确错误消息会锁定调用者不读取的措辞；调用者用来分支的错误类型才是契约。

测试也可以约束不变量，而不约束调用，例如某个键必须同时存在于两张表中，或一个编译期类型检查。此时不变量就是行为。
