# 边界纪律

适用：接入验证、错误处理或框架适配器时使用。把保护措施集中在系统边界（CLI、配置、网络、外部 API），信任内部类型，并把业务逻辑保留在纯函数中。

把验证、类型收窄和错误处理放在系统边界。内部沿用已建立的类型与不变量；插件、并发参与者、持久化旧数据或其他信任域输入仍按真实边界处理。业务逻辑位于纯函数中。外壳保持轻薄、机械。

**原因：** 散落各处的验证嘈杂、重复，并制造虚假的安全感。让逻辑远离框架接线，才能在没有框架的情况下测试它。

**模式：**

- **在边界处**（CLI 参数、配置文件、外部 API、网络协议）：验证、返回错误、防御性处理。
- **在系统内部：** 使用有类型的数据、传播错误、不重复验证。信任类型。
- **跨越边界时：** 暴露领域概念，而非边界私有的表示。通用机制留在内部，专门策略放在边缘。

**应用：**

验证与错误处理：

- 在解析配置时，也就是边界处验证配置，不在业务逻辑内部验证。
- 在边界把原始数据解析成领域类型。
- 不通过公开接口重新导出传输、存储、框架或线上协议的类型。
- 如果边界已经验证，不在调用链深处重复检查 nil。

代码组织：

- 业务逻辑位于不依赖框架的纯函数中。
- 解析函数：从原始字节到有类型状态的纯转换。
- 提示词构造：输入结构化状态，输出字符串。
- 评分与评估：从状态到结果的纯转换。

**判断问题：**

- “这份数据此刻正在跨越系统边界吗？”若没有新增信任边界、不变量失效风险或并发变化，再加同一验证通常是重复的。
- “这能成为一个由外壳直接调用的纯函数吗？”如果可以，就提取出来。
