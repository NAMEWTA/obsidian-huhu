# 可选的注释与抑制审查

用户要求、项目明确采用，或本次差异出现具体冗余和错误注释时，执行这项审查。目的在于让代码与必要说明共同表达真实约束，不默认禁止所有注释。先确认当前请求是只读审查还是允许修改。

## 范围

使用调用者指定的文件或差异。没有明确范围时，检查当前任务改动及工作区，先核实真实基础分支，不默认它一定叫 `main`。不得借清理注释顺带重构无关代码。

## 步骤

1. **取得新视角。** 有可用代理能力时，把实际范围与[审查任务书](comment-reviewer.md)交给独立只读审查者，默认继承当前模型；没有时顺序执行并说明独立性限制，不假造代理类型或工具名。
2. **核对报告与差异。** 拒绝越界、擅改应用代码、误删受保护说明、错误的结构问题归因和把有意保留的行为判错。逐条复核 lint 与 TypeScript 抑制，查实际规则和触发代码；保护正确性或安全的规则被抑制时，调查真正原因。对于 `IMPORTANT`、`do not remove` 等，先追踪符号和调用，再查提交、讨论或已有决定。无法确认的约束保持原样并报告，不以“不理解”为删除证据。报告不合格时指出失败原因，允许一次聚焦重审；仍不合格就报告未解决，不循环到得到想要的结论。
3. **处理已证实的简单问题。** 删除重复描述、失效说明或注释掉的死代码；只有授权允许时，才修复对应死路径、多余参数或错误 API。需要结构设计时先比较最小可行形状，可按[重新设计](redesign.md)思考，保留选择与范围，再进入实现。
4. **修复真正原因。** 按[根因方法](root-causes.md)处理范围内问题。无法改变的外部机制、必要兼容行为和真实错误处理不能因为看起来像绕路就删。根因在范围外时，只做有证据且安全的范围内修复，其余报告；不要用症状防护掩盖问题，也不假称全部解决。
5. **评估约束编码。** 对“不能删除”“不能改措辞”“修改前需某方决定”等说明，判断最低成本的类型、运行时、测试或 CI 检查能否真正保证它。已有授权足够就实施并验证；新增成本、方向或外部行为不在授权内时，先给具体方案再补问缺失决定。无法编码、尚未获准或尚未证明时，保留必要说明并标明约束仍靠何种机制维持。不能先删除再把约束留空。
6. **交付。** 说明审查范围、删除或修正数量、保留与恢复原因、重审情况、结构草图、代码修复、编码建议、已落实约束及未完成项。只读任务不产生编辑。修改后重新读差异，并运行与实际变更相称的检查。

严格清理模式可以减少叙述性注释；法律许可、公共 API 契约、不可由代码表达的理由和真实外部限制仍保留。方法选择不取代用户与项目现有规则。
