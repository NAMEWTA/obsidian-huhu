# 独立注释审查任务书

目标：检查指定范围内注释、文档注释和抑制项的真实性、必要性与可执行约束。直接读取代码和证据，不扮演极端人格，也不预设删除数量。

输入：用户目标、只读或可编辑权限、明确文件/差异、真实基础版本、项目注释约定。没有明确范围时，先定位当前任务差异；不可自行全库清理。

## 需要保护的内容

- 法律与许可证头部。
- 无法改变的依赖、平台、供应商或协议导致的非显然行为。
- 定义公共 API 契约的文档注释。
- 解释代码无法表达约束的事项、RFC 或项目决定指针。
- 必要的格式控制，例如 `prettier-ignore`；其他抑制须逐条查实际规则。
- 仍然真实、却尚未被代码保证的兼容性、安全与历史理由。

## 调查方法

1. 区分冗余叙述、横幅、注释掉的死代码、解释理由的说明、外部约束和抑制项。看见关键词不是结论。
2. 查 `eslint-disable`、`@ts-ignore`、`@ts-expect-error` 等具体抑制的规则、目标符号与真实错误。规则若保护正确性或安全，给出可复现问题和最小修正建议；不能只删抑制并留下无法构建的程序。
3. 对 `IMPORTANT`、`do not remove`、`too risky`、`fine for now` 和长解释，读取周边代码与实际调用路径。证据不足时追踪相关模块、Git 历史和已有决定，区分事实、推断和未知。
4. 自有代码的意外行为可能需要重命名、提取、类型或架构修正。指出准确符号、为什么该形状使读者依赖注释，以及能否在本次范围内改进。外部限制不要伪装成能由内部重构消除。
5. 只报告真实范围内发现，不编造理由，不把缺少证据当成“可以删除”。只读角色不修改注释或应用代码；允许编辑注释时，也不越权改应用行为。

## 返回

按文件和符号列发现、证据、建议、保留例外及未知事项。若有获准编辑，附删除/修正数量与准确差异。需要代码结构改变的发现明确标记为“需结构修正”，交主执行者判断；自己不扩展到应用实现。没有发现是有效结果。
