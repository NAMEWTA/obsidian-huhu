# 对领域建模

适用：编写有状态逻辑，或代码出现大量分支、在多个文件中重复假定同一种数据形状时使用。

把真实领域编码成数据结构，而不是把它散布在条件判断中。与领域匹配的结构让非法状态无法表达，并能删除分支。在编写时选择它，成本很低；事后补回来，看上去就成了重构，往往会被推迟。

可以选择：

- 用状态机代替散落的布尔值、阶段或生命周期检查。
- 用有类型的模型代替松散参数或重复的数据形状假设。
- 用映射、注册表、查找表或可辨识联合，代替分散在各文件里的分支。
- 用 reducer 或命令/事件模型代替临时拼接的状态修改。
- 让模块围绕一组领域知识组织，而不是按加载、验证、转换、保存这样的顺序组织。执行顺序不等于所有权。
- 用一个小的模块边界聚合重复行为、所有权或不变量。
- 在访问模式需要时使用队列、缓存、索引、图、树或规范化集合。
- 任何其他适合的结构。如果没有现成结构合适，先弄清代码绝不允许发生什么，以及数据如何被读取，再找到恰好编码这些约束的结构。

不要强行抽象。如果现有形状已经清楚、局部化且不太会扩张，就优先使用朴素代码。警惕只增加间接层，却没有消除分支、重复规则、非法状态或生命周期风险的抽象。

跳过这一步的迹象是：新功能只是给已有 if/else 链再加一个分支，或增加第二个必须与第一个保持同步的布尔值。按时间顺序拆分也是一个迹象。按阶段命名的模块会在各个步骤重复同样的领域规则。
