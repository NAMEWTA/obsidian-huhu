# 质疑前提

适用：两个或更多共享同一前提的修复，都未通过同一个门禁时使用。写下前提，直接检验，再编写依赖该前提的下一次修复。

两个或更多共享同一前提的修复都未通过同一门禁时，怀疑前提，而不只是怀疑修复。

**原因：** 每次失败修复都是反驳其所依赖信念的证据。在同一前提下尝试第三次修复，是把精力花在证据已经指明并非原因的地方。

**模式：**
- **写下前提。** 前提是每次失败修复都默认成立的那一句话。
- **下一次修复前检验前提。** 找到一个在前提错误时会出现不同结果的观察，并实际执行。观察失败的分布，不只看失败幅度。按[构建执行工具](repeatable-tools.md)使检查可以重跑。
- **跟随证据。** 证据反驳前提时，原因在别处。寻找这些失败共有、而前提没有预测到的特征。证据确认前提时，按[修复根因](root-causes.md)继续问下一个“为什么”。先前修复可能只处理了后果，而非原因。
- **消除条件，而不是补偿它，** 遵循[懒惰协议](minimal-change.md)。证据表明某部分总落在不利一侧时，改变造成这一处境的东西。事后清理机制会留下原因，并给每次运行增加工作。

**停止条件：** 写下并检验前提之前，不开始下一次修复。

本原则不同于[从第一性原理重新设计](redesign.md)，后者围绕新需求重建设计；这里质疑的是当前设计假定成立的事实。
