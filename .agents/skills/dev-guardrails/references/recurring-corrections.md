# 把重复纠正转成可靠约束

当同类错误在项目里反复出现，先找出为什么局部看似正确的改动会破坏整体，再选择有效、成本相称的结构修正。不要把一次纠正自动变成一条永久规则或 lint。

智能体可能只读取少数文件、复制近处示例、选择能编译的最短路径。用这个风险模型检查仓库，让常见正确路径清楚，错误路径尽量难以产生；不要据此假定每位贡献者都缺少判断。

## 找出错误类别

读取任务相关的近期提交、回滚、审查评论、指令与绕路注释，按机制分型。用真实独立事件判断重复；同一事故的多份报告只算一次。发生两次是可用识别信号，不要求等待高风险错误重演，也不因每次用户纠正都扩大清理范围。

每类写明症状、触发条件、证据与影响，区分规则缺失、规则不可见、机制无法执行，以及原规则本身错误。确认最新用户目标，不能用历史约束否定新需求。

## 在最高有效层处理

1. **架构消除。** 每份状态有明确所有者，常见任务有清楚的受支持路径。隐藏内部，阻止错误导入；用单一事实来源代替手工同步列表；移除会被复制的死代码与旧路。外部兼容或多种真实使用方式仍有必要时，不强行压成一条路径。
2. **类型或机械检查。** 能使错误状态无法表达时用类型。仍可编译、规则稳定且可机械判断时，再评估 lint、CI 或运行时检查，错误信息指出该用的文件、类型或函数。先复用已有机制，证明误报和维护成本可接受，不为每个 bug 新增 lint。历史债务普遍存在时，可先限制新增实例，但明确覆盖范围与退出计划。
3. **行为验证。** 按[行为验证](behavior-tests.md)检查测试是否会在真实行为损坏时失败、仅内部重组时仍通过。修正弱断言和自证测试；不能为了绿色而删除仍保护契约的检查。
4. **判断性说明。** 不能可靠编码的取舍，保留简短理由、失败例子与源码入口。文字不提供自动执行保证，但仍可保存必要业务背景；不要把“最后写文档”误读为不记理由。

## 修复并证明

按频率、影响和本次范围选择最值得处理的类别，不自动全库重构。每类形成可审查的小变更，提交按已有授权与项目流程进行。

新增检查应能捕获真实历史错误或代表同类机制的最小复现，同时通过合法场景。用隔离片段或工作区检验，不污染生产数据或共享分支。本地与 CI 尽量使用同一命令；平台不同就说明等价条件。没有运行条件时标明尚未证明，不伪称规则已有效。

例外放在最接近的受影响位置，说明理由和重新核对条件；确有时效时写到期时间。只有项目要求或当前授权缺失时才新增审批，不为每条例外重复请求已有许可。

## 维护最小规则索引

规则较多且需要导航时，在 `.agents/dev/notes/context/` 记录“规则 → 执行机制 → 证据”，按真实位置引用已有指南或模块文档。根 `AGENTS.md` 只保留高频约束和入口，不强制把整张表塞进去。已有规则反复被违反时，先判断机制为何失效，再按有效层处理。

结构已使某类错误不可能发生时，可以删除重复操作指令；仍有价值的理由、兼容边界和例外要保留。一次纠正完成后，只更新亲自核对的范围，不批量刷新全库知识。

## 交付

逐类说明证据、选用层级、更高层为何不适合、实际修正、检查辨别力及未覆盖范围。没有值得新增机制时，说明局部修复为何已经足够，不制造规则数量。
