# 构建执行工具

适用：用于任何非平凡工作，不只批量工作，包括编辑、迁移、分析与检查。构建完成或证明工作的工具，如代码迁移脚本、脚本、生成器或供子智能体遵循的技能，而不是手工处理。工具是审查者可以重跑的产物。

工作并非微不足道时，构建完成它的工具，而不是手工完成。

代码迁移工具、生成器或脚本，每次都以相同方式完成工作，可以轻松重跑。工具是一份审查者可以阅读并重跑的产物。手工变更只能靠重新做一遍来再次验证。确定性脚本把“相信我”变成“运行这个”。

先复用已有可靠命令。需要重复处理或可重跑证据时，构建最小工具；一眼能看清的小改动不为形式增加脚本，昂贵自动化也不能替代必要判断。

- 先手工完成第一个单元，掌握操作方法，再构建工具。在该单元重跑工具，与手工版本比较差异，证明其正确。让工具可安全重跑。
- 编辑用代码迁移工具或脚本；重复文件用生成器；分析用导出到 SQLite 的查询；验证用可重跑检查。
- 确定性工具优于扇出。工具能一遍处理所有单元时，自己运行，不派多个执行者手工重复脚本能做的事。
- 将工作分给子智能体时，把操作方法写成大家都阅读的技能：方法、验证契约与不可触碰边界，集中在一份产物里。放在执行者可写范围之外，避免它们悄悄修改契约。
- 应用本原则会产出文件。声称应用了它，差异里却没有代码迁移工具、脚本、生成器或委派技能，就没有实际应用。
- 工具需长期复用时，按项目流程和已有授权保存或提交；一次性证据保存在适当临时位置。

门槛是工作是否微小，不是是否重复。一次性工作也值得工具化，尤其工具能让工作可检查时。按[懒惰协议](minimal-change.md)，构建完成或证明任务的最小脚本，不构建框架。

它不同于[把经验编码进结构](structural-learning.md)，后者把重复指令变成持久约束。本原则关注眼前工作的吞吐与可审查性。验证自身的脚本化见[证明它确实有效](real-evidence.md)。
