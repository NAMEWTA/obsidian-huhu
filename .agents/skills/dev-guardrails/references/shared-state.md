# 共享状态先隔离再串行

适用：并发执行者可能写同一个文件、分支、键或状态对象时使用。先消除共享；只有单个共享写入者是真实不变量时，才从结构上串行化。

并发执行者可能共享可变状态时，先问它们是否需要同一个可变对象。如果不需要，就消除共享。确实需要共享时，从结构上保证串行：锁文件、顺序阶段、独占所有权。文字指令和约定不是并发控制。

**原因：** 对共享状态并发写入会产生竞态，间歇出现、难以复现，调试昂贵。

**模式：**
1. **识别共享可变状态**，例如双方都读写的文件、双方都推送的分支、双方都定义和消费的 API。
2. **默认消除共享写入目标。** 问：这些执行者需要同一个规范对象，还是在发布各自独立的事实？给每个执行者自己的文件、键、分支或状态目录，只在读取或报告边界合并。两个执行者分别向同一个 `state.json` 写自己的 `lastX` 字段，仍然是共享修改。`indexer-state.json` 加 `metrics-state.json` 才不是。
3. **只有同一个共享写入目标是真实不变量时，才从结构上串行访问，** 例如锁文件、顺序阶段、单写入者执行模型或原子比较交换。把“我们需要一把锁”看作需要审查的设计信号，不当作默认答案。
