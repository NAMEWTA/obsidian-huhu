# 把经验编码进结构

适用：当你发现自己第二次编写相同指令，或注意到重复出现的纠正时使用。规则明确、可机械判断且反复有用时，考虑编码为 lint、元数据标志、运行时检查或脚本；先衡量误报、维护成本和已有机制，不要求每个缺陷新增 lint。

如果经验需要判断，无法编码，就让指令更加醒目，并补充一个失败模式的例子。

**推论：** 如果修复是结构性的，就只采用结构性修复。避免再维护一份内容重复、容易漂移的指令；需要解释的理由与无法编码的约束仍应保留。

已经反复发生的错误，按[分型、修复与证明](recurring-corrections.md)寻找最高有效层，并用真实历史错误核验新机制的辨别力；不要直接从“用户纠正过”跳到新增 lint。
