# 让工程方法适合当前用户与项目

工作风格与开发方法可以分开维护。完整实施、分流和角色分工不要求所有用户采用相同偏好。本指南以个人模式的提炼、修订与评测为主，保留相关完整方法，说明哪些结果需要交给项目知识、工程约束或实施任务。

从小处开始。最初不需要很多技能：清楚提出目标，观察实际失败。同一种失败反复出现时再判断是否需要规则或检查；高风险缺陷不必等第二次事故才修复。

## 生成个人工作方式

可以直接提出：

```text
根据我提供的本项目记录，整理一份个人工程方式技能。
```

`dev-personalize`（偏好提炼方法） 在用户授权的近期记录中寻找回复、委派、验证、代码、文字和交付偏好，再核对哪些是用户真实意图。它按照 `dev-personalize`（技能结构规则） 写入指定源仓库，使用 `dev-writing`（清晰写作规范） 收紧文字，以用户已授权方式交付可审查修改。

习惯变化后可以更新：

```text
只用上次有效编辑之后的授权记录更新我的工程方式，保留没有被新要求否定的部分。
```

更新只分析新的证据，不重新复制全部历史。已有规则未经新要求否定就保留；新证据修订原规则，真正新模式才增加章节。 需要核对规则与原始材料时，使用`dev-personalize`（偏好证据模板）。

## 从会话中提炼经验

维护个人方式时，可以从有教训的任务检查哪些判断需要调整：

```text
这次处理太慢了。根据本次任务记录找出可复用的改进，让下一次避免同样的问题。
```

`dev-archive`（会话反思方法） 从判断、工具和遗漏三个视角阅读允许范围内的记录，再综合为接受、拒绝与待办。支持并行时可以独立审查；不支持时顺序完成，不固定模型。只有会改变未来决定的建议才保留。一次异常经历是线索，不能自动成为所有项目的规则。

仅要求分析时先交付改动建议；用户已经明确要求更新个人技能时完成其范围内的修改，不再逐条索要重复批准。项目背景和错误经验以 `dev-archive` 为主，结构性机制更适合处理的内容转入相应工程改动，不全部塞进提示词。

## 把反复错误转成约束

需要一再纠正同种工程错误时，先判断项目中的产生机制；这类结构改动以 `dev-guardrails` 为主。需要时调用该技能继续已授权工作，个人偏好记录引用结果。可按以下顺序考虑：

1. 用架构或数据结构消除错误路径。
2. 用类型、已有 lint 或 CI 检查阻止它，错误信息说明正确替代。
3. 用真实行为测试捕获它。
4. 对无法可靠机械约束的取舍，写简明理由、失败例子和代码入口。

持续依靠人工审查重复抓同类错误，说明约束仍可改进；不能把审查次数当修复机制。`dev-guardrails`（重复纠正方法） 可以处理例如：

```text
这个项目反复出现直接调用数据库客户端、绕过仓储边界的改动。找出证据并修正真正的产生原因。
```

它读取本次授权范围的提交、回退、审查和绕路注释，按机制分型。同一事故的多份报告不重复计数。按频率、影响和当前范围选择值得处理的类别，在最高有效层形成小型改动，并证明新约束能捕获真实历史错误或同类最小复现。

必要时维护“规则、执行机制、证据”的小索引，根项目指令保留导航。不是每个 bug 都新增 lint；已有规则为何失效也要调查。交付逐类说明证据、所选层级，以及更高层为何不适合。

反思改进工作方法；重复纠正改变项目，使错误更难复发。边界问题需要结合当前架构调查。跨多模块计划先收集真实数据并做小原型，在当前授权内研究，不因任务范围大就扫描无关项目或个人历史。

## 编写个人模式与交接专用技能

个人模式按下方技能编写方法维护。通用工作流技能由 `dev-workflow` 的技能维护流程负责；有专用验证目标时按对象交给 `dev-verify` 或 `dev-formal-verify`，例如：

```text
为这个仓库编写一份验证数据库迁移的技能。
```

`dev-personalize`（技能编写方法） 和 `dev-personalize`（结构规则） 负责触发描述、最小入口、完整本地参考、元数据与引用闭包。面向未来智能体的每句话都可能影响行动，因此删掉不改变决策的文字；不要把格式合格误称为行为已验证。

两类技能有更具体的证明要求。驱动真实应用的技能按 `dev-verify`（创建验证技能） 编写，并用 `dev-verify`（维护验证技能） 保持功能图与应用一致。检查代码属性的技能按 `dev-setup`（形式化验证适配） 明确属性、假设、代码映射及真实验证器。两者都不能只写文档就宣布可用。

## 写清个人方式及相关文档

个人方式、维护说明与提交消息同样需要清楚的标准；仅要求审查其他技术文档时以 `dev-writing` 为主，例如：

```text
按工程文档标准审查这次 README 修改。
```

`dev-writing`（完整技术写作规范） 先区分教程、操作指南、参考和解释，再逐句检查谁做什么、是否一个想法、是否存在歧义。目标是让疲惫的工程师首次阅读也能理解。可以审查刚写好的文字，也可以在开始写作时直接采用。

## 独立比较技能变更

技能变化会影响后续任务。采用新技能或修改已有行为时，应依据具体风险检查它是否改善真实工作，而不只根据一次表现喜好决定。

```text
用相同自然任务比较这个技能修改前后版本，让两个执行上下文独立完成，再按相同标准比较结果。
```

已知道持续遗漏的行为，也可以把修改与验证放在同一任务：

```text
修正审查技能，使其能识别缺失数据库迁移的改动，并用有代表性的任务验证。
```

预先确定成功行为可以减少对单次失败过拟合。连续修改容易让技能漂移；有代表性的独立验证应在交付前发现它。

`dev-review`（评测方法） 控制观察者效应：执行者收到自然任务，不获知另一个变体或评分提示；在隔离目录中完成。同一评判上下文按中性标签和同一标准阅读输出。流程遵循从真实读取和产物判断，不信执行者自称；只有授权记录可读时才查看它们，不为评测扫描私人历史。

接受评判前亲自阅读每份输出。分歧先检查评分标准、证据和偏见，不自动认为自己的判断错误。没有并发能力时顺序完成独立上下文；没有独立工具时说明限制，不伪造盲测。

## 需要操作界面时交给实施任务

用户明确要求浏览队列并发起真实动作时，这是 `dev-build` 负责的实现任务。该阶段按`dev-build`（完整操作界面方法）完成已授权的后续工作：创建小页面，由服务器把允许的动作发送到真实 webhook，比如浏览一项审查记录后请求处理该事项。发送密钥只在服务器，不进入聊天或浏览器。私网访问按实际节点、授权和访问控制配置，不默认公开网络端口。

不要在普通功能工作中悄悄改动通用技能。用户已要求同时修复时，把技能改动与产品改动说明清楚，保持可独立审查；未授权时记录具体建议并继续原任务。提交或 PR 如何拆分沿用本项目要求，不把“单独 PR”变成所有场景的固定门禁。
