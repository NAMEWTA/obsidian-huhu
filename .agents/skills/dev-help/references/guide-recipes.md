# 常用做法与常见问题

先给出值得复制的提示词，再说明每个人都会犯一次的错误。换成你自己的路径和完成条件。这些例子故意使用口语，因为人们实际就是这样输入，而技能能够理解意图。


## 理解陌生子系统

```text
先用 $dev-learn 理解初始化如何工作，再用 $dev-why 查清它最近为什么坏了。
```

先机制，后历史。每个技能的报告都会说明查了哪些来源，让你知道答案的依据。

## 改代码前先复述杂乱报告

```text
$dev-workflow 阅读这段讨论，用自己的话和通俗语言复述根本问题。暂时不改任何代码。
```

误读会在复述中暴露，只需一条消息纠正。代理给出自己的理解前，先别分享你的原因猜想。`$dev-intake` 只要求复述，不进入操作流程。

## 发送前深化提示词

```text
$dev-sharpen 给新的计费服务写一份入门文档。
```

代理说明专家还会做哪些你没要求的工作、会从哪些原始材料开始、采用哪些方法与工具，以及如何从外部确认结果正确。它返回据此改写的提示词，不执行任务。读起来合适后再发送。

## 选择前先做原型

```text
$dev-workflow 为设置布局做几个原型，用切换器展示，并给我每个方案的截图。
```

你从能运行的东西中选择，而不是从描述中选择。代理也会在过程中回答自己的布局和耗时问题。

## 将确定的设计变成计划

```text
$dev-workflow 把这个设计变成计划，小而可验证的 PR，每个都有自己的证明。
```

设计确定之后再提出。计划本身是交付物，并会说明由哪个操作流程来执行。

## 为设计取得第二意见

```text
让 $dev-parallel 对这段讨论和我们的方案给第二意见。
```

当前设计变成多个候选之一，综合结果会告诉你小组发现了更好的方案，还是确认了现有选择。相比难逆转的设计，这点成本很小。

## 并行检查独立切片

```text
$dev-parallel 按各自 check.sh 检查 packages/ 下每个包。一包一位执行者，一份报告。
```

具备委派能力时每位执行者负责一个隔离包；否则顺序完成切片并说明独立性限制。协调者汇总后返回一份 `PASS`、`ISSUES` 或 `BLOCKED` 报告，而不是堆出原始子代理输出。

## 带着怀疑审查分支

```text
$dev-review 带着怀疑审查整个分支，暂时不改任何内容。除非是真实 bug 或行为回归，不挑细枝末节。
```

这些限定确有作用。“暂时不改”保持只读，不挑细节的规则提前过滤噪声，让经验证的问题值得你花时间。

## 用失败测试修复缺陷

```text
$dev-workflow 先复现重复写入。有廉价测试路径就 $dev-tdd，再修复并重跑。
```

“有廉价测试路径”很重要。硬塞进脆弱 mock 的测试不如运行真实命令能证明的多，流程可以明确这样判断。

## 用证据复现并修复报告

```text
$dev-workflow 用当前项目实际存在的验证入口复现。如果 main 上也能复现，就修复并用视频证明。
```

“main 上也能复现”让缺陷已消失时可以提前结束。视频让你在读 diff 前先看修复是否成立。

## 证明测试难以触达的属性

```text
$dev-formal-verify 检查重试队列。一条消息绝不能被投递两次。
```

实际检查完成时，你会得到在明确模型与边界内已覆盖的属性结果；未完成、受阻和反例会分开报告；代码已经违反它时，会用代码术语给出反例；还会生成项目技能供下一位代理在相关代码变化时重跑。

## 发布数字前先核验

```text
$dev-benchmark 在写进 PR 描述前，核验这个 40% 加速。
```

结果是更快、更慢、没有可测差别或无结论，并附运行次数、范围，以及什么限制了这个数字。

## 停止反复纠正同样错误

```text
$dev-guardrails 代理总是添加配置标志却不把它注册到 Schema。
```

修正依据证据选择架构、类型、已有检查或测试，降低同类错误复发机会；只有机制确实排除了错误路径，才能说它无法再发生。

## 只问怎么做，不开始工作

```text
$dev-help 怎样让 dev-workflow 每一轮都保持生效？
```

你得到答案、一条可发送的提示词和来源链接。发送该提示词前不会执行工作。

## 离开时让执行保持可核查

```text
我要睡了。自主继续，直到每个夹具都通过，不要停。保留决定日志，方便我早上审查。
```

完整约定见[夜间执行页面](guide-autonomous.md)。任务与完成条件已经在对话中时，简短表达就足够。

## 纠正偏离方向的执行

引导提示词只需一行：

```text
我说目标是复现，还没有要求修复。
```

```text
应用 prove it works，给我真实输出，不是构建日志。
```

```text
$dev-writing 刚才那段，不要破折号。
```

通常不需要更多话，只需要准确名称。[原则页面](guide-principles.md) 就是词汇表。

## 用通俗话重说一遍

```text
$dev-learn 用通俗语言重述你上一条回复。
```

明确点出“通俗重述”分支后，[`$dev-learn`](capabilities.md) 会像人与人说话一样重述上一条消息：减少术语，更简短。回复技术上很详尽、你却仍不知道说了什么时使用。

## 了解离开期间的对话进展

```text
$dev-status
```

[`$dev-status`](capabilities.md) 用通俗话说明上次消息之后发生什么，再逐项列出等待你决定的事项、建议、证据与风险。汇报动作本身只读，不为补齐材料启动新实施。用户在已有任务中追问状态时，简短说明后继续原先已授权工作，除非明确要求暂停。

想观看回顾时，明确要求 [`$dev-status`](capabilities.md) 生成视频，并核对当前是否具备真实素材、渲染与成片检查能力。它用短字幕幻灯视频说明经过，并在下方用文字列出等待决定的事项。

## 常见问题

- **在提示词中枚举技能。** “先 $dev-learn，再 $dev-architecture，再 $dev-parallel”会重排流程已经安排的步骤。说明目标与约束，只有覆盖默认选择时才指定技能。
- **完成条件模糊。** “做得更好”不给持续执行机制可检查对象。给出能通过或失败的命令或产物。
- **先讲自己的原因猜想。** 代理会在你指的位置搜索。先让它复述问题，再分享直觉。
- **接受第一个设计。** 一次尝试锁定模型首先想到的形状。要求原型或 `$dev-architecture`，用证据选择。
- **打磨抽象计划。** 对没有代码支撑的计划做对抗审查，会发明永远不会发生的风险。用原型解决开放问题，再审查构建结果。
- **多个并行代理共用 worktree。** 它们会相互覆盖，没人知道谁改了什么。使用实际可用的隔离环境，或明确每个尝试有独立 worktree；共享端口、数据和缓存仍需单独隔离。
- **还不信任循环就开始循环。** 不能验证自身工作的循环，只会加速未经检查的工作。先把验证技能跑通。
- **相信未经核验的数字。** 热缓存或跳过的代码路径都可能伪造加速。数字用于任何地方之前，先运行 `$dev-benchmark`。
- **手工反复纠正同样错误。** 对话中的纠正只帮助一次执行。`$dev-guardrails` 修正仓库，让之后的执行不再重复。
- **把方案比选模式用于覆盖。** `$dev-parallel` 同时支持两类工作：方案比选让候选处理同一简报并融合优点，覆盖模式划分切片或已声明竞速分支并汇总。请求时说明目标，不用比选结果冒充覆盖完整性。
- **接受每条审查意见。** 人和 bot 都会在同一列表里混合真问题与噪声。`$dev-review` 只保留重跑证实的问题，并说明丢弃了什么、为什么；你可以推翻任何一边的结论。
- **把 `auto` 当模型标识。** `auto` 和 `inherit-parent` 在本地配置中表达继承；实际调用按宿主 schema 省略覆盖或用其支持方式，不能直接传不存在的别名。[配置页](guide-setup.md) 介绍各角色。
- **凭绿色构建宣称成功。** 构建证明能编译。要求真实命令、流程、存储值或 profile，并在回复里看到证据。
- **随手写 `SKILL.md`。** 通过`dev-personalize`（编写或修改技能流程） 处理，让校验与审查确实发生。

指南到这里结束。如果跳读到这里，回到[配置](guide-setup.md) 并运行一个真实任务。习惯来自使用，而非阅读。
