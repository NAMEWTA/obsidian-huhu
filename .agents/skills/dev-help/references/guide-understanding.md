# 修改代码之前先理解它

编辑自己不理解的代码，会让隐蔽的回归问题进入交付；这对智能体和你都一样。智能体通常以两种方式失败：误解你的要求，或缺少正确完成工作的背景。[提示词应该包含什么](guide-routing.md)处理第一种，本页处理第二种。

按交付目的选择入口。`$dev-learn` 解释当前机制并组织教学；`$dev-why` 独立追查历史理由；`$dev-status` 汇报指定范围进展；`$dev-workflow` 恢复背景后继续实施。教学可以引用历史依据，但不重复启动同一调查。每一种也都让智能体用你能核查的语言解释自己。这就是你监督一个可能比你更了解代码的智能体的方法。


## 从只读调查开始

原因不清楚时，要求调查发现，不要要求修复：

```text
$dev-workflow 调查为什么后台任务每隔几个小时就超时。告诉我已知事实、用了什么数据，以及你认为最合理的假设。先不要修改代码。
```

“先不要修改代码”会把任务路由到`dev-learn`（调查手册）。它运行 `$dev-learn`，在动机问题上加入 `$dev-why`，返回有引用的解释。面对方案选择时，它返回建议和权衡表。追问“用了什么数据”会让智能体区分证据与猜测。调查发现指向某个修复时，把修复作为新任务启动。

## 用 `$dev-learn` 追踪行为

```text
$dev-learn 我们怎样对通知去重？查找订阅者时是否存在 n+1？
```

提出你真正想问的问题。`dev-learn`（`$dev-learn`） 阅读代码，像资深工程师带你接手子系统那样回答，讲清运行流程、关键类型和不明显的部分。大型子系统在实际具备独立执行能力时，可按边界安排两到四个只读探索视角；数量依据范围与工具上限，不具备时顺序完成。窄问题直接阅读解释。

## 用 `$dev-why` 挖掘历史

```text
$dev-why 为什么重试上限设为五次？理由现在仍然成立吗？
```

`dev-why`（`$dev-why`） 从源码管理开始，再在当前授权与实际访问能力内，按需查询 MCP 或其他工具提供的证据，例如工单跟踪器、长文档、团队聊天、可观测性、错误追踪和分析数据。报告为每项内容提供引用，区分直接证据与推断，记录薄弱时说“看起来”。空结果也会报告，因为“没有人记录原因”本身也是答案。

两种方法可以自然组合。怀疑历史能够解释眼前混乱时，“先做 dev-why，再做 dev-learn”是一个好提示。

## 用 `$dev-learn` 真正理解

```text
$dev-learn 给我讲清这个 PR 如何改变重试。说服我它修复的是原因，而非症状。
```

[`$dev-learn`](capabilities.md) 用于摘要不足以让你理解的时候。它组合模块机制调查与历史依据调查，小改动也许只需其中一种，然后把发现组织成朴素说明，逐张图建立理解。“说服我”这种表达值得复用，它让解释成为可以检验的论证，而非导览。

它也适用于智能体自己的选择：

```text
$dev-learn 给我讲清为什么你这样实现，而没有使用队列。你做了什么取舍，为什么？
```

教学对智能体和你都有帮助。必须解释工作的智能体需要读代码，并为每个主张提供证据，而非自信地说完就继续。

## 恢复背景与回顾进展

```text
$dev-status 帮我回顾上周导出功能的进展
```

`dev-learn`（背景恢复方法）读取用户明确提供或授权的本项目近期记录，以及相关共享工单、既有修复和错误证据，返回当前状态与下一步的简报。旧聊天保存着新智能体缺少的背景，因此在旧主题上开始新工作时，先加载它，再交付新输入：

```text
$dev-workflow 恢复我昨天关于虚拟列表的背景，然后读这份缺陷报告并继续当前目标。
```

仅要进展时由 `$dev-status` 汇报；要继续某条指定聊天或分支时，使用下方的会话接续手册。

## 用会话接续接手此前工作

另一个智能体，或上周的你，留下了进行中的分支时：

```text
$dev-workflow 接手这个分支。读决策日志，弄清哪些已经完成，然后接着做。不要重做已完成的工作。
```

`dev-workflow`（会话接续手册） 把先前轨迹作为恢复起点，并用当前代码、提交与服务状态核对；旧记录不能覆盖最新事实。它重建分支状态与决定，指出恢复点，并对照原始目标验证继承的主张，而非从头推导一遍。

**误区：** 不要因为“智能体反正会读代码”而跳过本页的方法。没有追踪形成的模型就开始编辑，往往会在第一个看起来合理的位置修补症状。先做 `$dev-learn`，比再修第二个缺陷便宜。
