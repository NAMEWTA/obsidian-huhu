# 验证结果并打开 PR

“能编译”不是证据。`dev-guardrails`（证明它能工作原则） 要求智能体在报告成功之前检查真实工件，而你的职责是让“真实工件”能够被检查。本页介绍如何陈述完成条件、核查测量数字、为应用生成验证技能、形式化验证测试很少覆盖的性质、打开 PR，以及推进到合并。

验证是大多数智能体工作中最慢的一步，因为这一步通常在等待人。让智能体能够完成它，你就不再是瓶颈。跳过它，运行更多智能体只会带来更多未经检查的工作供你审阅。


## 先说清完成条件

在第一个提示中，用任何适合的表述写明什么叫完成：

```text
$dev-workflow 为这个命令增加 json 输出。文本输出保持逐字节一致，json 可以解析，两种模式都在示例项目上运行。给我看证据。
```

现在智能体有三个可以运行的检查，而不再是需要满足的一种感觉。回复返回时，应带有精确的命令和输出。如果某项检查无法运行，好的回复会说“无法下结论”。没有证据的自信回复是警告信号。

让检查与变更相匹配：

- CLI 变更运行真实命令。
- UI 变更在运行中的应用里走一遍改变的流程。当它必须逐像素匹配参考时，`dev-verify`（视觉等价操作手册） 会把截图与冻结的基线做差异比较，而不是凭眼睛判断。
- 解析器或迁移重放保存的输入。
- 性能变更比较修复前后的性能剖析结果。
- 存储变更读回刚写入的值。

要求把证明作为你能亲自检查的工件：先失败后通过的测试、修复前后视频、跟踪记录、截图。如果修复已经合并，要求在主干上再次做相同检查。工件胜过看似合理的解释，因为你不必重放整个运行就能质疑它。

对于你不完全信任的小差异，`dev-review`（`$dev-review`） 会找出它可能破坏的其他地方。它找出使变更安全的那个事实，并通过运行代码证明该事实，而不是为它辩护。

## 用 `$dev-benchmark` 核查测量数字

前后对比数字是最容易无意间出错的证据。热缓存、其中一边使用调试构建，或者计时区间里根本没有执行实际工作，都可能产生看起来很可信的加速。在报告数字或据此行动之前，输入：

```text
$dev-benchmark 在导出加速数字写入 pr 之前核查它
```

`dev-benchmark`（`$dev-benchmark`） 会问七个问题，每个问题都要求来自实际运行的证据：

1. 什么限制了这个数字，为什么不是两倍？
2. 每一方是否都像生产运行时那样进行了调优？
3. 结果是否突破了物理限制，例如磁盘带宽或核心数？
4. 是否发生错误，或返回错误输出？
5. 它是否能在交替运行中复现，并给出中位数和范围？
6. 在用户等待的路径上，它是否对端到端体验有意义？
7. 实际工作是否确实发生在计时区间内？

返回的结论是更快、更慢、没有可测量差异或无法下结论，同时附运行次数、范围和限制因素。如果无法说出限制因素，或某一方没有调优，就会说无法下结论。`$dev-workflow` 已经在性能问题和爬山优化操作手册中运行此清单，所以当你在它们之外做了测量，或别人的数字好得可疑时，再自己调用它。这是`dev-guardrails`（解释数字原则） 的实际工作形式。

## 创建项目验证技能

上面的 UI 条目隐藏了一个真实要求。智能体需要一种脚本化方式来操作你的应用。如果项目已有，很好。如果没有，运行：

```text
$dev-verify
```

`dev-verify`（`$dev-verify`） 访谈的是仓库，而不是你。它弄清用户会接触什么、应用如何在本地启动、什么可以操作它（优先已有测试装置，否则使用浏览器和 CDP、PTY 或普通 HTTP）、什么证据能够证明行为，以及两个实例能否并行运行。它只问代码无法回答的事情。

它在用户指定源仓库生成技能，安装目标为 `.agents/skills/dev-verify-<app>/`。正文包含启动、诊断、驱动、证据与清理，附带脚本时说明辅助工具；在 `features/` 下维护功能图，说明应用做什么及何种结果可证明有效。此技能附带一份`dev-verify`（完整功能映射示例），具有 README 索引，并为每个功能提供一个文件，使用四个必需的二级标题。交付之前，生成器会端到端证明一次技能：启动、健康检查、操作一项功能、捕获证据、清理，然后确认清理后证据仍在。如果这次证明失败，不要使用输出。

此后，具备相应工具、环境和授权的智能体可以按本地入口重跑；冷启动时仍应诊断实例与前置条件，不保证所有宿主天然可用。希望证明采用具体形式时，在提示中点名它：

```text
$dev-workflow 构建批量归档动作。使用这个项目实际存在的验证入口检查变更，并给我视频和截图作为证明。
```

```text
$dev-workflow 用这个项目实际存在的验证入口复现这个问题。如果主干上能复现，就修复它，并给我视频作为证明。
```

验证技能可用后，`dev-parallel`（`$dev-parallel`） 可以按功能图拆分检查；只有实例和数据能隔离、工具确实支持时并行，否则顺序完成并汇总结果。验证者群也可以用足够大的样本确认性能提升，或在 PR 交付之前对应用做模糊测试以查找回归。

把验证技能作为持续维护的项目资料。已有授权包含版本保存时提交它，让团队复用相同操作；只要求起草时先交付可审查内容，不为保存文档擅自推送。然后`dev-guardrails`（构建杠杆）。当智能体不断编写一次性脚本来点击应用时，要求提供一个供技能调用的小型控制 CLI。智能体消耗更少的 token，每次运行也变得可重复。便于智能体使用的 CLI 具有以下特点：

- 少量可组合、各自完成真实工作的命令，而不是大量很薄的命令。
- 可能破坏数据的操作提供真实可验证的预览或 `--dry-run`；检查它确实不产生受保护副作用，不只信任名称。
- 子命令逐步展示功能，而不是一次全展开。
- 错误消息说明下一步该做什么。
- 丰富的 `--help` 文本。
- JSON 等机器可读输出。

同时也让开发环境设置可重复：种子数据、测试用户，以及每次都用相同方式启动环境的一条命令。

## 让验证技能保持真实可靠

应用变化后，功能图可能过期。按相关代码变更或用户明确选择的频率维护；只有用户要求定时运行且宿主实际支持时才配置自动化，不默认建立每日任务：

```text
$dev-verify
```

`dev-verify`（`$dev-verify`） 审计生成的技能：按功能核对源码，再真实操作每个映射功能。实际有独立读取能力时可以并行分派，否则顺序完成；共享应用驱动仍按隔离条件安排。它恰好以三种结果之一结束。`clean` 表示完整覆盖且没有需要交付的内容。`changed` 表示验证技能目录内存在已证明更正，按当前授权方式交付；只有目标包含 PR 时才创建 PR。`blocked` 指明阻塞项。它绝不编辑产品代码。如果真实检查发现产品回归，就报告回归，而不是用文档编辑把它掩盖。

## 用形式化验证技能证明性质

验证技能证明你操作的路径。有些缺陷存在于没人操作的路径：两个重试重叠、写入中锁过期、状态变化乱序到达。测试很少到达这些情况。对于这类缺陷代价高昂的代码，运行：

```text
$dev-formal-verify
```

[`$dev-formal-verify`](capabilities.md) 从代码中挑选目标：代码承诺的一项性质，违反它会伤害用户，而测试很少触达破坏它的情况。它选择最有价值的目标，而不是最容易验证的目标。也可以点名一个领域或缺陷，从那里开始：

```text
$dev-formal-verify 任务租约和重试逻辑。一个任务绝不能在同一时间运行两次。
```

问题决定工具。事件是否可能以有害顺序发生，适合对设计的小模型使用模型检查器；可选 TLA+ 或项目已有适合工具；实际可用性、边界和维护成本决定选型，不因代码语言无关就强制安装某个工具。代码是否对每个输入都符合要求，适合直接在代码上运行的验证器。如果没有验证器支持你的语言，智能体会说明，并用生成的输入测试真实代码，而不是测试手写的函数模型。必须在每种规模上成立的性质，可能需要证明。智能体会告诉你选择了什么工具，以及为什么。

它验证一项性质，并展示这项性质在代码的损坏变体上失败，因为从没见过失败的检查无法证明任何事。如果当前代码已经违反性质，你会得到按代码术语表述的一串简短反例步骤。性质保持原样，因此发现仍然是发现。除非你提出要求，否则产品代码不改变。

它写出一个项目本地技能，告诉下一个智能体如何判断变更是否触及已验证代码、如何用一条命令运行检查，以及如何区分真实缺陷与建模错误。交付之前，生成器会在一个破坏性质的临时变更上遵循该技能一次，检查必须捕获它。交接说明验证了什么、使用什么工具和边界、检查发现了什么，以及没有覆盖什么。通过只覆盖模型或边界，不覆盖整个系统。

此技能还记录每项检查覆盖哪些代码，以及检查最后一次与其匹配的提交。绕过技能的合并和重构，可能让检查仍在通过，但检查的只是已经不存在的代码描述。发生这类变更之后，运行 [`$dev-formal-verify`](capabilities.md)。它根据代码更新验证、重新运行验证、展示每项更新后的检查仍然能够失败，并告诉你每次失败究竟来自验证漂移，还是代码缺陷。

## 用状态图展示行为

模型术语中的反例可以说服你。负责这项行为的产品经理或设计师，需要用他们的术语看到它。运行：

```text
$dev-statechart 用户离线编辑笔记时会看到什么
```

[`$dev-statechart`](capabilities.md) 从实际模型或行为定义生成用户视角的 Mermaid 状态图，并记录生成依据。使用 TLA+ 等检查器时保留真实结果；图或模型变化后仍需重新生成和核对，不能声称它们永远不会漂移。读者的规则（“离线时绝不能显示已同步”）会成为不变量。图会标出每个违反规则的状态，报告用读者的语言给出到达它的最短路径。交付之前，智能体会在真实代码中复现每条缺陷路径，避免把建模错误当成缺陷交给读者。

## 打开 PR

```text
$dev-workflow 打开 pr。小而有序的提交，描述中附证据。
```

`dev-deploy`（打开 PR 操作手册）先保护当前工作，再按实际需要隔离、整理可审查提交与差异，返回已创建 PR 的真实链接。只有必要且授权允许时才变基或改写历史。变更按真实依赖拆分，不为了达到固定 PR 数量而制造堆叠。

## 用持续照管推进到可合并

PR 一旦打开，就会立即开始积累阻塞。检查失败、审阅者评论、主干向前变化。把这些反复变化交给`dev-deploy`（持续照管操作手册）：

```text
$dev-workflow 持续照管这个 pr。让它变绿。
```

持续照管使用当前实际可用的托管连接器、CLI 或事件通知观察 PR，并依次处理冲突、审查和 CI。不假定包内有观察器，也不要求特定厂商的状态协议。已知修复合并为一次推送，使检查只重启一次，而不是每修一处就重启。评论分诊保持审慎，因为人和机器人会在同一个列表里提交真实问题和噪声。真实发现按授权修复，噪声用具体反证说明；只有外部回复已获明确授权时才在线程发送，否则交付拟回复。如果只想要状态，就提出更小的请求，持续照管会回答而不启动循环：

```text
$dev-workflow 看一下 pr 123。还有什么未解决？
```

持续照管到可合并就停止。即使全部变绿，它也绝不合并，因为合并是另一个决定。

## 用交付流程合入堆叠

绿色并不等于安全。当你准备好合入时，明确说出来：

```text
$dev-workflow 合入这个堆叠。
```

`dev-deploy`（交付操作手册） 在启用任何合并动作之前，独立验证每个 PR。按风险与项目要求，对每个 PR 提供真实行为证据和实际可用的独立复核；没有独立能力时如实说明，不能冒称完成必要门禁。已授权合并时，通过真实可用的托管工具从底部逐个合入连续通过的范围，并报告第一个阻塞项。位于未验证 PR 上方的已验证 PR 必须等待，因为合入它会把下面的缺口一起带进去。
