# 组织提示词

提示词说明意图与完成判据。操作流程提供步骤，所以几句普通话往往比一份规格更合适。

## 应当放入

- 目标：说明出了什么问题，或用户想要什么。
- 完成判据：可以通过或失败。“做得更好”和持续时长都不是判据。
- 要展示的证据：真实命令输出、流程视频、存储值，或前后对比数字。
- 用户已经知道的事实：症状、复现步骤、日志或链接可以减少一次搜索。
- 真实约束：“先复现”“暂时不改代码”“行为零变化”“继续前让我审查”都会改变代理行为。

## 应当省略

- 具体做法：说要达成什么，给代理寻找更好方法的空间。
- 技能或步骤列表：手工顺序容易遗漏或重排流程本会保留的步骤。只有要覆盖某个选择时才指定技能。
- 用户对原因的猜想：在代理复述问题前将猜想与已知事实分开，并先核对根本问题，避免搜索只围绕一个猜测。

## 先加载上下文

- 对信息杂乱的报告，要求代理先用自己的话和通俗语言复述根本问题，再做其他事。误读会在代码出现之前暴露。
- 新对话中用 `$dev-workflow` 从用户提供或授权的记录恢复尚不清楚阶段的工作并继续；已有明确切片时由原执行入口接续。只要历史进展简报时使用 `$dev-status`。缺少历史时说明范围，不跨项目搜索私人聊天。
- 修改陌生代码前，用 `$dev-learn` 理解机制、`$dev-why` 理解理由。没追踪过机制的代理会在第一个看似合理的位置修症状。
- 让 `$dev-learn` 为某个选择论证，例如“说服我，它修复的是原因而不是症状”。论证比摘要容易核查。

## 先设计，再计划

- 不接受第一个设计。要求几个方案的原型；UI 配截图或视频，再根据证据选择。
- 让原型回答开放问题。不要对抽象计划进行对抗审查，因为审查者会编出永远不会发生的风险。
- 共享包或 API 先写 README 或教程，再反推代码。文档成为代理自我检查的目标。
- 设计确定后再要计划，每个计划步骤以检查结束。

## 简短跟进

- 对话已经包含任务时，“做吧”“继续”“一直做完”本身就是完整提示词。
- 切换目标时明确说明这是新任务；“new task”是可用的普通表达，不是所有宿主必需的命令。状态追问和补充说明仍应保留原任务。

## 离开之前

- 离开时说明是否继续推进，以及已有授权和预算；离开本身不授予新增动作权限。
- 把完成写成每轮都可运行的检查；有实际事件或调度机制时采用，没有时在当前会话执行并留下恢复记录。
- 要求从明确基线创建新 worktree。
- 预先回答代理可能停下来问的问题，例如“提交前不用问我”。
- 要求保存稍后可以审计的决定日志。
- 给出退出条件：“如果几个小时后确实卡住，就停下来写明原因。”

## 用一句话引导

- 重申目标：“我说目标是复现，还没有要求修复。”
- 指出原则：“应用 prove it works。给我实际输出，不是构建日志。”
- 原则名称对应 `dev-guardrails` 的完整规则，需要时先读取；只在确实改变决定时说明作用，不能假定智能体已经读过全部资料。
