# 值得复制的提示词

换成真实路径、技能与完成判据。口语表达也有效。

## 理解

- `$dev-workflow 阅读 <讨论>。用自己的话和通俗语言复述根本问题。`
- `$dev-intake <冗长或杂乱的要求>`
- `$dev-sharpen <即将发送的提示词>`
- `$dev-workflow 调查为什么出现 <症状>。给出已知事实、使用的数据和最有根据的假设，暂时不改代码。`
- `用 $dev-learn 理解 <子系统>，再用 $dev-why 追溯与本次回归有关的历史变更和理由；实际故障复现与修复使用 $dev-debug。`
- `$dev-workflow 恢复我上周在 <话题> 上的背景，然后读取 <问题> 并继续当前目标。`
- `$dev-why 当时为什么采用这种实现而不是 <另一种方法>？有哪些可查证的取舍？`
- `$dev-workflow 接手这个分支。读取决定日志，查清已完成内容并继续，不重复已经结束的工作。`

## 构建

- 缺陷：`$dev-workflow <症状>。先复现，再修复并验证。`
- 应用缺陷：`$dev-workflow 用当前项目实际存在的验证入口复现。如果 main 上也能复现，就修复并用视频证明。`
- 有廉价测试路径的缺陷：`$dev-workflow 先复现 <缺陷>。有廉价测试路径就用 $dev-tdd，再修复并重跑。`
- 功能：`$dev-workflow 增加 <行为>。<当前输出> 保持字节一致，两者都验证。`
- 重构：`$dev-workflow 把 <代码> 移进一个模块，行为零变化。先记录当前输出，再证明修改后不变。`
- 性能：`$dev-workflow 在 <夹具> 上 <操作> 要花 <时长>。追踪并修复已测量的原因，给出前后对照。`

## 设计与计划

- `$dev-workflow 为 <功能> 做几个原型，截图或录视频让我比较。`
- `$dev-workflow 我们需要 <功能>。先 $dev-architecture，用原型回答开放问题，继续前让我审查。`
- `$dev-workflow 先写一份如何使用 <新包> 的教程，再 $dev-learn 它为什么优于当前版本。`
- `让 $dev-parallel 对这段讨论和我们的做法给第二意见。`
- `$dev-workflow 把这个设计变成计划。拆成小而可验证的 PR，每个都有自己的验证步骤。`
- `$dev-workflow 规划将 <库> 迁移到 <目标>。小而可验证的 PR；结果必须与原版完全一致，包括已有 bug。`

## 审查与交付

- `$dev-review 带着怀疑审查整个分支，暂时不改任何内容。除非是真实缺陷或回归，不挑细枝末节。` 同时阅读 Dropped 列表。
- `$dev-formal-verify 证明 <模块> 中的 <属性> 在 <步骤> 交错或重试时仍成立。` 这些代码合并或重构后运行 `$dev-formal-verify`。
- `$dev-parallel 按各自检查脚本检查 <目录> 下每个包，一包一位执行者，一份报告。`
- `$dev-workflow 开 PR。小而有序的提交，描述里带证据。`
- `$dev-workflow 跟进这个 PR，让它全绿。` 只看状态时用：`$dev-workflow 检查 PR <编号>，还有什么未完成？`
- `$dev-workflow 落地这组堆叠 PR。`

## 离开与回来

- `$dev-workflow 我要睡了。从 <基线> 的新 worktree 完成 <目标>，完成意味着 <检查>。保留决定日志，提交前不用问我。按当前可用机制持续执行，遵守约定预算。达到上限或确实卡住时，停下来写明原因。`
- `$dev-workflow 复核这次任务的决策记录及证据，说明昨晚的关键选择、结果和仍需关注的事项。` 这使用通用决策证据复核方法；只想快速了解变化时，使用 `$dev-status`。
- `$dev-status` 回顾本对话自上次消息以来的变化，列出等待你作出的每个决定。
- `$dev-workflow 对这个队列执行 full autopilot，每个条目互相独立。`
- `$dev-workflow 自动推进这些改动，但不要合并，我来落地。`
- `$dev-archive 保存这次学到的经验，避免下一轮重犯。` 只保留会改变未来决定的修改；已有维护授权时直接完成，未授权范围交付具体建议。
- `$dev-learn 用通俗语言重述你上一条回复。`
