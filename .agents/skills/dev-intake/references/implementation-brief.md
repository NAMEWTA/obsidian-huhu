# 编写智能体简报

## 阅读导航

- [原则](#原则)
- [模板](#模板)
- [示例](#示例)

智能体简报是请求已经足够明确时保存的结构化行为契约，可以是本地 Markdown，或在已获授权时发布为事项／PR 评论。它供无人值守实施者使用；原始正文和讨论是上下文，最新已接受的简报是本次契约。

简报说明**智能体应该做什么**，适用于两种入口：对事项，是从无到有构建变更；对 PR，是**现有差异还剩下什么要做**，例如完成它、补齐缺口、处理审查意见。两者原则一致；下方 PR 示例展示区别。

## 原则

### 耐久优先于精确位置

事项可能在 `ready-for-agent` 停留数天或数周，期间代码库会变化。简报应在文件改名、移动或重构后仍然有用。

- **要**描述接口、类型和行为契约。
- **要**指出智能体应寻找或修改的具体类型、函数签名或配置形状。
- 语义契约不依赖文件路径；把可检索的相对路径、符号和观察提交单列为现状证据，实施和归档时复核。
- 行号只能辅助本次审查，不作为长期唯一定位。
- **不要**假设当前实现结构将保持不变。

### 面向行为，而非操作步骤

描述系统**应该做什么**，而不是**如何实现**。智能体会重新探索代码库，自己作出实现决定。

- **好：** “`SkillConfig` 类型应接受可选的 `schedule` 字段，类型为 `CronExpression`。”
- **坏：** “打开 src/types/skill.ts，在第 42 行添加 schedule 字段。”
- **好：** “用户不带参数运行 需求入口 时，应看到需要关注的事项摘要。”
- **坏：** “在主处理函数中添加 switch 语句。”

### 完整验收条件

智能体需要知道何时算完成。每份简报必须有具体、可测试的验收条件。各条件应能独立验证。

- **好：** “运行 `gh issue list --label needs-triage` 返回已经过初步分类的事项。”
- **坏：** “分诊应该正常工作。”

### 明确范围边界

说明哪些不在范围内，避免智能体过度完善，或自行假设相邻功能也要做。

## 模板

```markdown
## 智能体简报

**类别：** bug / enhancement
**摘要：** 用一行描述需要发生的变化

**当前行为：**
描述现在会发生什么。缺陷写损坏行为；增强写新功能所建立于的现状。

**目标行为：**
描述智能体完成工作后应该发生什么。
明确边界情况和错误条件。

**关键接口：**
- `TypeName`：需要改变什么，以及为什么
- `functionName()` 返回类型：当前返回什么，应该返回什么
- 配置形状：需要哪些新配置选项

**验收条件：**
- [ ] 具体、可测试的条件 1
- [ ] 具体、可测试的条件 2
- [ ] 具体、可测试的条件 3

**范围之外：**
- 本事项不应修改或处理的内容
- 看起来相关但应分开的相邻功能
```

## 示例

### 好的智能体简报：缺陷

```markdown
## 智能体简报

**类别：** bug
**摘要：** 技能描述截断在单词中间，产生不完整输出

**当前行为：**
技能描述超过 1024 个字符时，无论单词边界如何，都恰好在第 1024 个字符处截断。
这会产生结束于半个单词的描述，例如 “Use when the user wants to confi”。

**目标行为：**
应在 1024 个字符之前的最后一个单词边界截断，并追加 “...” 表示发生截断。

**关键接口：**
- `SkillMetadata` 类型的 `description` 字段：无需改变类型，
  但为其赋值的验证／处理逻辑需要尊重单词边界
- 任何读取 SKILL.md frontmatter 并提取描述的函数

**验收条件：**
- [ ] 少于 1024 个字符的描述不变
- [ ] 超过 1024 个字符的描述在 1024 之前最后一个单词边界截断
- [ ] 截断后的描述以 “...” 结尾
- [ ] 包括 “...” 在内的总长度不超过 1024 个字符

**范围之外：**
- 修改 1024 字符上限本身
- 多行描述支持
```

### 好的智能体简报：增强

```markdown
## 智能体简报

**类别：** enhancement
**摘要：** 支持使用 `.agents/dev/notes/context/scope-decisions/` 目录跟踪被拒绝的功能请求

**当前行为：**
功能请求被拒绝时，以 `wontfix` 标签和评论关闭事项。
决定和理由没有持久记录。以后遇到类似请求，维护者只能回忆或搜索先前讨论。

**目标行为：**
被拒绝的功能请求应记在 `.agents/dev/notes/context/scope-decisions/<concept>.md` 文件中，
包含决定、理由，以及所有曾提出该功能的事项链接。
分诊新事项时，应检查这些文件是否匹配。

**关键接口：**
- `.agents/dev/notes/context/scope-decisions/` 中的 Markdown 文件格式：每个文件应有
  `# 概念名称` 标题、`**决定：**` 行、`**原因：**` 行，
  以及列出事项链接的 `**先前请求：**` 列表
- 分诊流程应尽早读取所有 `.agents/dev/notes/context/scope-decisions/*.md`，
  按概念相似性与新事项匹配

**验收条件：**
- [ ] 已授权拒绝功能后，在 `.agents/dev/notes/context/scope-decisions/` 中创建或更新文件
- [ ] 文件包含决定、理由和被关闭事项的链接
- [ ] 已有匹配文件时，把新事项追加到“先前请求”，而不是创建重复文件
- [ ] 分诊检查已有文件，新事项与先前拒绝匹配时，明确提出该记录

**范围之外：**
- 自动确认匹配，匹配由人确认
- 重新开启先前被拒绝的功能
- 缺陷报告，只有增强请求的拒绝才进入 `.agents/dev/notes/context/scope-decisions/`
```

### 好的智能体简报：PR

对于 PR，“当前行为”描述差异的当前状态，简报要求智能体完成或修复它，而不是从头构建。

```markdown
## 智能体简报

**类别：** enhancement
**摘要：** 完成贡献者为 `triage list` 提供的 `--json` 输出标志

**当前行为：**
PR 添加了 `--json` 标志，把事项列表序列化为 JSON。
正常路径可用，差异也符合项目命令结构。还有两个缺口：
错误仍以面向人的文本输出，而非 JSON；新标志没有测试覆盖。

**目标行为：**
指定 `--json` 后，所有输出包括错误都应在 stdout 上形成有效 JSON，
命令退出码保持不变。未指定标志时，现有可读文本输出不变。

**关键接口：**
- `--json` 下命令的错误路径应输出 `{ "error": string }`，替代纯文本错误
- 复用 PR 已加入的序列化器，不引入第二个

**验收条件：**
- [ ] `triage list --json` 在成功和错误场景都输出有效 JSON
- [ ] 退出码与非 JSON 命令一致
- [ ] 测试覆盖 `--json` 成功输出和一个错误场景
- [ ] 默认的非 JSON 输出逐字节不变

**范围之外：**
- 为其他命令添加 `--json`
- 修改 PR 已定义的成功负载 JSON 形状
```

### 不好的智能体简报

```markdown
## 智能体简报

**摘要：** 修复分诊缺陷

**要做什么：**
分诊那个东西坏了。看看主文件并修复。
大约第 150 行的函数有问题。

**需要修改的文件：**
- src/triage/handler.ts（第 150 行）
- src/types.ts（第 42 行）
```

不好之处：

- 没有类别。
- 描述模糊，例如“分诊那个东西坏了”。
- 只引用会过期的文件路径和行号，没有行为语义或复核上下文。
- 没有验收条件。
- 没有范围边界。
- 没有描述当前行为与目标行为的区别。

验收条件描述规格中的可观察结果。明确行为后，可用测试先行或实现后验证将这些示例变成运行证据，选择能最快获得可靠反馈的方式。
