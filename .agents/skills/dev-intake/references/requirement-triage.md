把聊天、文档、问题报告和附带改动的请求整理成可执行简报。复用项目已有跟踪器；没有跟踪器时用本地 Markdown。下列角色是描述处理结果的可选词汇，不要求状态机、固定标签或迁移门禁。

如果仓库把外部拉取请求也视为需求入口，见事项跟踪器配置，分诊也涵盖它们：**PR 是附带代码的事项**，采用相同的分类与处理思路，差异在下文以“对于 PR”标明。裸编号 `#42` 应按跟踪器配置解析为事项或 PR。

仅在用户已经授权发布事项或评论时执行外部写入，复用项目披露规范；没有规范时可使用以下声明。读取或分诊本身不授权评论、关单或改标签：

```text
> *此内容由 AI 在分诊过程中生成。*
```

## 角色

两个**类别**角色：

- `bug`：某项行为损坏。
- `enhancement`：新功能或改进。

五个**状态**角色：

- `needs-triage`：维护者需要评估。
- `needs-info`：等待报告者补充信息。
- `ready-for-agent`：规格完整，可交给无人值守智能体。
- `ready-for-human`：需要人来实现。
- `wontfix`：不执行。

对于 PR，相同状态应结合附带代码理解：`ready-for-agent` 表示已附简报，智能体应在当前差异上继续下一步；`ready-for-human` 表示可由人合并。

已有标签体系时，避免互相矛盾的分类和进展描述。遇到冲突先读取最新讨论与实际证据，修正本地简报；只有冲突影响目标且无法查明时才询问维护者。没有标签体系无需创建。

这些名称只帮助理解分支。复用已有跟踪器标签或自然语言描述；本地记录方法见 `dev-plan`（本地工作记录）。

处理结果可以是待评估、待补信息、可实施、需人工或不执行。报告者提供新证据后重新评估；维护者的最新明确意图和已授权范围持续有效。不要求按某个状态顺序流转。

## 调用

维护者使用本技能，用自然语言描述意图。理解请求并执行。例如：

- “展示需要我关注的内容。”
- “看一下 #42。”可以是事项或 PR。
- “把 #42 移到 ready-for-agent。”
- “有哪些可以交给智能体处理？”

## 展示需要关注的事项

查询事项跟踪器，按以下三组展示，各组旧的在前：

1. **无标签**：从未分诊。
2. **`needs-triage`**：正在评估。
3. **上次分诊笔记后报告者有新活动的 `needs-info`**：需要重新评估。

PR 在范围内时，把外部 PR 也放进这些组，每行标注 `[PR]` 或 `[issue]`。发现阶段只展示**外部** PR，跟踪器配置定义何为外部，因此协作者正在开发的 PR 不属于分诊工作。这个过滤只适用于发现阶段；明确指定的 PR 无论作者是谁都应分诊。

显示数量，并为每项提供一行概述。若用户要求浏览队列，供其选择；已指定目标时直接处理目标。

## 分诊指定事项或 PR

1. **收集上下文。** 阅读完整事项或 PR，包括正文、评论、标签、作者和日期；PR 还要阅读差异。解析已有分诊笔记，避免重复询问已解决的问题。使用项目领域词汇表探索代码库，尊重相关区域的 ADR。针对代码库做两项检查：其一，**重复实现检查**，按领域概念而不只按请求措辞搜索已有实现，并报告查过哪里；如果已存在，就是已实现的 `wontfix`，转第 5 步。其二，**先前拒绝检查**，阅读 `.agents/dev/notes/context/scope-decisions/*.md`，指出类似请求。

2. **提出建议。** 告诉维护者建议的类别和状态及理由，并简述相关代码库情况，包括是否已经实现。用户明确要求先审建议时等待；已要求处理时，在既有授权内继续。

3. **验证主张。** 任何追问前，先检查主张是否成立。缺陷按报告者步骤复现。PR 要确认差异是否做到了声称的事情：检出它，运行相关测试或命令。报告结果：已确认并给出代码路径、验证失败，或细节不足；细节不足是强烈的 `needs-info` 信号。确认过的验证使智能体简报更可靠。

4. **必要时追问。** 请求需要细化时，阅读`dev-grill`（决策访谈）和`dev-architecture`（领域建模），一轮问题一轮问题地打磨需求，同时精确领域术语，并在决定落定时即时更新 `glossary.md`／ADR。

5. **落实结果：** 以下发布、标签和关闭操作均以用户已授权对应外部动作为前提；未授权时将同样内容保存为本地简报或待执行建议，不冒充已发布。
   - `ready-for-agent`：发布智能体简报评论，见 [实现简报](implementation-brief.md)。
   - `ready-for-human`：结构与智能体简报相同，但说明为什么不能委派，例如判断取舍、外部权限、设计决定、人工测试。
   - `needs-info`：发布分诊笔记，模板见下文。
   - `wontfix`：关闭事项，评论内容取决于**原因**：
     - **已经实现**：代码库中已有此变更。指出所在位置；**不要**写入 `.agents/dev/notes/context/scope-decisions/`，该知识库用于记录被拒绝的请求，而不是已实现的功能。
     - **拒绝，缺陷**：礼貌解释，然后关闭。
     - **拒绝，增强**：写入 `.agents/dev/notes/context/scope-decisions/`，在评论中链接它，然后关闭，见 [范围决定](scope-boundaries.md)。
   - `needs-triage`：应用角色。如有部分进展，可选择评论。

## 快速覆盖状态

维护者说“把 #42 移到 ready-for-agent”时，信任其判断并直接应用角色。简短说明即将进行的已授权动作，包括角色修改、评论、关闭，然后执行，不重复索要确认。跳过已经完成的追问；需要交接时依据已有上下文补齐简报，仅对真实缺失的行为决策提问。

## 待补信息模板

```markdown
## 分诊笔记

**目前已经确定：**

- 要点 1
- 要点 2

**仍需要你（@reporter）补充：**

- 问题 1
- 问题 2
```

把追问中解决的全部内容放在“目前已经确定”下，避免成果丢失。问题必须具体、可行动，不能只是“请提供更多信息”。

## 恢复先前会话

事项或 PR 已有分诊笔记时，先阅读，检查报告者是否回答了未决问题，再在继续前展示更新后的全貌。不要重复询问已解决问题。
