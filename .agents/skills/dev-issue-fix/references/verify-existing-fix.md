# 验证已有修复

当一个开放的拉取请求或已经合入的提交可能修复这份报告时，使用此模式。

已有工件拥有修复任务。验证它。不要编辑它、编写竞争补丁，或再打开一个拉取请求。

## 确认工件资格

要求有一个具体工件：

- 包含解决该症状的代码变更的开放拉取请求
- 已经合入的拉取请求
- 代码和意图匹配的已合入提交

没有拉取请求或提交时，线程中的声称、追踪器状态、分支名称或原因假设都不够。

存在多个工件时，选择原报告或追踪器链接的那个。否则选择与受影响代码最接近的一个，并说明原因。

## 保护工作树

仓库支持时，使用隔离的工作树或另一个干净检出。不要覆盖用户变更。

记录：

- 基线版本
- 修补后版本
- 拉取请求或提交 URL
- 两次运行共用的构建和环境输入

使用目标仓库平台实际返回或验证的规范拉取请求链接。

## 测量基线

对于开放的拉取请求，使用它的基分支作为基线。

对于已经合入的修复，如果紧邻修复之前的版本可以构建，且能够代表旧行为，就使用该版本。

通过已配置的控制适配器：

1. 启动基线应用。
2. 确认应用和环境正确。
3. 通过真实 UI 动作执行报告中的路径。
4. 观察能够区分结果的症状。
5. 重置并重复。
6. 捕获基线录像、截图和状态检查。

如果症状未在基线上出现两次，就不存在基线。不要宣称修复有效。

## 测量修补后的构建

使用相同环境和数据，构建并运行拉取请求或修复提交。

1. 执行相同的 UI 路径。
2. 重复两次。
3. 确认错误状态已消失。
4. 确认预期状态出现。
5. 捕获修复后录像、截图和相同的状态检查。

不要止步于编译或测试。修复后的结果必须来自正在运行的修补后应用。

## 结果

### 已确认

基线复现两次，修补后的构建解决两次。

- 将运维状态标记为已验证。
- 链接工件。
- 已选择来源回写且既有授权覆盖外发时，来源预检后发布一条简短的原生回复；本次已用主动回复额度时改用获准的运维记录或运行输出，不重复主动打扰来源。输出模式直接交付结果，未获外发授权时准备完整草稿。
- 包含修复前后结果。
- 不打开任何拉取请求。

### 修复不足

症状在基线和修补后的构建上都出现。

- 将运维状态标记为已复现但未修复。
- 链接工件，并说明它没有解决症状。
- 如果已有外发授权，且本次运行尚未使用确认复现的来源更新额度，发布正常的确认复现更新；否则保留在获准的运维线程或运行输出。
- 不打开竞争拉取请求。

### 无法下结论

基线无法复现、修补后的应用无法运行，或证据没有展示能够区分结果的状态。

- 不要宣称成功。
- 说明哪一半无法测量。
- 将结果保留在运维线程或运行输出中。
- 除非直接提问需要答复且已有发送授权，否则不向原报告发布任何内容。

## 清理

停止两个构建，按照保留策略删除临时配置文件和捕获文件，并在不丢弃用户工作的前提下，使仓库回到先前状态。
