# 问题报告分诊

为一份指定报告分类，在原报告的原生讨论位置或已选运行输出交付一条有用结论。只有明确的新缺陷才考虑创建追踪器问题。不要在这里复现或修复。

读取用户指定的报告或实际事件，按`dev-issue-setup`（来源适配）核对报告身份、内容、交付方式与当前授权。手工只读任务可直接从现有材料形成最小配置；持续任务读取包外项目配置。缺少某项写入或持续运行条件时，完成其余只读准备并列明缺口，不把“分析这份报告”扩展成外发或监听。已有授权继续有效；配置参考`dev-issue-setup`（配置模板）。

## 不可违反的安全规则

- 来源范围和原始报告身份不可变；具体平台字段按来源适配核验。
- 来源回复不新建报告、不广播；Slack 分支绝不发布来源频道根消息。
- 不改发其他容器或接收者，不发送未授权私信，不新建替代讨论。
- 在任何追踪器写入之前，以及发布结论的紧前时刻，重新核验原报告对象。
- 如果原报告缺失、已删除、不可访问或无法确定，停止新业务写入。仅对本次已经创建的工单，可以在核实交接失败后执行事先授权的补偿；先核对实际发帖结果，结果未知时记录未知，不重发、不臆测成功或删除。
- 发布一条实质性结论。不要播报进度。
- 协调者是唯一可以向来源平台或运维目标外发的执行者。
- 委派的工作者只返回发现。它们必须为只读，且不得获得来源或追踪器凭据及任何外部写入动作。
- 每个子任务提示都必须禁止当前工具集的全部外部写入。Slack 分支包括 `SendSlackMessage`、`PostToSlack`、`chat.postMessage`；这些是示例，不假定动作存在，提示禁止也不能代替真实权限隔离。
- 如果工作者隔离无法执行这些限制，就由协调者完成工作。
- 绝不创建无法追溯到原始报告的问题。
- 宁可不建工单，也不要建猜测性或重复的工单。
- 将 `dev-guardrails`（先拆分共享状态） 应用于来源坐标。
- 将 `dev-guardrails`（降低阅读负担） 和 `dev-writing`（清理机械写作） 应用于最终结论。

## 1. 固定来源坐标

在制作工作清单或委派之前，按`dev-issue-setup`（来源适配）完成：

1. 从用户指定材料或真实事件取得来源类型与账号、工作区、容器范围，并与当前配置核对。
2. 提取原报告身份及原生回复关系；事件投递 ID 与报告身份分别保留。
3. 保存不可变的 `SOURCE_SCOPE`、`SOURCE_ITEM_ID`、适用的 `SOURCE_PARENT_ID` 和 `SOURCE_REFERENCE`。
4. 读取原对象，核对正文、实际作者及返回身份；手工材料核对实际文件、附件或当前用户输入。
5. 确认结果交付到原报告还是当前运行输出，不因后续工具失败更换。
6. 采用 Slack 时，完整执行来源适配中的七步线程规则：`trigger.thread_ts` 为空才使用 `trigger.ts`，核对非空根坐标与真实永久链接。

之后每次读取或外发都使用保存的身份，不替换成回复、运维对象或同名记录。

## 2. 阅读完整报告

在决定之前，阅读原报告、当前讨论和实际作者；手工材料保留用户给出的完整语境。

记录：

- 报告者的原话
- 已提供的产品版本、应用构建、环境和平台
- 预期行为
- 观察到的行为
- 发生频率和触发条件
- 错误文本或堆栈特征
- 已有问题、提交或拉取请求链接
- 关于某人已经在修复的明确说明

检查每份相关附件。

- 以足以使用的完整分辨率阅读截图。
- 检查视频中区分正确行为和错误行为的状态转换。
- 阅读日志、跟踪记录和崩溃文本中的具体特征。
- 如果媒体需要专门审阅，使用只读媒体工作者，并提出一个范围明确的问题。工作者只返回发现。
- 如果附件无法读取，在结论中说明。不要编造它所展示的内容。

先使用原报告与已有讨论中的证据，再要求报告者补充。

## 3. 先追踪原因，再分流

在选择负责人或目的地之前，对源码和历史进行一次有边界的检查。使用`dev-learn`（模块运行追踪） 追踪从报告中的操作到观察结果的路径。报告看起来像回归，或涉及防御性代码时，使用 `dev-why`（历史依据调查）。

1. 识别从报告中的操作到观察结果的可能代码路径。
2. 检查可见症状属于这条代码路径，还是它下层的依赖。
3. 当报告像回归时，检查近期变更。
4. 检查是否已经有合入的提交或开放的拉取请求解决同一症状。
5. 区分已确认事实和假设。

这次检查不需要找出完整根因。但它必须足以避免把可见症状分给错误的负责人。

如果无法读取仓库，不要猜测代码负责人。继续保守分类，并说明无法追踪原因。

## 4. 分类

选择一个类别。

### 缺陷

某种情况违反了预期行为。例如错误输出、损坏的状态、报错、崩溃、挂起、静默无操作或回归。

### 性能

报告描述可测量的缓慢、内存过量、电池消耗、卡顿或其他资源问题。把它视为缺陷，但保留测量和性能剖析结果。

### 功能请求

当前行为看起来是有意设计的，报告者希望获得不同的行为或操作能力。

### 问题或反馈

报告询问某件事如何工作、表达没有具体缺陷的偏好，或给出一般反馈。

### 转交

原因追踪表明另一个已配置的目的地负责该问题。

当缺陷与功能请求的界线不清楚时，不要建单。唯一的一条结论可以提出一个聚焦的问题，并使用 `other` 标记。

## 5. 应用已配置的分流规则

从 `routing.map_path` 读取可选分流映射；结构与完整规则见 [分流映射示例](../assets/routing.md)。

- 根据已确认的产品领域、代码路径或错误特征进行匹配。
- 当原因追踪指向其他位置时，仅凭可见症状不足以分流。
- 如果没有匹配的规则，说明负责人不明确。不要猜测。
- 不跨容器或接收者发帖。在原报告或运行输出中告诉报告者应把问题转交到哪里。

默认不提醒负责人。只有以下条件全部成立时才允许提醒：

1. 分流映射明确列出了负责人。
2. 配置允许这种提醒类型。
3. 该事项是需要负责人输入的功能请求，或近期历史以强证据识别出可能引入回归的作者。
4. 负责人不是范围宽泛的值班组。

其他情况都不提醒。

## 6. 使用问题追踪器适配器

追踪器是一个适配器，而非必须使用的厂商。Linear 适配器是一个有效例子。GitHub Issues 适配器或其他追踪器也可以实现相同契约。

所有追踪器写入及失败补偿都必须在用户或已启用任务的既有授权内；缺少写入授权时，只做搜索和读取，准备完整拟更新内容。按本次查重或写入范围核对以下能力；只读分类不要求创建、更新或补偿权限：

- 按文本、状态、标签、来源引用和日期范围搜索问题
- 读取一个问题及其链接
- 创建包含标题、正文、状态、标签和可核验来源引用的问题
- 更新现有问题，同时不替换无关字段
- 添加来源链接和复发说明
- 如果约定的结论交付明确失败，能够取消、关闭或删除本次运行创建的问题

先确认当前连接器、API 或已配置 CLI 实际提供这些能力和权限；所列是能力契约，不是固定工具名。如果所需操作不可用，则禁止相应写入。

未配置追踪器且只要求分类时，交付分类与证据并注明查重、建单未执行；不能声称没有重复问题。已要求查重或写入时，能力缺失属于该部分受阻，不跳过检查去建单。

在运行时解析配置中的团队、项目、状态和标签。除非配置明确要求，否则不要编造 ID、创建标签、分配负责人或设置优先级。

## 7. 去重

始终检查来源身份与引用是否已关联到追踪器问题或先前结论。来源本身就是目标追踪器中的同一问题时，复用这个问题，不再创建副本；按授权更新分类或补充证据。重复投递先核对已交付结果，不重复发布或创建。

对于缺陷和性能报告，使用以下信息搜索追踪器：

- 精确的错误或崩溃特征
- 产品领域
- 触发条件
- 症状
- 版本或日期窗口
- 怀疑引入回归的提交
- 来源永久链接

选择一种结果：

- 确信重复：特征相同，或者领域、触发条件和症状都相同，或者已确认存在共同原因。
- 可能相关：存在共同原因是合理的，但尚未证明。
- 微弱相似：相似仅停留在表面。
- 无匹配。

对于确信重复的问题，给已有问题补充来源永久链接和一条简短的复发说明。除非配置要求，否则不要重新打开、改标签或重新分配。

对于可能匹配的问题，在结论中将其链接并标注为不确定，不创建任何问题。

已经关闭很久的问题是回归线索，不会自动成为仍然有效的重复问题。

## 8. 决定是否创建

只有用户或已启用自动化的授权明确覆盖创建和失败补偿，且以下条件全部成立时才创建：

1. 分类是缺陷或性能。
2. 行为明确有问题。
3. 问题仍然存在，或尚不知道它已被修复。
4. 去重没有找到确信或可能存在的有效匹配。
5. 原报告和稳定引用通过了预检，且来源并非已存在的目标问题。
6. 追踪器目标字段已解析。
7. 如果结论发布失败，适配器能够执行补偿。

绝不为功能请求、提问、反馈、转交、可能重复、确信重复或已经修复的问题建单。

新问题必须自包含：

- 直接点明领域和症状的标题
- 报告者引文
- 预期行为和实际行为
- 版本和环境，或 `unknown`
- 触发条件和频率
- 原报告的稳定引用及必要访问范围
- 简短的原因追踪结果，并将假设明确标成假设
- 支持时嵌入截图或有代表性的视频帧
- 其他工件的链接
- 配置指定的接收状态和标签

不要把猜测的根因写进标题。

## 9. 发布一条结论

先核对 `source.reply_mode`。`run-output` 在当前会话或实际运行记录中交付完整结论；`origin` 只有在已有发送授权与真实适配能力成立时才外发，否则交付完整草稿并标明未发送。

回写前重新检查原报告，使用保存的原生回复目标恰好发布一条回复。Slack 分支必须使用 `channel=SOURCE_CHANNEL_ID` 和非空 `thread_ts=SOURCE_THREAD_TS`，不改发根消息；其他来源遵循`dev-issue-setup`（各自的原生回复规则）。

保持回复简短：

- 先说结果。
- 存在追踪器问题时，链接已有或新建的问题。
- 需要时说明转交方向或一个缺失事实。
- 最多包含一次获准的负责人提醒。
- 最后恰好放一行标记。

标记契约：

```text
[issue:bug]
[issue:bug] tracker=<已核实的问题链接>
[issue:performance]
[issue:performance] tracker=<已核实的问题链接>
[issue:other]
```

只使用已配置的标记字符串。按`dev-issue-setup`（可信分诊结果）保存实际作者或运行身份、原报告关联和证据版本；复现流程不凭文本标记自行认定可信。

外发后读取同一原报告，验证结论位于保存的原生回复目标；Slack 还核对它在 `SOURCE_THREAD_TS` 之下。运行输出模式核对实际记录可读。交付未确认时不更换目的地重试。

如果本次运行创建了追踪器问题，且能够确认结论未到达约定交付位置，则只对这个本次新建问题使用已经授权的补偿动作。原报告随后消失也不阻止这一范围内的补偿。验证问题已经取消、关闭或删除。若发帖结果未知，先核对可用的返回值与原报告讨论；仍不明确时不重发、不贸然删除，只在运行输出记录工单标识、发送状态与待核对证据。无法验证补偿结果时，同样只在运行输出报告失败。

## 10. 观察一个后续窗口

仅在已经授权的单次运行预算或持续任务范围内，关注已配置的后续窗口，然后停止。采用实际支持的事件、等待或调度能力；没有后台能力时不能宣称已在后台监听。当前会话需要暂停时，把新增恢复点统一保存到 `.agents/dev/changes/<日期-报告>/evidence.md`，不建立流程状态数据库。

- 只回答直接向分诊身份提出的问题。
- 安全时，对追踪器问题应用具体更正。
- 同一次运行不要发出第二个标记。
- 不参与人工协调和旁支闲聊。
- 如果有人要求自动化停止，提前停止。

不要把窗口延长超过一次。新报告应启动新的运行。
