# 回忆工作上下文

**开始或恢复工作之前，重建用户最近的工作上下文，返回紧凑的现状概括和下一步。**

保持紧凑、切题。只读取范围内工作线索所需要的内容，然后停止。

上下文存在两份记录中。自己的聊天历史保存你做过什么、决定过什么；共享记录保存在其他名字之下围绕相同代码发生的一切：用户反复报告的症状、已经上线又被回退的修复，以及生产中仍在发生的错误。第二份记录是 `dev-why`（决策调查）跨源码管理、工单系统、聊天与问题频道、长文档和错误跟踪系统搜索的内容。长期伴随缺陷的功能，其故事多数留在那里，因此不要只从自己的会话记录重建它。

会话记录使用当前宿主明确提供且属于本工作区的位置。先核实实际格式与路径，不猜测其他宿主固定目录；没有日志时，使用当前对话、已有交接笔记与项目记录，并注明证据范围。

1. 先分类，再路由。恢复某一条具体旧会话应使用 `dev-workflow`（会话接续）手册，不是本流程。把习惯变成持久技能应使用 `长期经验整理`。供人阅读的工作总结又是另一项任务。回忆是在行动前，跨最近会话加载工作上下文。如果用户已给出完整状态胶囊，包括路径、分支和改动，就使用它并跳过挖掘。
2. 搜索前固定范围。明确时间窗口：“最近”必须是真实区间，默认最近 7 天；明确用户指出的主题，以及工作区，默认当前活动工作区。未被要求时，绝不读取另一个项目的会话记录。复述搜索范围。绝不悄悄把“全部”改成“最近 N 条”。
3. 跨聊天历史并行检索。按实际工具与任务成本选择并行子代理，默认继承当前可用模型，每个负责语料的一部分。告诉每个子代理：按真实修改时间（`ls -t`）排序候选，不按 UUID 名排序；先检索主题，再只读匹配会话及其有关片段；跳过当前会话和明显噪声，包括子代理、评估和测试会话。每个子代理返回相同结构，每段对应一条会话：主题、用户目标、决定、未完成线索、困难与纠正、产物（PR、工单、分支），每项引用会话 UUID。只有一两条会话时跳过并行，直接搜索。原始会话保留在子代理中，主线程只接收发现。按本地执行支持选择可用的子代理能力和并发量。
4. 主题涉及功能、文件、子系统、区域或缺陷时，搜索共享记录。这是默认动作，不是临时判断，“我在 X 上的工作”也不例外。交给 `dev-why`（决策调查）的各来源调查者，但把问题从“为什么这样构建”改成“目前状态怎样、试过什么却没能持续奏效、用户还在报告什么”。复用其每来源操作手册，让调查与聊天历史挖掘并行，继承其姿态：每个来源一个调查者，无结果也是发现；跳过不可用的 MCP，并说明。把结果合入简报。只有不带具体目标的纯活动回顾，例如“我这周做了什么”，才跳过此步，此时自己的历史和实时状态就是完整答案。
5. 对照实时状态验证。取得挖掘和共享记录检索找到的 PR、分支、工单，用 `git` 和 `gh` 核对。如果答案取决于代理实际做了什么，例如运行了什么工具、读了什么文件、遇到什么错误，就读取完整会话，而不只读裁剪过的本地副本。
6. 按下面的输出契约撰写简报。按工作线索分组，始终围绕指定主题。

## 输出契约

先给状态胶囊，再给各条工作线索的状态，然后列问题，最后给下一步。更深细节放后面或删去。

- **状态胶囊。** 最多 5 个要点。说明这项工作是什么、整体到哪里了。
- **工作线索。** 每条一行，用一个清楚的实际状态说明，例如：`[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]` 或 `[planned, not started]`。状态是简洁的说明，不建立必须驱动流程的状态机。
- **问题。** 最多 5 项，选择反复出现的。包括用户反复报告的症状，以及已上线又回退的修复，让下一次尝试从上一次失败的位置开始。
- **下一步。** 一项最有用、具体的后续动作。

相邻功能或工单除非阻塞当前目标，否则不纳入。当状态胶囊和工作线索超过一屏时，先删细节，不先删工作线索。通过`dev-writing`（清晰写作）撰写简报；聊天发现用 UUID 引用，共享记录发现引用其来源，例如 PR 编号、工单 ID、聊天永久链接、错误跟踪问题；公开输出前脱敏私人上下文。

**回复：** 按上述契约给出简报。
