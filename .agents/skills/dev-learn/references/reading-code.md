# 沿业务路径读代码

模块复杂、跨层或准备二次开发时读取。提纲帮助发现缺口，不要求每项都写成一份文档。

## 入口 → 结果

先用具体输入定位入口，再沿真实调用追踪到可观察结果。每一段说明：输入是什么、谁处理、读写哪些状态、结果怎样交给下一段。遇到事件/队列/回调时继续查真实消费者，不能把“发出事件”当成链路终点。

| 需要弄清的问题 | 主要证据 |
| --- | --- |
| 用户操作怎样触发能力？ | 页面事件、命令注册、路由、公共 API |
| 参数/身份/权限在哪里确定？ | 入口解析、配置、认证、策略实现 |
| 业务规则由谁拥有？ | 领域服务、模型、状态转换、校验位置 |
| 数据在哪里变成持久状态？ | 写入函数、事务、文件/数据库/外部请求 |
| 界面或调用者怎样收到结果？ | 返回值、事件消费者、投影、查询与渲染 |
| 失败时到底发生什么？ | 抛错/返回错误、补偿、重试、日志和用户提示 |

同名函数、类型和接口不证明运行时一定连接。核对实际注册、构造、注入、配置和调用点；测试替身与生产实现分开看。仅在接口看不到真实 provider 时把它标为未解析，而不是补一个“通常如此”的实现。

## 重要的交接

选择与目标有关的部分：

- **状态与生命周期：** 创建者、持有者、销毁者是谁？热重载、取消、重复请求或重连时发生什么？
- **时间与并发：** 哪一步完成才承诺成功？顺序、幂等、事务或最终一致性由哪里保障？
- **持久化：** 哪些是事实源，哪些是可重建索引/缓存？重启与恢复从哪里读？
- **安全与外部依赖：** 权限在哪一层执行？凭据由哪里注入？外部 API 失败由谁报告？
- **扩展：** 已有插件、适配器、事件、配置或接口能否承载需求？代码中可定位的扩展点比泛泛建议“加一层抽象”更有用。

不要把所有项目都强行解释为同一种分层架构；按真实结构命名关系。

## 与文档和测试核对

先列出会改变结论的少量断言，逐条定位代码。现有测试可以帮助发现边界、时序和预期行为，运行它们之前确认环境要求。需要改造时，依据任务风险和项目惯例选择开发与验证方法，保持行为约定可检查。

文档与源码不一致时列出差别、对应修订和影响。如果规范表达的是未来需求，保留为期望行为；如果它自称当前事实但已过时，就纠正或标出待更新。

## 讲解的证据强度

- **源码事实：** 指向读过的文件、符号和修订。
- **运行结果：** 指明实际命令/操作、环境及观察，不把工具不可用写成通过。
- **设计理由：** 指向真实 ADR、issue、注释或用户决定。
- **推断：** 写清哪些证据支持它、哪一步尚未核实。
- **未知：** 明确缺少的实现、配置、资料或访问；继续解释有依据的部分。

复杂关系用一张只表达一个问题的短图；按真实同步/异步、数据/控制关系标注箭头。接口调用不画成持久化，日志记录不画成事实源，成功路径不替代恢复路径。
