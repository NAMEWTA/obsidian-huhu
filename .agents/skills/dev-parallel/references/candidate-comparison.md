# 候选方案比选

先在当前任务记录中列出界定、展开、交叉评审、选择、融合、验证六个活动。记录是导航，不另建状态机；只需要一个确定方案的小任务无需展开候选竞技。

## 阶段 A：界定

每个候选得到相同提示，因此提示本身就是契约。

1. 说明每个候选要产出什么。
2. 制定评分准则，包含 3—6 个具体、可以评分的成功标准，针对*本次*任务。它供阶段 D 的选择者使用，候选只看到任务。
3. 选择实际可用的执行者。默认继承当前模型；用户或项目已配置且宿主支持时，可使用不同模型获得判断差异。先查看工具的真实参数，不假定模型名、推理档位或速度。配置被拒绝时，只使用当前工具明确支持且授权允许的替代能力，并记录变化；无法满足某个席位时记录退出。比较通常至少需要两个候选；只有一个时明确这是单方案审查。设计方向多时按价值增加候选，但不得超过并发上限；生成型任务可使用同一模型多次。没有子智能体能力时顺序形成候选，并说明缺少独立上下文。
4. 给每个候选独立输出位置：可用时使用 git worktree，否则使用 `/tmp/arena-<slug>/candidate-<n>/`；遵循`dev-guardrails`（共享写入隔离）。

## 阶段 B：展开

用宿主实际支持的并发方式启动 N 个独立执行者，能够后台运行时并发推进，每个都收到任务、共享基础资料路径、自身输出路径，以及产出结果和简短理由的指令；理由应列出考虑过的替代方案与否决项。

某个候选没有产出时，继续处理 N−1 个，并记录退出者。

## 阶段 C：交叉评审

阶段 B 的候选停止写入后，启动一位只读评审者。优先使用与生成者不同的可用判断能力，或至少使用独立上下文；仅在用户、项目与宿主支持时选择不同模型。不用虚构的模型标识，也不为得到评审而扩大数据或账户访问。

评审者接收评分准则与按路径标记的候选，逐项评分并给出基础方案建议和理由。它可与阶段 D 中协调者的阅读并行。配置不可用时按已允许的真实能力降级并记录；完全没有独立评审能力时，由协调者独立阅读和打分，明确报告跳过交叉评审，不能宣称已取得独立认可。候选仍在写入时不要启动评审。

## 阶段 D：选择基础方案

选择前，完整阅读每个候选。对照准则逐项评分，不凭整体感觉判断；如果阶段 C 启用了交叉评审，就与其结果比较。对基础方案达成一致，可以确认选择；有分歧，意味着你们之一存在偏向，或准则含糊。决定前阅读双方理由。

选择未来维护者最容易扩展、且不会破坏不变量的基础方案。两个方案难分高下时，根据`dev-guardrails`（精简决策与差异），优先边界更清晰或 API 更小的方案。

## 阶段 E：融合

再次查看每个落选方案，寻找值得移植到基础方案中的部分，通常每个一两项，而不是大部分。遵循`dev-guardrails`（在同一设计中整合需求），手工整合每一处，让结果保持统一认知模型，不机械粘贴。

候选收敛到同一形态，说明一致性很强。记录它，交付共同形态，不必融合。如果差异极大，则阶段 A 定义不足。重新界定并再运行，而不是对分歧取平均。

## 阶段 F：验证

遵循`dev-guardrails`（实际行为证据），像验证任何其他输出一样，验证综合后的产物。如果发现方案竞技没有识别的问题，要么阶段 A 有误，应重新界定并运行；要么某个候选已经发现，而你漏掉了相应融合，应回到阶段 E。不要用表面补丁掩盖它。

## 输出

一个综合后的产物，以及放在旁边的简短综合说明：选了哪个基础方案及原因、交叉评审结论或阶段 C 跳过评审的事实、每处融合及其来源候选、否决了什么以及理由、任何收敛或退出情况，以及验证结果。
