**本分支先形成实施计划，由负责人按计划执行，以证据核对进展。** 用户只要求计划时，计划就是交付物；用户已要求持续实施时，计划完成后继续已授权工作。

## 规划步骤

1. 改动只有一两个文件且方案明显时，用简短行为说明代替多阶段计划，并按当前授权继续。
2. 写作前先用原型解决开放问题。对需要可运行答案的问题使用`dev-build`（原型方法）。保留分支、SHA 和截图，放进附录 A。只有任何运行都无法解决的产品或偏好问题才询问操作人。给出选项，其他已明确部分继续推进。
3. 可用时用独立子智能体探索相关模块，没有时自行按范围调查。返回文件指针、约定、已有验证命令和入口点，避免把整段源码复制进计划。按实际能力与任务复杂度分工，不依赖指定模型或宿主。
4. 把下方骨架复制进计划文件，填完每个占位符。除非用户本次明确指定其他路径，否则统一写入 `.agents/dev/changes/<YYYY-MM-DD-slug>/plan.md`。按本次规模保留相关标题和子块，清楚交代不适用的验证维度，不要求填满固定 Schema。每个实际交付单元一节；使用 PR 时，一个 PR 就是一个拥有独立证据的改动，在这个边界产出可核对结果。在**如何阅读**中指出执行方式：已授权自动合并、交给用户合并的堆叠 PR，或持续项目的分阶段交付；并明确每种方式的终点与授权。具体执行分工见`dev-build`（功能执行）。
5. 正文写成可执行操作指南，解释与参考放附录。每个标题说明任务或发现；使用具体动词、证据与清楚依赖，删掉套话，不建立额外写作工具依赖。
6. 对照下方模板检查计划：每项有交付、真实依赖、唯一负责人和证据；所有文件与命令来自当前项目；不存在虚构路径、悬空占位符或无依据的通过结论。项目已有计划检查命令时运行它并修复实际问题。
7. 给出计划位置、核对结果与剩余决定。用户只要求计划时在这里交付；已有实施授权时按计划继续，不重复要求开始指令。

## 验证选择

**验证。** 验证覆盖本次真实风险；记录适用的静态或单元检查、实际行为及性能证据，不适用的维度说明理由。这句话就是验证规则，每个验证块说明该维度实际证明什么。行为变更需要实际运行证据；纯文字等低风险变更可以直接检查。按风险选择独立验证场景，在实际头提交上操作对应入口；模板给出十个可选场景槽位，按覆盖需要增删，不强制十个智能体。每条场景记录动作、适当证据和通过判据。其中一条是**对照主干的回归通道。** 它在主干和头提交上运行同一个关键场景。若主干没有此功能，通道记录这一事实，并以差异新增的行为及用户等待的最终状态为门禁，不编造主干结果。涉及性能目标或风险时，性能比较必须双侧：主干与头提交都必须产出指定指标。若主干没有此功能，还要隔离差异新增的工作，为该工作和用户等待的端到端状态设置绝对预算。不要对不相同的场景宣称比率。性能块要写清指标、交错执行的探针、先测量的主干基线，以及带有失败数值的规则。交互改变时保存截图或视频；用户明确要求预先审查的，合并前交其审查，否则在持续授权内验证后推进。未改变任何交互的 PR 写 `**审查门禁。** 无。<PR id> 没有审查门禁。`，其下不放复选框。

**操作入口。** 按界面选择当前可用的工具：Web 或桌面网页使用浏览器或现有 UI 驱动，CLI／TUI 使用终端，原生移动端使用项目已有模拟器。触及两个界面时验证两者。缺少操作能力时在附录 C 记录真实限制与可行替代，不把无法执行记为通过。

## 如何阅读

一个复选框是一项工作单元。每项都指出完成勾选所需的证据。嵌套项是上一级的子步骤。只有证据已经存在时才能勾选，可以是文件、日志行、截图、测试运行或 SHA。正文是操作指南；附录用于解释与记录。

本项目按<当前已授权执行方式>推进，操作细节见本技能的`dev-build`（功能执行）。<谁负责合并，哪些任务需用户审查，最终交付环境是什么。>

### 每个 PR 的机制

- [ ] 一次性确定当前可用且已授权的代码托管工具或 CLI；记录项目约定，不要求额外安装特定工具。
- [ ] 已授权创建 PR 时，按实际完成程度使用草稿或就绪状态，目标分支来自项目约定；堆叠子项以父分支为目标。PR 正文说明问题、行为变化、证据与风险。
- [ ] 在面向 PR 的推送前运行一次仓库的 lint 和类型检查。保持钩子开启进行推送。
- [ ] 提交前检查本次差异，删除无关修改、重复逻辑和复述代码的注释；保留必要意图说明。
- [ ] 逐条核对自动或人工审查意见，区分真实问题、既有基线问题、已解决项和不适用项；依据代码与行为作结论。
- [ ] 代码就绪报告和跟进前，核对实际目标主干、补丁及拟落地结果，记录当前基线。修复轮次保持可复现基线；只有冲突、检查要求或相关主干变化使其不足时，按仓库策略和已有授权选择合并或变基。Git 可用时可用 `git merge-tree` 等真实能力检查冲突；不因进入合并阶段就无条件重写分支。

### 每个 PR 的裁决与合并

- [ ] 在代码就绪的实际提交上完成覆盖风险的验证。只有新行为、重设计或大量新差异才扩大复验；变基、冲突解决或小修复只验证受影响范围。验证组合包括项目必要门禁、所选实际场景、适用的性能场景，以及独立规格和代码质量检查。负责人核对实际证据，不轻信 PR 正文。
- [ ] 对每条发现判断是否阻塞当前验收。对照主干场景在主干也失败时记录基线问题，不能直接归因给本变更。新提交重新核对证据适用性；差异未变也要确认运行环境和集成关系没有改变。
