# 计划与切片模板

## 最小计划

```markdown
# <需求名称>实施计划

目标：<与规格一致的可检查结果>
规格：<链接>
交付点：<本地完成 / 推送 / PR / 指定环境上线，依据用户授权>

| 切片 | 完成后的行为 | 真正依赖 | 所有者与边界 | 完成证据 |
| --- | --- | --- | --- | --- |
| 01 <名称> | <可演示结果> | 无 | <模块或文件> | <运行或观察入口> |
| 02 <名称> | <可演示结果> | 01 的 <产物> | <模块或文件> | <运行或观察入口> |

## 顺序与并行
<哪些可以并行，哪个共享契约需要先确定，谁负责整合>

## 未定部分
<还需要调查什么，以及它只阻塞哪些切片>

## 完成边界
<最终整合验证、交付状态、已知限制>
```

只有切片足够大或需要分工时才建立独立任务文件。

## 单个切片

```markdown
# <NN> <切片名称>

规格：<规格中的相关行为>
交付：<从用户视角描述的完整结果>
依赖：<真实阻塞项及所需产物；无则写无>
边界：<唯一所有者、涉及模块、明确不做>
当前代码指针：<路径 / 符号 / 观察提交；实施时复核>

## 验收
- [ ] <可观察条件>
- [ ] <重要边界>

## 完成证据
<各阶段应运行的命令或场景，包含基线、必要的失败证据和最终结果位置；不要预填“通过”>
```

## 垂直与横向

“数据库表全部建好”“全部 API 完成”“全部页面完成”不能让用户体验一个完整能力，通常不是独立功能切片。

“用户创建一条任务，退出重开后还能看到它”贯穿输入、业务、存储与展示，是一个垂直切片。后续可分别扩展“编辑任务”“完成与撤销”“筛选任务”。

公共依赖不一定要单独出一项。若基础调整很小、只有一个调用者，可以并入第一个完整切片。只有实际阻塞多个切片且可独立交付的工作才单列。

## 任务图与工作前沿

假设 A 交付领域契约，B 和 C 各自依赖 A，D 依赖 B 与 C：

- 起初只有 A 可执行。
- A 完成后 B、C 可以并行，且各有独立写入边界。
- B 先完成时，不必让负责 C 的代理停下来等汇报；D 仍等待 C。
- 两者真实产物整合后，D 执行完整场景验证。

“代理说完成”不自动解除依赖；以实际可读的产物和验证为依据。

## 跨仓库机械重构

先说明为什么不存在能独立落地的垂直切片。按实际约束选择：

- 要求逐批可运行：提供有期限的迁移桥接，迁完全部消费者后删除。
- 允许整体替换：在整合分支完成所有消费者迁移，一次验证新契约。

对于后一种，不把临时无法运行的中间点标为已交付，也不为了表面上每一步通过而长期保存两套接口。

## 持久化最小集

规格与计划说明目标；进度说明已经发生什么；证据说明如何知道结果。用链接连接它们。不要复制同一段验收条件到多个互相独立的真相源，不建立强制状态迁移图。
