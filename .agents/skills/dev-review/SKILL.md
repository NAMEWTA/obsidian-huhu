# 交付审查

使用规格与规范两轴独立审查。代码可以遵守全部规范却实现错需求，也可以实现需求却破坏项目约定；一种通过不能掩盖另一种失败。

通过对抗审查与影响范围调查补充行为证据：对能运行验证的缺陷亲自重现，不靠听起来可信的风险列表下结论。

审查目标、规格、项目规范与实际行为，不因实现采用某种开发方法就默认通过或失败。已经授权修复时，按缺陷性质选择回归测试先行、真实运行复现或直接修正，再复核结果；不要求为已充分验证的改动补做形式化过程。

## 固定审查范围

明确基准、目标提交及是否包含工作树。优先采用用户指定的 commit / branch / tag；没有指定时，从 PR、当前任务或默认分支确定合理基准并说明。确实无法确定才询问。

先确认引用存在。比较已提交分支时通常使用 `git diff <base>...HEAD`，同时检查相关提交；工作树审查额外包含 staged、unstaged 和本次新增文件。不要漏掉未跟踪文件，也不要把他人已有改动混入本次范围。

空 diff 只表示这个比较没有改动，检查是否基准或工作树范围选错，不能直接宣称完成审查。

## 找到契约与规则

读取用户指定的 issue / spec、后续讨论、已确认的范围变更，以及当前代码。找不到正式规格时以本次明确请求为契约并说明证据限制，不捏造要求。

规范来源包括相关 `AGENTS.md`、`CONTRIBUTING.md`、编码约定和模块内规则。工具已经稳定检查的格式问题交给工具；人工审查聚焦语义、设计与遗漏。

## 分开执行两轴

**规格轴**检查：

- 要求是否全部实现，包括重要边界和失败行为。
- 代码实现的是否是用户真正要求的行为。
- 是否增加未要求的功能、兼容层、迁移或交互。
- 声称完成的运行、UI、存储或部署结果是否有对应证据。

**规范轴**检查：

- 是否违反明确项目规则，给出具体规则位置。
- 模块边界、状态所有权、数据约束、错误处理是否与项目约定一致。
- 当前改动是否引入有实际代价的设计问题。

采用 [审查基线](references/review-baseline.md) 作为启发式，不把个人审美当硬性违规。项目已经明确采用的模式优先。

有独立代理时将两轴并行交给不同上下文，分别提供契约、规则、基准和目标；否则顺序审查，仍分别记录。不给审查者预设结论。

## 追踪差异之外的影响

重要行为变更要跟到调用者、持久化格式、外部协议、异步时序、权限和部署配置。符号搜索看不到的消费者尤其值得检查。

找到决定安全性的关键事实，例如“这次删除只作用于可重建缓存”。能用小型探针、真实调用或应用操作证实的，实际运行；查看真实依赖版本和本地补丁，不凭 API 名字猜行为。

缺陷报告写明预期、实际、触发条件、影响及证据。运行证据、直接代码证据、未证实的假设分开；无法运行时明确限制，不把假设写成已确认故障。多个发现若共享同一根因，合并。

## 给出可行动结果

分别输出“规格”和“规范”结果。在每个轴内按影响排序，引用具体代码和对应要求。启发式建议明确标注为判断，不与确定违规混在一起。

再简述验证证据、已排除的关键风险，以及未验证部分。没有发现也是有效结果，但不能表述成对未执行路径的保证。可用 [报告模板](references/review-report.md) 保持证据完整。

只要求审查时交付报告；已经授权修复时，修复确认问题并复核受影响部分。每轮新的代码变更需要与原结论重新对应。

需要保存的审查结果写在 `.agents/dev/changes/<YYYY-MM-DD-slug>/review.md`，运行输出引用 `evidence.md`。小审查直接在当前任务记录即可，不生成空报告。
