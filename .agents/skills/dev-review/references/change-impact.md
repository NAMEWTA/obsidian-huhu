# 影响范围

在交付前找出改动会在其他地方破坏什么。用于“X 的影响范围”“这可能破坏什么”，或审查一个你暂时不放心的小差异。

与 `模块探索`、`决策调查` 配合。`模块探索` 说明代码做什么，`决策调查` 说明为什么采用这种形态，影响范围说明它会在其他地方破坏什么。

工作不是罗列调用者。智能体一秒就能搜索到它们。工作是找到搜索显示不出的破坏。

## 不要相信自己的说明

一份听起来合理的影响范围说明毫无价值，无论真假都读起来很有说服力。所以不要只交还说明。找出整件事依赖的一两个事实，运行代码证明它们。

### 你有多确定

对改动安全性依赖的每个事实，在成本低廉的前提下尽量沿下列清单推进，并说明停在哪一步。

1. 你说它如此。单独毫无价值。
2. 你指出了对应代码行。真实的 `file:line`，或库自身源码。
3. 你展示了坏情况不可能发生。逐步走过失败路径，它无法到达。
4. 你运行过它。一个调用真实代码的脚本或测试，若你的判断错误会明确失败。
5. 你在运行中的应用里复现过它。

第 4 步通常只需一个小脚本：导入应用实际交付的同一个库，调用你担心的精确函数。

## 步骤

1. 阅读改动。差异、新增修改删除的符号，以及现在行为有何不同，包括差异未直接说明的部分。使用 `决策调查` 第 2 步获取 PR 和提交。
2. 找出它之所以安全的关键事实。大多数看起来危险的改动之所以安全，是因为一个事实，例如“这个调用只丢弃已经失效的缓存条目，没有其他行为”。找出该事实。若成立，大部分风险情形会一起排除。把时间花在这里，不要写很长的可能性列表。
3. 查看搜索到不了的地方。阅读所调用库的源码，检查锁定版本和本地补丁。弄清什么时候运行：微任务、卸载与清理、Solid 与 React 的区别。跟进符号搜索遗漏的内容：API 返回的 JSON、数据库列、线格式、读取同一组字节的另一种语言、功能开关、再往下游三跳的代码。
4. 诚实描述每项风险。给出真实的发生可能性与发生代价。保留已确认的风险。把已检查并排除的另列一组。规则与 `决策调查` 相同：引用真实 `file:line`，搜索无结果也是答案，绝不编造调用者或 API。
5. 证明关键事实。编写运行真实代码的脚本或测试，运行，并贴出发生了什么。
6. 对大型或范围很广的改动，按 `方案比选` 运行。向多个模型提出同一问题，并合并答案。不同模型会抓住不同的真实缺陷。

## 交付内容

- **它做什么。** 改变了什么，包括不显然的部分。
- **它之所以安全的关键事实。** 陈述事实，说明推进到哪一步，并展示证据。无法证明就写未证实。
- **风险。** 每项指出如何破坏、`file:line`、可能性与严重性，以及检查方法。重要风险贴出证据。
- **已排除。** 检查过什么，为什么没问题。
- **合并前。** 能捕获真实缺陷的最便宜测试或复现，包括你编写的脚本。

用 `清晰写作` 整理文字，引用真实代码，对外发布前移除私人信息。

**回复：** 上述说明，其中关键安全事实要么已证明，要么标为未证实。
