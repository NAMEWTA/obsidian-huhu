# 审查基线

下列基线属于设计启发式。用“存在某种问题的迹象”描述，除非已经直接违反明确项目规范。项目采用的既有模式优先；仅凭风格偏好不报缺陷。

| 迹象 | 检查含义 | 若成立，可考虑 |
| --- | --- | --- |
| 命名不明 | 名字不能表达真实职责或数据意义 | 按领域重命名；无法命名时重看设计 |
| 重复逻辑 | 本次变更多处保护同一规则或执行同一行为 | 将共有知识集中，不机械合并偶然相似代码 |
| 过度依赖他方数据 | 一个方法主要操作另一个对象的内部状态 | 将责任移到拥有知识的一方 |
| 数据总成组传递 | 相同参数组合频繁一起出现 | 明确它是否是领域概念 |
| 原始类型掩盖概念 | 任意字符串或数字代替有约束的领域量 | 用合适类型表达实际约束 |
| 重复分支 | 相同类型或状态判定散落各处 | 统一策略、注册表或恰当多态 |
| 一改就散落多处 | 一个逻辑变化需要同步修改大量位置 | 将共同变化的知识聚合 |
| 多个无关修改理由 | 同一模块同时承受多类互不相关变化 | 按实际责任拆分 |
| 推测性泛化 | 接口、选项或扩展点服务于尚不存在的要求 | 删除无真实使用者的复杂度 |
| 长导航链 | 调用者必须穿越多个对象才能完成操作 | 在拥有职责的模块内完成导航 |
| 纯转发中间层 | 新层只将相同参数继续转发 | 删除或赋予真实适配职责 |
| 不合适继承 | 子类忽略或覆盖大部分父类契约 | 考虑组合或重新划定职责 |

## 证据要求

- 规则违反：给出实际规则来源及对应差异。
- 规格偏差：给出要求、当前行为及触发条件。
- 运行缺陷：能运行时给出命令、实际输出、预期输出。
- 设计判断：说明具体维护或行为代价，不写泛泛的“可能不好”。

不要为了证明某个设计建议而写镜像实现的测试。只有真实风险需要运行证据时才构造最小探针。

## 跨边界检查

重要变更还要检查差异外的消费者，包括 API 数据、存储结构、跨语言读取方、取消与卸载时机、权限条件、配置和旧数据。检索不到符号不能证明没有消费者。

找出一个或少数决定安全性的关键事实，实际查证。例如被清理的目录是否只包含可再生缓存。标明证据停在代码推导、运行探针还是完整应用场景。
