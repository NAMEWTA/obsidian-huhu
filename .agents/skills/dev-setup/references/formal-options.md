# 判断并接入形式化验证

形式化检查针对一个明确的高价值属性。它不替代真实行为验证，也不意味着项目无缺陷。先查项目是否已有模型、证明、验证器或对应项目技能，能复用就不另建体系。

## 选择范围

从代码和用户承诺中找一项性质，例如重试不会导致同一副作用重复提交、一个作业不会同时运行两次、解析器拒绝某类非法结构。写清用户损失、输入和状态边界、并发假设及外部依赖。没有重要性质或缺陷代价很低时，不增加形式化工作。

## 选择工具与映射

优先项目已有可运行工具。有限状态、代码级验证或证明工具各有范围，不能只画状态图就声称做过模型检查。每个变量、动作与原子性假设都要映射到当前代码。模型独有的简化和未覆盖行为单列。

当前已有专门形式化技能时可以选用；本方法不依赖它。没有时，在已授权范围建立最小可运行检查，先选一个可控边界，不为配置任务安装整套无关工具。

## 证明检查可用

运行真实验证器，保留命令、版本、退出结果、覆盖范围及反例。达到时间或状态上限而未穷尽属于未完成。只有编写了模型而未运行时，交付草稿并指出具体限制。

在隔离副本中注入与属性相关的真实实现故障，检查能否失败，再撤掉故障重新验证基线。单独弄坏手工模型只能证明模型检查器会报错，不能证明它能发现真实代码退化。

把反例逐步映射到实现：能发生的是潜在代码缺陷，不能发生的是建模问题，无法判断时保留未决。不能通过删掉属性或削弱边界让检查变绿。

## 形成项目本地入口

在用户指定技能源中创建标准 `SKILL.md`，带齐运行所需的本地模型、配置、脚本和说明。记录属性、假设、代码映射、精确执行方式、证据位置、反例阅读与维护方法。安装仍使用 `.agents/skills/`。

后续代码、接口或并发语义变化时，重新核对映射和假设，再运行检查。维护文档不能把产品回归写成新正常行为。交付必须区分已证明、反例、受阻和未覆盖，不把本次配置选择当作已经完成证明。
