# 深化任务并改写请求

把投入聚焦到更好的问题、材料、方法和证据。用户已有目标与范围是边界，不靠增加功能、交付物或流程数量制造深度。

## 四个问题

读取[完整四问](references/deepen-task.md)，依次说明：

1. 顶尖专业人士会做、而当前请求尚未要求的关键工作是什么？
2. 应从哪些最原始材料开始，而不是只读他人已经消化的摘要？
3. 需要哪些具体方法与工具，它们各自解决什么问题？
4. 除了你与用户的主观判断，什么独立证据能说明结果正确？

把每项落到当前任务。调试可能需要失败输入与日志，研究可能需要原始论文和数据，设计可能需要真实用户任务与界面约束。不要假定材料存在；标明已提供、可取得和缺失项。只写实际可用或需明确接入的工具，不杜撰命令。

## 改写与交付

四问之后给出一份可直接使用的完整提示词，可按[提示词骨架](assets/request.md)组织。写明目标、范围、材料、方法、证据与交付，删去不适用栏目。保留用户原本强调的限制和授权。

产品方向、审美偏好、取舍预算等属于用户的选择，保持开放。能通过读取和运行查明的事实写成调查动作，不要求用户代为查明。不把调查建议当成已经批准的新功能。

用户只要求改写时交付提示词。交付四问答案、改写后提示词，以及真正留给用户的选择；同时要求执行时，把这些结果交回当前开发任务继续，不重建已明确的规格、计划或基线，也不重复询问是否开始。

## 交给后续执行

已有流程适用就复用。复杂且没有更窄方法合适时，读取`dev-workflow`（定制执行流程），把已深化的请求形成可审查路径。它保留界定、设计、假设循环、证据和整体验证的完整方法，由当前执行者沿同一目标使用；仅因任务规模大或用户暂时离开，不必重新设计流程。

重要决定按`dev-workflow`（决策证据方法）记录，默认使用项目 Markdown 或`dev-workflow`（记录模板）。可选 TSV 格式与本地追加工具只在该方法的相应分支使用，不是前置要求。只要求规划时交付流程；已有实施授权时由 `dev-workflow` 或已明确切片的 `dev-build` 持续推进。阶段调用沿用同一任务与记录，不重复启动已完成工作。
