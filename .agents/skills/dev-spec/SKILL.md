# 开发规格

把已有共识整理成可以独立交给实施者的规格。采用综合式写法：以用户问题、目标行为和决定为主，不重新进行一轮已经完成的访谈。

用规格说明意图、边界与验收条件。后续可按任务采用 TDD、实现后行为验证或组合方式；规格服务于判断结果，不代替实际验证。

## 建立规格依据

1. 读取完整来源和已有共识。issue 包括后续讨论；PR 包括当前差距，不把“完成已有 PR”误写成从零重做。
2. 检查相关代码、领域词汇和既有 ADR。找出行为已经存在、与需求冲突、或目前只是假设的部分。
3. 用一句话说明用户问题，再说明期望体验。所有要求要能追溯到用户意图、已确认决策，或明确标注的必要推导。

从已有上下文综合；只在发现影响范围、权限、数据或交付的实际冲突时补问。可由代码或运行查到的事实自行解决。

## 写行为契约

使用 [规格模板](references/spec-template.md)，按需求删去不适用部分。通常包括：

- 问题与预期效果。
- 用户故事或使用场景，覆盖实际参与者、主要路径及重要边界。
- 目标行为与验收标准，每项说明输入或条件，以及可观察结果。
- 实现决定：模块职责、接口语义、数据生命周期、关键不变量与取舍。
- 验证决定：在哪个真实入口验证、必要的检查、完成证据。
- 范围之外、待决问题、相关来源。

用户故事要完整覆盖本次需求，不为长度填充。验收应具体到能判断结果，避免“完善”“优化”“正常运行”作为唯一标准。

对于行为保留型重构，明确必须保持的语义与允许改变的结构。对于重新设计，直接写新契约和明确放弃的旧行为；是否兼容由本次需求决定。

## 分开目标与现状

规格中的目标行为是本次开发契约；当前代码只是现状证据。两者冲突时记录差异，不用当前实现否定已确认的新要求，也不把未来目标描述成已经实现。

语义契约优先描述领域概念、接口和结果。当前代码指针单列在“现状证据”：相对路径、符号、观察日期或提交，读取时核对最新代码。行号可以帮助一次性审查，不作为唯一长期定位。

原型里确有比文字更精确的状态、类型或数据形状时，保留最小决策片段并说明来源；不要把整个试验原型当成正式实现方案。

## 选择验证入口

沿用项目既有、能够覆盖真实行为的验证入口，优先较高层的稳定接口。通常一个覆盖完整场景的入口，比很多锁死实现细节的检查更有价值。

明确哪些证据需要运行应用、调用 API、操作 CLI 或打开页面。静态检查证明的内容单独写明；它不能替代用户可观察行为。简单、低风险文档或样式修改可以用直接检查与预览，测试按真实风险决定。

UI 需求写清主要状态、交互、布局约束及参考依据；部署需求写明目标环境、版本和可验证上线结果。具体设计与执行步骤可以后续展开，不把未知细节伪装成定案。

## 保存与交接

先查阅已有规格并保留引用；新增规格统一写入 `.agents/dev/changes/<YYYY-MM-DD-slug>/spec.md`，并在已有 `brief.md` 中引用。小改动只需一份简短规格，不强制多个文件。

只有用户已授权发布到 issue tracker 时才发布；否则本地 Markdown 就是交接物。一次发布使用同一规格引用，避免本地与远端各自成为不同契约。

交接时说明范围、关键决定、验收入口，以及仍阻塞的决定。大需求可继续用 `dev-plan` 拆分，已有充分计划的需求可进入 `dev-build`。两者均为可选，本技能无需其他技能即可完成规格。

## 本地完整方法

- [规格综合方法](references/specification-method.md)：完整问题、方案、用户故事、实现决定、验证决定、范围和原型例外。
- `dev-intake`（实现简报与示例）：完整模板、缺陷示例、增强示例、已有 PR 的差距示例，以及反例。
- `dev-plan`（本地工作记录）：规格、任务、依赖和问题答案的轻量保存约定。

这些资源随本技能安装。前文的[规格模板](references/spec-template.md)是日常填写入口；完整方法用于检查是否遗漏行为或边界。
