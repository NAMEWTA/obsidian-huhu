# 开发进展

先让用户知道发生了什么、证据支持到哪里，以及还有哪些决定属于他们。根据请求选择一种交付，不把“查看进展”扩成继续开发或发布通知。

## 选择交付

| 请求 | 阅读资料 | 完成条件 |
| --- | --- | --- |
| 跟上本次对话进展、梳理待决事项 | [完整进展回顾方法](references/status-report.md) | 每项结果有真实状态，每个待决事项在回复中有足够依据 |
| 回顾指定时间或主题，证据分散在多次会话与项目记录 | `dev-learn`（完整背景取证） 与[来源资料](references/history-index.md)，再按进展回顾方法组织报告 | 明确时间与项目范围，核对历史产物的现状，给出来源与证据缺口；只汇报，不接管实施 |
| 用短视频说明变化 | [完整视频方法](references/status-video.md) 与 [分镜模板](assets/storyboard.md) | 真实产物组成视频，字幕与停留时间经过成片检查 |

## 共同规则

1. 回顾范围从本次请求之前用户最后一条消息开始；通知和子智能体输出不算用户消息。用户指定时间或任务范围时按其范围。仍未解决的旧待决事项也列入。
2. 数字、PR 状态、测试结果和截图必须来自可读取的证据。状态变化较快时做只读核验；无法核验就写未知或尚未检查。
3. 待决事项只包含用户必须承担的决定、缺失授权或访问条件。已有授权下自己能继续处理的工作单列，不伪装成用户待办。
4. 普通回顾这一动作只读，不为补齐汇报运行应用、改文件或启动检查。用户在已授权工作中追问状态时，简短汇报后继续原任务，除非用户明确要求暂停或停止；独立的状态请求不启动新实施。视频分支只为该请求生成独立产物，避免改动目标仓库。
5. 没有截图就说明缺失，不生成假截图。没有视频渲染或视觉检查能力就如实交付受限结果，不称视频已验证。

表达遵循 `dev-learn`（通俗重述方法），只借用其中的清晰表达，不把回顾任务替换为重述上一条回复。

## 后续需要操作界面时

用户明确要求新建按钮、仪表盘或 webhook 服务时，将它作为实现任务交给已安装的 `dev-build`。需要构建时调用`dev-build`（完整操作界面方法）及`dev-build`（接口约定模板）继续已授权的构建；普通进展回顾不进入该流程。构建界面不自动授予按钮背后的合并、部署、删除、消息或定时任务权限。

交付前按 [进展记录模板](assets/status.md) 检查遗漏。模板是写作辅助，不要求为每次短回顾创建文件。

用户要求保存本次回顾时，新增简报、分镜和产物清单统一放在 `.agents/dev/changes/<日期-主题>/status/`；已有证据按真实位置引用。视频的最终交付位置按用户本次要求处理，普通状态答复无需落盘。
