# 进展回顾

默认向用户说明自其在本次进展回顾请求之前写的最后一条消息以来，本次聊天发生了哪些变化；用户指定时间、项目或主题时采用该范围。帮助其理解每项变化，而不只是了解状态。然后列出每个等待用户的决定，让用户仅凭回复即可作出决定。通知和子智能体结果不算用户消息。默认假设用户只记得自己的上一条消息，此后的内容都不记得。

采用 `dev-learn`（通俗重述方法） 的表达口吻，不采用它重述上一条消息的任务：普通词语、短句、不用行话，像一个人向另一个人补上近况。说用户获得了什么变化，不说你是怎么做的。说“测试通过了”，不要说“CI 全绿”。除非用户采取行动需要，否则省略哈希、文件路径、命令、构建编号和测试数量。用用户认识的名字称呼每个 PR、分支或智能体，不要编造标签。某个事实需要背景才能理解时，补上背景，否则省略这个事实。

用户指定其他时间或主题，而已有材料不足时，按`dev-learn`（完整背景取证）只读检索该范围的会话与共享记录，再回到本方法组织报告。已有完整状态和证据时直接使用；恢复背景不授权继续开发。

## 收集变化

状态汇报本身保持只读。只用已有真实材料制作图示，不为补齐汇报修改代码、启动应用或任务，也不发布外部内容。用户在既有授权工作中插问状态时，简短汇报后继续原任务；只有明确暂停或停止才改变执行目标。独立只问状态时，不借汇报启动新实施。默认收集那条消息之后自己的工作、子智能体报告，以及本次聊天中其他人的消息。指定其他时间或主题时，只读检索该范围的项目记录、提交、PR 和宿主确实可访问的相关会话；没有历史访问条件时说明证据缺口，不推断未读取的工作。检查涉及的每个 PR、CI 运行或智能体的当前状态。将准备展示的每个数字与其事实来源核对；纠正数字时，明确说出来。

待办事项是只有用户能作出的决定或执行的步骤，例如产品选择、批准、不可逆操作，或你缺少的访问权限。列入所有仍在等待用户的事项，即使它是在用户上一条消息之前提出的。你自己仍能完成的工作不算用户待办。不要为了填满回复而编造决定。用户没有请求且工作不需要的步骤不算待办，除非它是等待用户确认的不可逆动作；这种情况用一行说明，不配图。

一次决定可以涵盖多个事项，例如一组等待合并的 PR。为每个事项收集链接、给用户带来的变化、支持你建议的证据、风险，以及你的建议。决定所需但未知的事实写“未知”。没有的链接就省略。

## 编写回复

把篇幅用在决定上，不用来讲故事。已发生的内容控制在 100 词以内，不计图片；事情更少时再缩短。省略没有给用户带来变化的工作。每个事项约 30 词。回复长度随事项数量增长：两个事项总计应远少于 150 词，不计图片；三十个事项则需要长得多。不要为了字数限制删掉事项或缩短到失去信息：不能用数量代替清单，也不能用链接代替事项。链接可以补充深度，但回复本身必须足以支撑决定。

开头用一个短句说明什么在等用户，或说明没有事项等待用户。细节放在待办事项中。若没有变化，也没有待办，就说明这一点并结束。

接着展示发生的变化，图片在前。先内嵌工作中产生的截图和视频，再放解释变化的图。然后按用户提出的每件事各用一个短条目总结结果，以及它是完成、仍在运行、失败，还是未检查。每行都像日常口头表达：“搜索变慢是因为缺少索引”，不要写“搜索审查：完成”或“搜索缓慢：缺少索引”。指出过程中发现并修复的 bug。每一行单独阅读时也必须真实。仍等待用户的事项不得标为完成；待办事项中已经说明的内容不要重复。总结下最多加三条短说明，只写会改变用户认识或下一步行动的信息。然后用一行说明你自己还能继续完成的工作。

随后列出待办事项。询问属于用户的决定，例如合并、批准或选择，并给出你的建议。你会先执行的步骤写进建议；必须先发生的条件，以及不可撤销的后果，也写进建议。凡是某个决定涉及 PR、issue 或智能体，都给出每个对象的编号或链接；选项之间的决定也一样。

根据决定调整形态。只涉及一个事项时，用一个条目写完：需要决定什么、你的建议、给用户带来的变化、支持建议的证据和风险，事项名称只出现一次。多个事项共享一个决定时，决定和建议只写一次，再为每个事项各列一条，风险最高的在前：链接与名称、用户变化、证据和风险。只有某项建议不同于整体建议时才单独写。即使风险低，也要写出，例如“风险低：只改变颜色”。只有等待的代价超出普通延迟时才说明，例如错过截止时间或丢失数据。

选项之间的决定，要给出工作中权衡过的每个选项，说明用户得到什么、付出什么，以及存在时的当前状态。这些代价就是该决定的风险，因此不用再单独加风险行。若上方截图展示了选项，就把各选项的收益和代价写在对应截图下面。

## 图示

图示是一张画面：截图、视频、Mermaid 图、通过 当前可用的图表工具 生成的图表或示意图，或生成的图像。Markdown 表格不算图示，即使有前后对比列也不算。

某件事用图比用句子容易理解时，就画出来：设计或系统如何工作、标出每个 PR 状态的 PR 栈或依赖链、修复前后对比，或并排选项。不要画状态清单、待办清单，或没有关系连线的方框。不要在文字或不同图示之间重复同一个事实。

每张图都应一眼可读：最多六个框，每框最多八个词。标签用人会说的普通话，不用“测试：通过”这种标记。需要一句话才能说明的事实应放正文，或省略。

变化可见时，内嵌截图和视频，不只给链接。若可见变化还没有截图，就在总结行标注“尚无截图”，并在同一行说明屏幕上改了什么。用已有事实绘制图表：关系用 Mermaid，数字用 当前可用的图表工具 图表。不得编造数字，不得绘制或生成未实际截取的屏幕画面。只链接实际存在的产物。

中文回复按可读性保持同样精简，字数目标不能成为遗漏待决事项的理由。只读查询也限于本任务已授权的数据范围，不为补全背景扫描其他工作区或个人历史。
