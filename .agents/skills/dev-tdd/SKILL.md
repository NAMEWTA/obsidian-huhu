# 测试驱动开发

先确定需要保护的用户行为和公共接口，再让一个会因该行为尚未满足而失败的测试驱动一个最小实现。以真实契约评估测试价值，保持测试能够经受内部重构。

这是一种按任务选择的开发方法。用户已经指定方法时遵循其目标；没有指定时，根据风险、反馈速度和接口是否稳定判断是否采用，不把测试先行变成所有工作的门禁。

## 选择当前任务的流程

默认的缺陷回归路径采用[完整六步回归修复](references/bug-regression-tdd.md)：用户要求失败测试或回归测试，或缺陷有明显且低成本的本地测试目标时，从最小复现开始，保留修复前失败与修复后通过的证据。只有新功能或持续实施已明确选择测试先行时，才补充[逐切片红绿方法](references/tdd-method.md)，不再重走一轮缺陷流程。

测试需要大范围搭建环境、脆弱模拟或不相称的成本时，按回归修复方法选择最接近目标的可执行检查，不为了方法标签创建坏测试。两种方法都保持阶段原义，不把重构、环境建设或无关覆盖混入当前红绿切片。

只为已有正确行为补集成测试时，按当前实施任务或 `dev-build` 完成测试变更，不为制造红灯修改产品行为。需要检验测试敏感性时，在隔离副本中引入对应故障并撤回，记录检查确实能捕获退化。

本包只维护测试先行方法及测试设计、替身示例。类型约束由 `dev-guardrails`、架构由 `dev-architecture`、独立审查由 `dev-review` 负责；按当前需要读取其入口，不复制它们的正文，返回后继续当前切片。

## 明确当前切片

读取当前要求、相关代码、既有测试、领域词汇与 ADR。写清公共接口、一个可观察行为和独立来源的期望结果。沿用已经确认的边界与授权；关键边界仍不清楚且会改变目标时再询问。小任务用几句话即可，不强制建立完整规格目录。

需要调整接口形状时读 `dev-architecture`（模块设计）；依赖隔离与替身选择读 `dev-architecture`（依赖与加深），存在真正结构取舍时再读 `dev-architecture`（替代设计）。

## 运行一个完整循环

按已选的[缺陷回归方法](references/bug-regression-tdd.md)或[逐切片方法](references/tdd-method.md)推进，不把两条路线串成重复工作。每次只选一个行为，观察测试因目标行为失败，再完成使它通过的最小实现。确认失败不是语法错误、无关环境问题或错写的期望值。不要一次预写全部测试，也不提前添加未来能力。

测试的设计与示例见 [好测试与坏测试](references/behavior-tests.md)，外部系统替身见 [何时使用模拟](references/test-doubles.md)。用 `dev-guardrails`（行为契约检查） 判断测试是否会捕获错误行为、又能经受内部重组。

## 复核结果与结构

当前行为通过后，再选下一个有价值的切片。结构改善放入独立的 `dev-review`（两轴审查） 阶段，并使用既有行为证据约束重构；保持实现循环中的反馈紧凑。

应用、UI、CLI 或部署结果还需要 `dev-guardrails`（真实对象证据）：通过测试不自动证明当前环境已经正确启动、发布或产生用户期望的副作用。按风险运行必要路径，检查充分后停止重复验证。

输出实现的行为、测试接口、观察到的失败与通过结果、当前制品以及尚未覆盖的风险。需要持久化时统一写入 `.agents/dev/changes/<日期-主题>/evidence.md`。测试和任务产物留在目标项目，不能写进本技能安装目录。

工具、授权与持续工作的具体约定见 `dev-workflow`（本地执行支持）。全部资源可从 [资料索引](references/method-index.md) 按需选择，按当前任务读取。
