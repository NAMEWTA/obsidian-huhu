# 用 TDD 修复缺陷

用户明确要求 TDD、失败测试或回归测试，或缺陷具有明显、低成本的本地测试目标时使用。测试路径不明确或成本不相称时，采用下方替代检查并说明证据范围。

修复测试路径明确且成本低的缺陷时，在修改产品代码之前，把错误行为变成可执行的检查。目标是一条聚焦的回归测试：修复前失败，修复后通过。

不切实际时，不要强行测试。如果可用测试需要大范围搭建验证框架、脆弱的模拟、缓慢的端到端基础设施、仅生产环境存在的状态、含糊的复现步骤，或大规模修改无关夹具，就跳过新增测试，改用最接近目标且有用的验证。

## 工作流程

1. **理解缺陷。** 明确预期行为、当前行为、受影响路径和最小可观察复现。
2. **选择最窄的可执行检查。** 优先使用该代码路径已有的、最接近它的单元、组件、集成或回归测试。如果没有明显可行的测试路径，不要仅为了满足流程而从零创建一套。
3. **先写失败测试。** 添加本来能够抓到这个缺陷的最小聚焦测试。测试应编码预期行为，而非照抄当前实现。
4. **修复之前运行新测试。** 确认它因预期原因失败。如果通过，或因无关原因失败，先修正测试或复现，再编辑实现。
5. **修复缺陷。** 做满足预期行为的最小产品改动，同时保留相邻契约。
6. **重新运行回归测试。** 确认测试现在通过。

## 失败测试不切实际时

改用最接近目标的可执行回归检查：定向脚本、手动复现命令、浏览器自动化、快照对比、日志断言，或聚焦的集成检查。

宁可不新增测试，也不要坏测试。坏测试主要在测试模拟对象，编码当前实现细节，依赖时序或无关全局状态，为小修复要求昂贵基础设施，或在证明修复后立刻就会被删除。

## 护栏

- 不要仅为了匹配错误实现而修改测试。
- 除非预期行为确实改变且原因清楚，否则不要弱化既有断言。
- 回归测试聚焦当前缺陷。避免大范围修改夹具或扩展无关覆盖。
- 缺陷不稳定时，尽可能让测试确定性运行，并记录正在固定的信号。
- 缺陷暴露出更广泛的失败类别时，先落实聚焦的回归路径，再考虑增加相邻覆盖。

## 最终回复

报告证据，而不只是结果：

- 指出修复前失败的测试或可执行检查，以及它产生的失败。
- 指出修复后通过的测试运行，以及执行过的相邻验证。
- 如果无法展示修复前失败的证据，说明原因，并描述实际使用的最接近目标的回归检查。
