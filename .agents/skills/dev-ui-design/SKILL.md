# UI 设计与实现交接

从用户要完成的任务和现有界面开始。交付可实现的视觉与交互约定，以及实际检查过的结果；完整功能开发仍沿用当前任务的负责人和交付目标。

## 按当前问题读材料

| 当前需要 | 本地方法 |
| --- | --- |
| 产品页面、后台、桌面界面或现有交互改造 | [产品 UI 工作流](references/product-ui.md) |
| 建立或补齐设计系统，处理主题、组件状态和视觉一致性 | [设计系统方法](references/design-system.md) |
| 查间距、圆角、文本样式、双层颜色与语义别名的完整表 | [设计变量参考](references/design-tokens.md) |
| 营销、下载、活动或等待名单页面 | [完整落地页设计](references/landing-page-guide.md) |
| 用可运行证据比较尚未确定的方案 | `dev-build`（原型共同约定），再选`dev-build`（界面变体）或`dev-build`（逻辑演示） |
| 保存本次设计决定与验收入口 | [设计记录模板](assets/design.md) |

只读取当前分支及它需要的具体规则。页面改造不要求先创建完整设计系统；一般业务页面不加入营销区块。

## 实施顺序

1. **接入已有需求。** 读取当前 spec 或等价记录，定位用户、入口、动作、数据、例外和完成信号。能从代码、截图和已有决定得到的答案不再提问；只澄清会改变交互、范围或信息结构的缺口。
2. **先复用实际实现。** 查路由、组件、样式变量、图标和字体资源。用户要求与已有设计系统优先；没有既定系统才采用本包完整默认，不强制更换框架或整站换肤。
3. **明确一条可实现路径。** 记录布局、复用组件、适用状态、主题、窄屏、长内容和键盘行为。token 与组件引用真实源码，产品 UI 与营销页的标题字重只采用一个明确约定。
4. **逐区域实现并检查。** 先做关键区域或一条完整路径，实际渲染后修正再扩展。UI 原型只回答已列明的问题，正式交付按项目生产要求实现。
5. **交接结果与缺口。** 按适用视口检查截图、键盘、表单错误、长内容、数据状态与真实链接。营销页同时按完整指南检查 CTA、元数据、分享图、footer 和 390px 布局。给出已验证范围、实现位置和未完成事项。

## 关键约束

- 组件通过语义 token 使用颜色、间距、圆角和命名文本样式；新设计的完整数值与模式见对应参考，不在入口维护另一套表。
- 复用已有设计资产。新建完整组件库时保留完整状态集；局部任务只补当前路径确实需要的状态与变体。
- 真实价格、客户、评价和统计来自用户或可核验来源。缺失事实明确标注，虚构演示说明身份，不用编造素材填满布局。
- 运行和截图是视觉验收证据。缺少渲染、交互或外部文件写入能力时说明缺口，完成可交接规格，不把源码阅读或草图当作实际体验通过。
- 控件有可读语义与可见焦点；状态不只靠颜色表达；动效尊重 reduced motion，并保留最终可读内容。

## 记录

必要的设计决定、实际截图与验收入口写入当前变更的 `design.md` 或等价文件；本套新增资料默认位于 `.agents/dev/changes/<日期-主题>/`。小改动可在已有记录补一节，不为流程填空模板。长期稳定约定只留短说明与真实代码链接，写入 `.agents/dev/notes/`；已有资料按真实位置引用，不复制整套 token 到项目记忆。
