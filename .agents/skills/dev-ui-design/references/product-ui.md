## 从现有产品取证

从真实入口跟踪到结果：入口/路由 → 用户动作 → 组件/表单 → 状态或查询 → 服务请求/数据 → 成功反馈与恢复路径。记下相应文件和符号，先理解这条路径，再改页面布局。

观察相邻页面如何选中、导航、返回、过滤、保存和展示错误。把已有交互当作产品语言；只有能说明用户任务如何改善时才更换它。

列出三类事实：

| 事实 | 证据 | 设计用途 |
|---|---|---|
| 用户正在完成什么 | 需求、反馈、真实操作路径 | 决定主动作和完成信号 |
| 系统已经支持什么 | API、状态、权限、组件 | 避免设计不存在的能力 |
| 当前界面哪里阻碍任务 | 截图、复现、键盘操作 | 将问题变成可验收的行为变化 |

不要把“现代化”“更高级”当作信息架构。若需求只是修改日期组件，就先复用项目的组件库与 token；没有必要重做整个应用壳层。

## 信息结构与交互

先确定主对象、用户动作和重要程度，再选容器。下面是选择依据，不是所有项目必须使用的版式：

| 场景 | 优先考虑 | 需要明确 |
|---|---|---|
| 层级档案、目录、项目 | 可折叠树与内容区 | 节点选中、展开、搜索、空节点、键盘方向键 |
| 同一集合的条目详情 | 保留上下文的侧栏/抽屉，或已有详情路由 | 返回位置、选中态、深链接、未保存更改 |
| 互斥的少量视图/状态 | 语义明确的单选分段控件 | 是否切换视图、过滤数据，还是改变对象状态 |
| 待办完成 | 原位置的状态反馈、撤销入口 | 完成后是否保留、移动、划线；与服务端失败一致 |
| 日期与时间 | 已有可访问日期组件 | 本地化、时区、键盘、范围、无效值和保存格式 |
| 大集合 | 与现有数据层兼容的搜索/过滤/分页或虚拟化 | 加载范围、选择是否跨页、错误重试 |
| 修改重要配置 | 字段级修改、清晰的保存/生效反馈 | 立即生效还是保存后生效、重启要求、恢复原值 |

详情面板需要保留触发点，关闭后把焦点送回合理位置。危险操作要表达实际对象和后果；操作失败保留输入与上下文。不要仅因为“卡片好看”而把密集列表拆成低密度卡片。

## 组件和视觉系统

优先复用项目已安装且版本匹配的组件库。先读 `package.json`、锁文件、组件封装与当前框架。新依赖只有在现有能力无法满足需求时引入，并说明它替代了什么维护成本。不要直接复制一个陌生组件连带整套状态管理或 CSS 基座。

采用以下设计方法：

- 类型、字号、行高、间距和圆角通过已有 token 或有命名的样式复用。
- 新设计没有约定时，采用[设计变量参考](design-tokens.md)的完整尺度与命名样式；建立或维护体系时按[设计系统方法](design-system.md)处理双层颜色、组件状态和基础预览。
- 颜色分为原始 palette 和用途语义（surface、text、border、action、status）。组件使用语义层，主题通过映射切换。
- 内嵌圆角关注外框半径与间距的关系；避免内部元素与外框弧线互相挤压。
- 一套图标使用一致的视觉重量；有既有图标系统就沿用。
- 内容层级优先靠字号、字重、留白和位置表达，颜色只提供辅助。
- 建立新的通用组件时覆盖当前用途需要的状态与变体，不用单次页面修改制造整套未被使用的组件库。

本地默认的字体选择、纯色背景和具体动效是一套明确的风格方向，不是操作系统或所有产品的通用规定。已有项目按其设计系统工作；用户明确选择这套默认风格时完整采用，并在设计记录里说明。

## 状态与可达性

对当前使用路径逐项检查适用状态，不为不存在的场景制造页面：

| 组件/数据状态 | 预期 |
|---|---|
| 初次加载/刷新 | 保留结构与上下文；用与内容匹配的骨架或现有加载模式 |
| 空数据/过滤无结果 | 区分“还未创建”和“条件无结果”，给相关下一步 |
| 校验失败 | 字段附近说明原因与修复方式，保留输入 |
| 服务失败/离线 | 明确失败对象，支持合理重试，避免重复提交 |
| 保存中/已保存 | 按实际请求状态显示，不能提前宣称成功 |
| 禁用/无权限 | 语义与原因明确，不只降低透明度 |
| 键盘与焦点 | 可达、可见、顺序合理；模态/菜单符合组件已有可访问模式 |
| 长内容/放大/窄屏 | 无重要内容裁切、关键操作仍可达，文字可换行 |

采用语义 HTML 或宿主等价控件；图标按钮有可读名称。文字和背景的对比按项目要求与当前可访问性标准检查；不要只凭肉眼断言通过。状态不能只用颜色表达。动效尊重 reduced motion，手势有可用替代；布局变化不要制造跳动和焦点丢失。

## 渐进实现与验收

先完成一个主要任务从入口到结果的薄切片。渲染并走通，再增补其他状态和相邻区域。将检查与验收条件对应起来，而不是事先堆出一套会失败的 UI 测试。

有浏览器/原生工具时，检查项目目标视口、键盘、表单失败、长文案和实际响应。视觉对比时保留同一视口与状态，截图才可比较。没有运行能力就记录具体缺口和可复现步骤，不把设计草图或源码检查标记成实际体验通过。

将“日期框换成现有组件”“点击条目保留列表并开详情”“完成状态与服务失败回退一致”等变化直接对应用户需求。最终证据应让接手者知道哪些行为已实现、如何重现、哪里继续改。
