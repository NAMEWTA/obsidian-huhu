# 真实行为验证

把明确的完成条件变成真实用户路径上的证据。先确定当前版本、目标环境、入口和可观察结果，再驱动应用并核对实际发生了什么。静态审查、类型检查和 CI 只能说明它们观察的内容；本技能负责操作、结果及副作用的验证闭环。

## 选择本次模式

- **验证当前实现**：按下述流程执行本次相关行为，不因一次验收就自动生成长期技能。
- **创建项目验证方法**：项目需要可反复使用的启动、诊断、驱动、证据、清理流程时，完整采用 [创建验证技能](references/verification-authoring.md)，并实际跑通生成结果。
- **维护已有验证方法**：应用、界面或驱动工具变化时，完整采用 [维护验证技能](references/verification-maintenance.md)，覆盖功能图中的每个功能。

仅授权验证时不隐式修改产品代码。发现产品缺陷就记录证据与影响；已有修复授权时可继续修复，再按同一路径重新证明结果。验证脚本和资料的维护遵循其明确编辑范围。

## 完整验证与交付指南

本技能负责真实应用验证。形式化属性检查由 `dev-formal-verify`、TLA+ 结果图由 `dev-statechart`、PR 落地由 `dev-deploy` 负责；按当前需要调用各自入口，明确其检查边界，不以普通测试冒充证明。使用说明可选查阅 `dev-help`。

## 验证当前实现

1. **固定对象与契约。** 记录提交或实际构建、环境、用户路径、前置条件及成功和失败状态。以用户目标、项目约定和当前代码识别真实入口，不用内部 setter 或特设测试端点替代用户操作。
2. **建立可控实例。** 使用项目已有启动和健康检查。检查端口、数据目录、账号权限及实例归属；复用会影响用户的会话前先核实授权。多个验证者不能同时驱动共享状态，无法隔离就串行。
3. **驱动并观察。** 运行本次路径与重要边界，记录动作和结果状态，并核对相关文件、持久化状态、请求或消息等副作用。用户入口不止一个时，清楚区分已执行与尚未执行入口。
4. **解释失败。** 区分产品缺陷、驱动缺口、资料漂移和未满足的前置条件。驱动失败后重新诊断，必要时恢复已知状态再试；不能把健康但卡住的界面当成可用实例。无法到达时写明具体原因与尝试路径，不把跳过写成通过。
5. **收集充分证据。** 使用 `dev-guardrails`（真实对象证据） 与 `dev-guardrails`（行为契约检查） 选择最便宜的充分检查。可重复脚本、命令输出、界面状态与截图须对应同一版本和动作；替代环境证明不了真实目标特有的设置。
6. **清理并回读。** 只停止自己启动的实例、清理本次验证数据与临时脚手架，确认所需证据在清理后仍然存在。不要按进程名杀死未知进程，也不要删除用户原有状态。

发布、外部消息和不可逆副作用按用户已有授权执行。凭据不进入普通证据文件；采用测试模式时实际核对它跳过哪些副作用，不凭 `dry-run` 名称推断安全。

## 建立可维护的功能图

完整参考 [功能图索引](references/feature-map-index.md)、[创建笔记示例](references/feature-map-example.md) 和 [搜索笔记示例](references/feature-search-example.md)。示例展示用户入口、前置条件、驱动动作、预期状态与陷阱，命令只属于示例应用；移植时替换为当前项目真实能力并运行证明。

按功能维护轻量 Markdown，不建立强制状态机或复杂 Schema。项目专用验证包按用户指定位置编写；安装时扁平放入 `.agents/skills/dev-verify-<app>/`。新增运行记录与证据统一放 `.agents/dev/changes/<日期-主题>/evidence.md` 及其明确引用的产物目录，不写入通用技能安装包。

## 交付验证结果

给出实际验证对象、已执行路径、观察结果、产物位置与未覆盖限制。维护模式明确 `clean`、`changed` 或 `blocked`；只有所有约定覆盖都已证实才称完整通过。生成的验证技能从未实际运行时标记草稿，不能当作已经证明可用的交付物。

工具、授权和记录约定见 `dev-workflow`（本地执行支持）。全部资源见 [资料索引](references/method-index.md)。
