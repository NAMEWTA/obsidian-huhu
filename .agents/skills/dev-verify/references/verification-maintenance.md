# 维护验证技能

应用一变，功能图就开始过时。本技能是 [验证方法生成](verification-authoring.md) 生成的技能，或任何带功能图的项目本地验证技能的维护循环。严谨性的单位是功能，而非每句话：从源码覆盖每份功能文件，并实际操作每个功能，不必把每个条目都变成终端步骤。

## 结果

选一种并明确说明：

- **clean**：每个功能都有源码和实际运行覆盖，没有值得交付的修改。不建分支，不开 PR。
- **changed**：按当前授权的交付方式交付已证明的文档、驱动工具或功能图修正，需要 PR 时合并为一个聚焦 PR。
- **blocked**：覆盖未能完成，或已证明的修复无法安全交付。精确说明阻塞原因。

## 编辑范围

只编辑验证技能自己的目录，即 SKILL.md、features/、其拥有的驱动脚本。运行期间不编辑产品代码：功能图描述而应用已不再提供的行为，要么是文档漂移（修图），要么是产品回归（报告，不要在文档中掩盖）。

## 执行

0. **定位目标。** 找到要维护的验证技能：正文有启动、驱动章节和功能图的项目本地技能，通常在 `.agents/skills/dev-verify-*/`。多个候选先按用户项目与当前任务定位，确实无法区分才问；没有现成目标时说明，并按当前授权判断是否使用 [验证方法生成](verification-authoring.md)，不要发明目标。

1. **整理索引。** 读取功能图 README，枚举相邻文件。修复缺失、多余、重复或失效条目。保持轻量，不生成清单系统。

2. **源码波次。** 按功能独立读取源码；有子智能体能力时，在并发上限内每个功能分配独立只读调查，单人或工具不可用时顺序完成全部功能。各自从源码解释“这个用户功能如何工作”，带引用标记疑似文档漂移，返回一份简洁实际验证配方。子智能体不驱动应用、不编辑文件。返回格式为功能摘要 / 源码入口 / 疑似漂移或无 / 一份配方。

3. **协调。** 确保每份功能文件都有返回摘要。把重叠配方合并到尽可能少的应用状态。抽查被引用的漂移，不重新证明干净结论。扫描近期改动，寻找功能图缺失的用户界面；只有具体源码路径才能认定缺失。

4. **实际运行。** 源码看起来干净也必须执行。协调者拥有全部驱动，遵循验证技能自己的启动模型：服务器与 UI 用一个长生命周期实例串行驱动，短生命周期 CLI 每次驱动新建隔离会话，具体由该技能“启动”一节决定，不由此处决定。每个功能至少操作一次，无论出现什么失败，整个过程维持三条不变量：（1）实例发生异常后，没有再次健康检查就不得继续驱动；第一次驱动前诊断，以会话为单位时每个新会话诊断，任何驱动失败后再次诊断；诊断看不到失败时，例如进程健康但 UI 卡住，应重置为已知状态或重新启动，不靠希望。（2）此前记录的证据在每次清理后都存活，要到指定位置确认，不能假定。（3）驱动启动的任何内容都不能超出该驱动有用期存活；失败迭代残留无论会话卡住、退出还是共享都要清理；共享实例清残留，不清实例。由技能漂移导致的诊断失败也属于漂移：在编辑范围内修正，只重启修复使之失效的内容，再重试一次，之后才能标为 `blocked`。功能不可到达时，只有写明具体前置条件（认证、权限、操作系统、外部状态）和尝试过的路径，才能标为 `verified-unreachable`；图未写前置条件就是漂移。分类处理产生的任何驱动修复都必须再次实际驱动后才能交付。最终清理在最后一次驱动之后进行，包括这些再次证明，确保除按技能要求保留的证据外，没有运行内容遗留。

5. **分类处理。** 用户视角描述错误或缺失是文档漂移，修正；行为可用但驱动工具无法驱动，是驱动缺口，修正；驱动修复遵循生成时同样的辅助工具规则，脚本可执行，技能正文写调用方式。应用行为确实损坏，是产品缺口，记录给用户，不放入本 PR。

6. **交付或停止。** changed：先重读每个修改文件，再按授权交付已证明修正；项目要求 PR 时使用一个聚焦 PR，不把直接推送请求改成强制 PR。clean 或 blocked：不开 PR，诚实报告结果与覆盖。

在临时位置保存简洁运行笔记，记录已覆盖功能、不可到达的前置条件、已确认漂移和结果，不提交这些笔记。
