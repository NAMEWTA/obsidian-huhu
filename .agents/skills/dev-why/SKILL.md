# 追溯设计理由

代码说明现在如何运行，不能独自证明作者当时的意图。沿提交、评审、工单、文档和可用运行记录查找理由，明确哪些结论有证据、哪些只是解释。

本次结果是历史理由与约束。当前故障的复现、根因和修复以 `dev-debug` 为主；解释当前机制以 `dev-learn` 为主；核对一段任务过程的决策日志与实际证据以 `dev-workflow` 为主。它们可采用本包调查方法补足背景，复用已有证据，不另开一轮相同调查。

## 调查

1. 理解用户的问题和具体代码目标；模糊时说明最合理的理解，先查现有事实。
2. 建立代码锚点：真实路径、符号、当前版本、关键变更、相关 PR 与工单。新代码状态与历史动机分开。
3. 按[完整调查方法](references/investigation-method.md)识别可用证据来源。在实际能力、访问权限和任务范围内调查；没有某类工具时记录缺口，不假定一定有 Git、远端或公司内部账户。
4. 用[来源索引](references/source-investigation.md)选择对应手册。可并行时，每位调查者负责一个证据类别，按[调查简报](references/investigator-brief.md)返回查询、引文、位置、矛盾与空结果；无并行能力时顺序调查。
5. 用[证据层级](references/evidence-confidence.md)与[综合方法](references/investigation-synthesis.md)整理。保留反证和不同解释，抽查引证，不把多次转述同一材料算成独立支持。
6. 如果调查是为了改代码，交还“保留、改变、避免、风险”的约束，明确哪些需要用户判断。不要用推断出来的历史意图覆盖当前用户目标。

## 事实与未知

直接引文支持的理由可以明确陈述；多条间接证据的结论说明推导；猜测标明替代解释。找不到理由也是有效结果，列出具体搜索范围和未取得的材料。用户问题里自带的假设是候选解释，仍需核查。

若目标是防御性代码，补看[事故与复盘线索](references/incident-investigation.md)。运行指标与上线时间相关不等于因果关系，采样率、保留期限和埋点变化都可能影响结论。

## 持久化

调查者只读检索，不发送消息、不修改工单或远端状态。任务要求留下背景，或结果对后续开发有长期价值时，由协调者使用[调查记录模板](assets/investigation.md)，将新增背景写入 `.agents/dev/notes/context/`，已有背景按真实位置引用。记录理由、范围、代码锚点、证据版本、置信层级与缺口，避免整段复制聊天和敏感遥测。

正式架构决定可转入 decisions；复发错误与恢复经验进入 errors；术语别名进入 glossary。保存当前知识时核实代码引用，历史证据标明时间范围。现有记录冲突时合并和修正，不新建另一个互相矛盾的“最终版”。

本包自带完整调查提示、来源手册与证据规则。需要解释运行机制时可按目标调用链直接阅读，或选用已安装的 dev-learn；本任务本身不自动启动实现或部署。
