# 证据与可信度

当证据来自历史、零散不全且有时互相矛盾时，如何判断可信度，并在告诉用户时避免将它们压成虚假的确定性。代码展示它做什么，不展示它*为什么存在*。原因存在于提交、PR、工单、文档和对话中，这些来源都不完整、有偏向，有时甚至缺失。假装情况并非如此，就会产生听上去自信却误导用户的猜测。

## 可信度层级

输出中的每个主张都必须归入一个层级。层级决定它所在的章节和表述方式。

### 1. 直接证据

明确的文字引证回答了问题：作者实际*写过*且说明原因的内容，而不是“代码做了 X，所以作者一定想要 X”。例如，PR 描述写着“这修复了拥有超过 1000 个条目的用户无法分页的问题”；工单写着“我们增加这个功能，是因为 Acme 客户在安全审查中提出要求”；代码注释写着“// 限制为 100，因为上游 API 会拒绝更大的值”；设计文档写着“我们选择方案 A 而非 B，因为需要跨重启持久化”；或者作者在聊天中说“改用这个方法，因为旧方法在测试中不稳定”。

表述：明确、使用现在时、附引证。“它之所以存在，是因为 X。”

### 2. 相互支持的证据

多个间接证据共同指向一个结论。没有单个来源明确说明，但不同来源呈现的模式使结论很可能成立。例如，PR 标题写着“提升性能”，工单标记为“perf”，周边提交都修改同一条热点路径。或者，与这次变更同时增加的几个测试都使用非常大的输入。或者，作者同一周的其他 PR 都提到同一个事故。

表述：有把握，但明确说明结论是推导而来，并引证每条材料。“证据强烈指向 X：[具体材料]。”

### 3. 推断

对背景的一种合理解读，但没有明确证据支持。这是*你的解释*，不是记录中的事实。例如，PR 没有说明原因，但事故频道的时间显示错误当时出现在生产环境，而且修复在同一天合并、显得仓促，因此它很可能是紧急修复。或者，函数名暗示重试逻辑，而重试次数 3 与代码库其他地方的团队三次重试惯例一致。

表述：保留限定，并明确给出推导链。“考虑 A 和 B，C 看起来很可能成立，因为 D。”

### 4. 猜测

建立在稀薄证据上的合理假设，其他解释同样说得通。值得呈现，因为用户可能知道哪种解释正确，但要标明是猜测。例如，“这可能是针对一个后来已修复的浏览器问题的规避措施，不过我们没有找到当时的证据”；或者，“这个阈值可能是为了匹配某项 SLA 承诺，但没有 SLA 文档提及它”。

表述：“一种可能是 X，但我们没有直接证据。”通常放在“相互竞争的假设”中，与其他可能性并列。

### 5. 未知

你进行了查找，但未能查明。这是有效且重要的结果。记录下来。

表述：“我们搜索了 X、Y 和 Z，没有找到说明原因的证据。”具体写明*搜索了什么*。“我们没查明”不如这样的表述有用：“我们用关键词 A 和 B 搜索了工单系统，查看了自 2023 年以来修改过该文件的 6 个 PR，并在仓库中搜索匹配这个阈值的字符串字面量。都没有找到理由。”

## 表述指南

**表达确定性的词**意味着有直接证据或相互支持的证据，需要紧邻引证。不要将它们用于推断：“因为”“原因是”“被设计为”（声称知道作者意图）、“修复了”／“解决了”／“消除了”（声称变更达到了目标）、“团队决定了”（声称发生过集体决定）。

**限定词**表明这是解释而非事实报告。在“我们可以合理推断的内容”中充分使用：“看起来”“似乎”“很可能”“暗示”“与……一致”“一种解读是”“有可能”“可能曾经”“证据倾向于”。

**应避免的词：**

- “显然”。如果显然，用户就不会提问。
- “清楚地”。后面几乎总跟着并不清楚的主张。
- “当然”。同上。
- “只是”（例如“它只是为了性能而做 X”）。带有轻视，通常掩盖了不确定性。
- “我觉得”／“我相信”。你在综合证据，不是在发表个人意见。改用“证据表明”。

## 避免事后合理化

今天“说得通”的代码，可能是基于如今已不适用的理由写成，也可能当时理由就是错的。不要把整齐的解释硬套到混乱的历史上。不要先假定作者做了“正确”的事，再倒推理由替它辩护。不要假定一致的模式必然出于有意设计，它可能只是复制粘贴。不要把没有证据变成不存在的证据（“没人提到安全顾虑，所以它一定不是顾虑”）。

## 迎合陷阱

用户经常把假设放进问题：“为什么我们这样做，我猜是为了性能？”不要直接确认。这个猜测是调查的起点，不是需要验证通过的结论。把它与其他候选解释并列，独立检查证据。如果证据支持，就附引证说明；如果不支持，也明确说明，并呈现证据*实际*支持什么。

## 证据互相矛盾时

在输出中呈现双方来源，并附引证。不要选择更符合整齐叙事的那一方。例如，工单说“客户 X 的合规要求需要这个”，PR 却说“清理这一部分的技术债”。两者可能都成立（工单促成了工作，PR 给出了作者的表述角度），也可能有一个是错的。让用户判断。

## 证据缺失时

诚实地说“我们不知道”是最有价值的输出之一。用户由此知道答案不在显而易见的位置，需要去问某个人（原作者、产品负责人、团队负责人），或者可以决定这个问题不值得继续追查。不标明缺口、反而用自信的猜测填上，会实际伤害用户，因为他们会据此行动。具体列出每个缺口：问题是什么、搜索过哪些来源、在每个来源中搜了什么、找到了什么（什么都没有，或只有旁支材料）。

## 定稿之前

综合者交付输出之前，要检查“我们找到了什么”和“我们可以合理推断的内容”中的每个主张。每个主张要么附引证，要么移到推断或假设。措辞必须与层级相符。不能把代码当作它自身意图的证据（如果如此，删除或重新归类）。输出应有“我们不知道什么”一节。如果完全没有提到缺口，就值得怀疑：要么证据罕见地完整，要么有东西被掩盖了。
