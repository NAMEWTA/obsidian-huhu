# 为什么如此

调查代码背后的动机和意图。运行机制说明回答代码做什么、如何运作；本方法回答哪些力量导致这种形态。需要理解运行机制时沿真实调用链阅读代码，调用 dev-learn。

调查者与综合者使用本环境可用的能力，默认继承当前模型；需要独立判断且有工具支持时使用独立上下文。不存在指定模型配置时直接继续，不虚构模型标识。

调查只读。若宿主的只读模式不提供必要连接器，选择允许读取的最小权限，但仍禁止写入、发送消息和修改远端。无子智能体工具时依证据类别顺序调查。

## 工作姿态

作为**认真、谨慎、精确的调查者**工作。诚实区分知道与推断。阅读[证据与可信度](evidence-confidence.md) 获取完整置信框架与措辞指南。综合者必须遵循它。

## 第 1 步：理解目标与问题

**目标**通常是一块代码、一种模式、一个功能或一项有名称的设计决策。**问题**通常是设计理由、权衡、触发设计的边界情况、外部约束、死代码或广泛历史调查。

目标模糊时，例如“为什么这样做”没有明确指代，依据对话背景作最佳判断，包括打开的文件、近期修改、光标位置、刚才讨论内容。简要说明理解，让用户可以纠正，然后继续。

## 第 2 步：建立代码锚点

派调查者前，直接建立种子背景：真实文件路径与行范围、关键符号（函数、类、常量），以及能够取得的相关提交、PR 号和工单 ID。当前环境确有 Git 检出和命令时，使用 `git blame -L <start>,<end> <file>` 查看最近触及提交，`git log --follow -p -- <file>` 查看跨重命名的补丁历史，`git log --oneline -20 -- <file>` 查看近期提交，`git log -1 --format=%B <commit>` 提取正文中的 PR 号；主题中的 `(#1234)` 是一种可能格式，不能假定所有仓库相同。随后通过已连接且获授权的仓库读取工具取得实质提交对应的 PR 正文与讨论；只有 `gh` 已安装且可访问目标时，才使用 `gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews`。没有 Git 历史、PR 工具或权限时，保留当前代码锚点并明确历史缺口，继续处理其余可访问证据。将已取得的锚点与缺口交给每位调查者和综合者。

## 第 3 步：派出并行调查者

**默认进行完整并行调查。** 目标是完整覆盖图，不是最小覆盖。记录空结果，不跳过搜索。

### 发现能力

派生前，列出当前环境已提供的连接器和工具，按实际元数据判断可读取的证据类别，不探测无关账户或未提供的目录。

把每个可用 MCP 映射到一种证据类别：

1. 源码控制历史
2. 问题或工单跟踪器
3. 长文档
4. 团队即时聊天
5. 基础设施可观测性
6. 错误或异常追踪
7. 产品分析数据仓库

有 git 检出时可读本地源码历史；远端 PR 通过已连接工具或可用的 `gh` 获取，缺少访问时明确记录。其余六种按 MCP 名称、服务器说明、工具名和资源描述分类。MCP 可匹配多类时，选其主要证据所属类。在覆盖图记录有歧义的情况。

有独立调查能力时，在当前并发上限内为每个具有可用读取能力的类别分配一位调查者；超过上限就分批。每份简报只负责一个证据类别及其对应工具或连接器，保持来源边界。没有子智能体能力时，按相同类别依次调查并分别记录结果，不能声称已取得独立并行判断。

每位调查者的提示是填好的 `investigator-brief.md`，再附：

- 从 [来源调查索引](source-investigation.md) 选出的实际类别手册，例如 [版本控制历史](source-code-history.md) 或 [工单系统](source-issues.md)。附该叶文件，不能只给索引；按当前连接器的真实能力适配示例。
- **目标代码看起来具有防御性**时附 `incident-investigation.md`，包括空值检查、重试逻辑、超时处理、限流、功能开关、出口防护、OOM 处理。
- 代码锚点和用户原始问题。

### 调查者名单：每个可用证据类别一位

下方每类都有独特优势，“最擅长”之后指出其能揭示的“为什么”。用它预判结果、在类别返回空时命名缺口，并且仅在少见的可证明无关情形下解释跳过。

1. **源码控制**（git 历史、用 `gh` 获取 PR、代码注释、测试）。存在可访问历史时优先调查；没有 Git 历史或远端访问时记录缺口，不能假定一定可用。最擅长*审查期间记录的实现时理由*。
2. **问题或工单跟踪器**（例如 Linear、Jira、GitHub Issues、Plane、Shortcut MCP）。最擅长*迫使变化的产品或商业因素*，理由来自工程之外时最强。
3. **长文档**（例如 Notion、Confluence、Google Docs、Coda MCP）。最擅长*在变成代码前写下的长篇设计理由*。
4. **团队即时聊天**（例如 Slack、Discord、Microsoft Teams、Mattermost MCP）。最擅长*从未进入文档的实时讨论*。源码、工单和文档轨迹稀薄时尤其重要。
5. **基础设施可观测性**（例如 Datadog、New Relic、Honeycomb、Grafana、Splunk MCP）。最擅长*促成代码的基础设施和运行时现实*。目标响应基础设施信号，如超时、重试、限流、熔断时最强。
6. **错误或异常追踪**（例如 Sentry、Rollbar、Bugsnag、Airbrake MCP）。最擅长*促成防御或修正代码的具体异常和错误轨迹*。适用于 catch 块、空值防护、类型检查、重试及其他防御。
7. **产品分析数据仓库**（例如 Databricks、Snowflake、BigQuery、ClickHouse、dbt、Redshift MCP）。最擅长*塑造代码的产品和数据现实*。适用于开关控制代码、实验驱动交付、数据迁移、“这个数字从哪里来”。

### 何时跳过调查者

只有提供**明确书面理由**，并写进最终“查阅来源”时才可跳过。两种有效理由：

- **环境中没有该类别可用且获授权的读取能力。** 标为缺口，不是选择：“跳过团队即时聊天。没有可用匹配 MCP，因此无法搜索对话记录。”
- **来源可以证明无关**，而非“可能无关”。门槛很高：“跳过错误或异常追踪。目标是构建时脚本，没有运行时代码路径。”

若范围判断认为目标只是一个提交的琐碎改动，且 PR 描述已经完整回答，只有在确认七个可用类别的搜索全部冗余后，才可直接回答，并明确说明。应当少见。

## 第 4 步：综合

派一位综合者。使用独立综合上下文；没有该能力时由协调者综合并说明。给予：

1. 调查发现，包括空结果与有理由跳过的类别。
2. 代码锚点。
3. 用户原始问题。
4. `evidence-confidence.md` 中的置信框架。
5. `investigation-synthesis.md` 中的综合提示模板。

## 第 5 步：展示

向用户展示综合者输出。可为清晰度轻微编辑或补充对话背景，但**不要改写置信措辞**。

## 输出格式

结构遵循 `investigation-synthesis.md`：问题、相关代码、发现的事实、可以合理推断的内容、竞争性假设、未知项、查阅来源、置信总结。按需要适配，但保持置信分离；“查阅来源”按调查者一行，包含返回空和跳过的调查者及原因。

“查阅来源”之后，如果用户问“为什么”是为了随后修改代码，把历史发现转成规划约束集：保留 / 改变 / 避免 / 风险。

## 应避免的常见失败

- **近因偏差。** 假定最近提交最权威。当前形态通常积累了许多更早决策，应向前追溯。


## 持久化交接

调查者只读收集证据。协调者在任务需要保存时，将新增的长期结论统一写入 `.agents/dev/notes/context/`，按真实位置引用已有背景；保留代码锚点、来源、核对版本、置信层级和缺口。临时查询记录留在当前需求目录，不能复制为永久事实。后续代码改变时重新核对当前机制，历史动机保留其时间范围。
