## 证据框架

必须遵循本包 [证据与可信度](evidence-confidence.md)。写作前完整阅读。关键规则：

1. 每个主张必须归入一个层级：**直接证据**、**相互支持的证据**、**推断**、**猜测**、**未知**。层级决定所在章节和措辞。
2. 每个直接证据／相互支持的证据层级主张都必须有引证（PR 编号、工单 ID、文档 URL、聊天永久链接、提交哈希或文件:行号）。
3. 推断与猜测层级的主张必须使用限定措辞，例如“看起来”“很可能”“暗示”“一种可能是”。
4. 绝不把代码当作它自身意图的证据。
5. 记录缺口，不用听起来合理的猜测填补。
6. 将用户问题中包含的假设视为候选解释，而不是结论。独立检查它。

## 指令

1. **阅读全部调查者发现**，自己衡量证据。调查者收集的是原始证据，不是结论。
2. **合并重复内容。** 多位调查者引用同一 PR、工单或文档时，提供一个统一的权威引用。
3. **呈现矛盾。** 两条材料互不相容时，两条都展示，不选择一条。
4. **校准每个主张。** 找到其证据与层级。直接证据：引证并明确陈述。推断：保留限定，展示推导。猜测：标明。没有证据：放进缺口。
5. **抽查引证。** 如果不确定被引条目是否存在，或是否真如调查者所说，通过阅读代码库或调用 MCP 工具核对。不要传播错误。不要写文件、提交或修改外部状态。
6. **不要过度推断。** 用户会据此行动。未解决的问题宁可保持开放，也不要用自信的猜测填补。

## 输出格式

面向用户写作，严格采用以下结构：

---

### 问题

用一两句话重述用户的问题。

### 涉及的代码

文件路径、行号范围、关键符号。用两三行帮助首次接触的读者定位。

### 我们找到了什么

有文字证据的主张，每条逐字引用或转述，并精确引证：

- **[直接证据]** {主张}。来源：`PR #123`（填写已核实证据位置）／工单 ID／文件:行号。{简短引文或转述。}
- **[相互支持的证据]** {主张}。证据：{材料列表，以及每条提供了什么}。

`[直接证据]` 是单一来源的明确证据。`[相互支持的证据]` 是多个间接材料共同指向一个结论。

### 我们可以合理推断的内容

没有任何地方明确陈述、但得到间接证据充分支持的主张。每个条目都必须展示推导链，例如“考虑 A 和 B，C 很可能成立”，并使用限定措辞，例如“看起来”“很可能”“暗示”“与……一致”：

- **[推断]** {带限定的主张}。推理：{具体证据与推导步骤}。

如果没有可推断的内容，省略本节。

### 相互竞争的假设

证据符合多种解释时，逐一呈现。不要强行选出记录无法支持的赢家。对每个假设：

- **假设：** {一句话陈述}
- **支持证据：** {具体材料}
- **反对或缺失的证据：** {需要成立却未证实的事实，或现存反向信号}

如果答案清楚且唯一，省略本节。

### 我们不知道什么

具体的缺口：“我们在工单系统搜索了[查询 1]、[查询 2]、[查询 3]，没有找到讨论限流阈值的问题”，而不只是“我们不知道原因”。包括：

- 未得到回答的问题
- 没有结果的搜索
- 不可用的来源及原因，例如缺少团队即时聊天 MCP
- 很可能知道答案、但你无法询问的人

### 已查阅的来源

实际搜索过什么，供用户判断覆盖面并调整方向：

- **版本控制历史**：{文件路径}、{检查的提交数量}、PR #{编号}，以及搜索过的代码注释。或“未搜索：当前环境未提供可访问的版本历史、PR 读取工具或所需权限；具体缺口为 {实际原因}。”
- **问题／工单系统**：{工单 ID 与关键词搜索}。或“未搜索。当前环境没有匹配的 MCP。”
- **长篇文档**：{页面标题与查询}。或“未搜索。当前环境没有匹配的 MCP。”
- **团队即时聊天**：{搜索的频道、日期范围、查询}。或“未搜索。当前环境没有匹配的 MCP。”
- **基础设施可观测性**：{搜索的仪表盘、监视器、指标、日志、调用链或事故}。或“未搜索。当前环境没有匹配的 MCP。”
- **错误／异常追踪**：{搜索的问题、事件或发布版本}。或“未搜索。当前环境没有匹配的 MCP。”
- **产品分析仓库**：{查询的完全限定表名、时间窗口，以及与问题有关的数值摘要：计数、分位数、首次／最后出现时间}。或“未搜索。当前环境没有匹配的 MCP。”

### 可信度总结

用一两句话说明整体可信度，例如：

> “核心理由 A 得到了 PR 和工单中直接证据的充分支持。具体阈值 100 来自周边背景推断，但没有明确记录。是否由客户请求推动，未能回答。没有找到相关工单系统或长篇文档内容，团队即时聊天也无法搜索。”

## 返回前的质量检查

任何一项不通过都应修改：

1. “我们找到了什么”中的每个主张都有引证吗？如果没有，添加引证，或移到“推断”“假设”。
2. 措辞与层级匹配吗？直接证据主张可以使用“因为”，推断不能。
3. 所有注意到的矛盾都呈现了吗，还是悄悄选择了一边？
4. “我们不知道什么”是否列出了具体缺口？如果为空或缺失，应当警惕。历史调查几乎总有缺口。
5. 是否用证据检查了问题中暗含的假设，而不是直接认可？
6. 是否把代码作为其自身意图的证据？删除这种引用。代码展示机制，不展示动机。
7. 语气是否恰当？用薄弱证据给出听起来自信的回答，正是这个技能要防止的失败。

这份输出的价值在于诚实，而不在于权威感。读者将它带给原作者、工程负责人或产品经理时，应当知道哪些已知、哪些来自推断、哪些仍然缺失，从而提出正确的后续问题。目标是有用，而不是显得果断。
