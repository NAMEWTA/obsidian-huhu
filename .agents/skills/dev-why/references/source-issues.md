# Linear 工单

## 这个来源包含什么

- 描述功能、缺陷及其动机的问题
- 附在问题上的项目文档，通常是 PRD 或规格
- 父／子问题关系（较大的工作方向 → 具体工单）
- 问题评论（澄清、范围变化、“为什么做这件事”的理由）
- 表明动机类型的标签，例如 `compliance`、`customer-request`、`perf`
- 解释范围变化的状态更新
- 附件与关联的 GitHub PR

产品／业务背景经常存在于 Linear：例如“因为客户 X 提出要求所以做这件事”，或“这是第三季度合规计划的一部分”。

## 如何搜索

有已授权的工单连接器时，使用其实际读取工具。

1. **从关联工单开始。** 如果初始提交或 PR 引用了工单 ID，例如 `ENG-1234`、`[BUG-567]`，先用 `get_issue` 获取。阅读完整问题，包括评论。
2. **按关键词列出相关问题。** 使用 `list_issues`，以功能名、关键符号或业务术语做文本搜索。尝试多种表述。
3. **沿问题树追查。** 如果找到的是子问题，获取其父问题。子问题偏向具体行动，父问题经常保留“为什么”。
4. **阅读项目文档。** 如果问题属于某个项目，用 `get_project` 检查附带文档。项目级文档最常记录规格和理由。
5. **检查标签和里程碑。** 标签暗示动机类别，例如客户请求、事故跟进、合规。里程碑把工作与截止日期联系起来，这往往揭示动机。

## 这里的好证据是什么样

- 问题描述明确说明业务问题：“Acme 客户因为 SOC2 审计需要 X”。
- 评论记录某个决定：“我们决定采用方案 B，因为方案 A 需要改动计费服务”。
- 父问题标题体现计划方向，例如“第三季度企业就绪”或“减少支付失败”。
- 附带的 PRD 或规格。
- `customer:acme`、`incident-followup`、`compliance`、`perf-regression` 等标签。

## 常见陷阱

- **范围漂移。** PR 引用的工单可能关闭后又按不同范围重新打开。阅读完整历史。
- **机械模板。** 某些团队要求填写“为什么”一节，但只填套话。泛泛的文字（“改善用户体验”）很可能不是真正答案。
- **过时工单。** 旧工单常反映已经变化的某版计划。检查日期，并与代码上线日期交叉核对。
- **因重复而关闭的链条。** 沿“重复于”关系找到正式工单。
- **私有工作区内容。** 无法访问某个问题时，将它记为缺口，不要猜测。

## 返回什么

对每个相关工单：
- 工单 ID 和标题
- 从描述或评论引用的问题／动机，不转述；综合者需要精确文字用于引证
- 标签、父问题、项目
- 作者、创建日期、关闭日期
- 如有，附工单链接
