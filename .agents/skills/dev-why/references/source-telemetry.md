# Datadog 遥测

## 这个来源包含什么

Datadog 保存运行时记录，即生产环境实际发生过什么，而不是计划或讨论过什么。

- **指标。** 团队埋点的计数器、量规、直方图。某个指标的*存在*本身就是有人认为这个数值值得观察的证据。
- **监视器与告警。** 团队认为值得把人叫醒的条件。监视器对 `rate_limit_hit > 10/min` 发出告警，是团队担心这个阈值的直接证据。
- **仪表盘。** 团队对某个子系统重要信息整理出的视图。
- **APM 调用链与跨度。** 请求级运行时数据，用于“为什么这么慢”“为什么这里超时”等问题。
- **日志。** 大量事件记录，经常包含促成防御性代码的错误条件。
- **事故。** 带时间线及关联复盘的正式事故记录。
- **笔记本。** 团队的探索性调查，通常包含假设与分析。

## 如何搜索

有已授权的观测连接器时，使用其实际工具。先广泛搜索，再缩小范围。

1. **确定所属服务。**

   ```
   search_datadog_services（按名称或团队筛选）
   search_datadog_service_dependencies（查看上下游）
   ```

2. **先看仪表盘和监视器。**

   ```
   search_datadog_dashboards（查询：功能名、服务名、符号）
   search_datadog_monitors（相同查询）
   ```

   当仪表盘或监视器覆盖目标时，记录其查询和监视阈值。阈值经常就是“为什么这里限制为 N”的答案。

3. **目标周边的指标。**

   ```
   search_datadog_metrics（按名称模式，例如功能或符号）
   get_datadog_metric_context（元数据：描述、单位、标签）
   get_datadog_metric（时间序列；“PR 日期附近是否有突增？”）
   ```

   将指标轨迹与目标新增／变更日期关联，是强支持证据：“`payment_timeout` 指标在 2023-11-03 突增，重试逻辑于 2023-11-06 合并。”

4. **日志：缩小范围，不倾倒内容。**

   ```
   search_datadog_logs（目标附近的原始日志模式，设置 use_log_patterns=true）
   analyze_datadog_logs（SQL 风格聚合，只在需要计数时使用）
   ```

   用符号、错误字符串或功能名搜索。**强烈优先采用有时间边界的查询**，例如变更前后各 30 天。

5. **APM 跨度与调用链。**

   ```
   aggregate_spans（统计：“这个端点多久失败一次？”）
   search_datadog_spans（检查单个跨度）
   get_datadog_trace（特定调用链 ID）
   ```

   对超时、重试、慢路径和跨服务行为很有用。

6. **事故。**

   ```
   search_datadog_incidents（按标题、团队、日期范围）
   get_datadog_incident（某次事故的完整详情）
   ```

   如果目标看起来具有防御性，搜索它加入时附近发生的事故。某次事故时间线写着“为 X 增加防御检查”，就是接近直接的证据。

## 这里的好证据是什么样

- 监视器的查询和阈值与代码执行的约束匹配（代码限制为 100，监视器在请求超过 100 次／分钟时告警）。
- 目标作者创建的仪表盘，其中部件对应代码测量或防范的内容。
- 代码合并前生产指标突增，合并后数值稳定。
- 事故记录引用了目标代码、相同符号或相同错误字符串。
- 变更之前的时间窗口内，日志显示了防御性代码所要防止的特定错误模式。

## 常见陷阱

- **相关性不等于因果关系。** PR 前突增、之后稳定具有暗示性，但不能定论，因为同一窗口可能还有其他变更上线。检查相邻 PR。
- **对找到的图表过度解读。** 图表体现制作它的人如何理解问题。名为“重试成功率”的图表证明团队关心重试成功，不能证明这就是某一行代码存在的原因。
- **消失的遥测。** 指标可能被重命名、删除，或保留期限很短。如果找不到相关窗口的数据，那是缺口，而不是空结果。
- **规模带来的噪声。** 积极用服务、标签和时间窗口缩小日志搜索。用 `analyze_datadog_logs` 聚合，不要倾倒原始日志。
- **有埋点不等于造成原因。** 某个指标说明有人认为它值得测量，不能说明代码*因为*它而加入。交叉核对提交／PR 日期。

## 返回什么

对每个相关条目：
- 类型（仪表盘／监视器／指标／日志模式／调用链／事故／笔记本）
- 标题或名称
- 链接或标识符（仪表盘 ID、监视器 ID、指标名、事故 ID）
- 所有者／作者和创建／修改日期
- 与问题有关的具体条件、查询或引文，尽量逐字保留
- 相关性：它对目标代码暗示什么，以及关联有多强
