# 从需求到交付

先说清用户要改变什么、完成意味着什么，随后执行。把已授权的工作持续做完；需要决策时先完成不依赖该决策的部分。不要把“写了计划”“代码能编译”“已开启自动合并”当成最终交付。

## 工作约定

- 按目标、风险和反馈成本选择开发方法。可先写规格，也可在明确的公共接口上测试先行，或直接实现后验证；方法可以组合。始终明确可观察的完成条件，取得真实行为证据，不把某套流程强加给所有任务。
- 以当前代码、运行结果和实际发布制品描述“现在是什么”；以用户确认的目标描述“要变成什么”。发现差异就修正实现或过期记录，不能拿旧文档覆盖用户目标。
- 依据规模选择过程。小修改可把规格写成几句话；跨模块需求才拆切片、设计和记录。不要为每次编辑加载全部知识、建立固定审批链或填写空模板。
- 用户已经授权的范围持续有效。研究、实现、可逆验证不重复确认；外部发布按用户明确目标执行。仍缺生产目标或授权时，先把制品、差异、回滚和检查准备好，再说明缺什么。
- 本技能是编排入口，依赖下表的阶段技能。按当前任务调用对应入口，携带已有产物与返回条件；安装依赖不表示执行所有阶段。
- 一个任务由当前负责人持续推进。专门方法补充当前阶段的证据与产物，沿用已确认决定和同一份记录，不另开一套竞争流程。

## 选择下一步

| 当前情况 | 推进方式 | 可调用技能 |
| --- | --- | --- |
| 不知道应该用哪个能力，或只想了解使用方法 | 按任务选择最小入口；先解释使用方式，不把咨询误当实施授权 | `dev-help` |
| 首次配置环境、角色模型或推理预算 | 核对真实可用工具和模型，沿用已有配置，不假定后台能力；默认目录骨架由安装器负责 | `dev-setup` |
| 想让重复工作逐步符合自己的习惯 | 从允许读取的历史中提炼稳定模式，形成简短可维护的项目技能 | `dev-personalize` |
| 用户在任务中询问进展，或需要交接简报 | 汇总已完成、当前证据和待决事项；回答后继续原任务，除非明确要求暂停 | `dev-status` |
| 输入来自聊天、Issue、截图、日志或多处反馈 | 找到原始证据、实际行为、目标和范围，合并重复诉求 | `dev-intake` |
| 要配置报告接入或按来源监控需求 | 分开选择来源、追踪器、仓库路由、控制方式与实际触发器，完成授权内初始化 | `dev-issue-setup` |
| 已配置来源适配器的报告需要分类、查重或分流 | 按原生报告、身份与追踪器契约处理证据；来源可为聊天、工单、邮件、告警或手工输入，本阶段不复现或修复 | `dev-issue-triage` |
| 已配置报告管道，可信分诊和真实 UI 控制条件齐备 | 核对归属，按完整协议复现或验证已有补丁；需要且已授权时修复并交付草稿 PR | `dev-issue-fix` |
| 产品规则有关键歧义 | 先从代码回答事实，围绕会改变方案的问题逐轮澄清 | `dev-grill` |
| 需求已清楚但还不能直接验收 | 写用户行为、边界、非目标和成功条件 | `dev-spec` |
| 用户要深化或改写待执行的请求 | 用四问检查专业遗漏、原始材料、具体方法与独立证据，交付可使用的提示词 | `dev-sharpen` |
| 接手陌生模块 | 沿一个真实用例走通入口、业务、存储、反馈和失败路径 | `dev-learn` |
| 不理解历史设计为何存在 | 区分当前行为、当时理由和推测，追溯代码与可获得的决策证据 | `dev-why` |
| 边界或接口有实质取舍 | 比较不同结构；从调用方体验、状态所有权与领域术语判断 | `dev-architecture` |
| 已有或明确要建立 TLA+ 模型，需要带检查结果的状态图 | 运行 TLC，生成规则标记和最短反例，逐步核对真实代码 | `dev-statechart` |
| 需要检查关键属性、选择形式化工具或维护模型 | 明确属性、假设与边界，运行检查并识别模型漂移；普通解释图不自动进入此流程 | `dev-formal-verify` |
| 涉及页面、交互、设计系统或视觉验收 | 沿用实际代码中的组件与 token；按产品或营销场景读取设计规范，不要求设计工具账号 | `dev-ui-design` |
| 需求无法一次可靠交付 | 拆成可验收的垂直功能切片，显式依赖，先跑通最小完整链路 | `dev-plan` |
| 有互不冲突的工作或值得比较的不同方案 | 分配写入范围和验收规则，再集成并验证最终结果 | `dev-parallel` |
| 规格或切片已具备实施条件 | 按既有工程规范实现，接通真实行为，验证当前制品 | `dev-build` |
| 普通 Issue、CLI/API/UI 功能错误或验收失败 | 沿实际入口复现并定位根因；仅以性能指标为目标时进入测量流程 | `dev-debug` |
| 用户指定测试先行，或当前实现已选择 TDD | 按公共接口逐个完成失败测试与最小实现；已有正确行为补测不自动进入红绿实现 | `dev-tdd` |
| 同类错误反复出现或关键约束容易被绕过 | 优先改善类型、接口与状态所有权；有真实价值时增加可执行规则 | `dev-guardrails` |
| 实现完成 | 分开检查规格符合度和工程质量；修复真实问题 | `dev-review` |
| 需要证明实际用户路径可用 | 驱动真实应用，核对结果与副作用，维护可重复验证方法 | `dev-verify` |
| 目标是改善延迟、吞吐、资源或其他测量指标 | 固定工作负载和口径，完成取证、优化或公平比较，复用同一份基线 | `dev-benchmark` |
| 目标包含上线 | 确认环境与版本，执行授权部署，验证实际服务并记录 | `dev-deploy` |
| 需要清晰的文档、提交说明或 PR 简报 | 按读者问题组织信息，给出具体行为、证据与必要取舍 | `dev-writing` |
| 一个需求已经交付或明确停止 | 整理新知识、修复冲突、保留有价值的理由并归档过程 | `dev-archive` |

已有规格直接实施；只要求设计就交付设计；只要求解释就停在解释。读 [推进与恢复](references/execution.md) 处理并行和中断。需要完善需求时读[需求到实施的阶段衔接](references/workflow-routing.md)，执行已选任务时读[工程执行方法](references/operating-method.md)；它们补充当前阶段，不重新选择已完成的阶段。

复杂任务没有合适现成流程时，用[定制执行方法](references/custom-workflow.md)形成可验证单元并继续已授权工作。长任务的记录与事后复核使用[决策证据方法](references/decision-trail.md)，检查决定、替代方案与实际证据是否对应；只要求复核时交付审计结果，不自动继续迁移或实施。追查某项设计当时为何被采用由 `dev-why` 负责。用户明确要构建可操作的状态面板时，将它作为实施任务；仅查询进展使用 `dev-status`。

## 让工作能继续

本套技能新增的项目资料统一以 `.agents/dev/` 为根，按需使用以下分区。已有资料按真实位置查阅并保留必要引用；只有明确要求迁移时才搬迁，并保留内容、标识和有效链接。用户本次明确指定其他位置时按其指令执行：

- `.agents/dev/changes/<日期-主题>/`：当前需求的 brief、spec、plan、progress、evidence，按需创建。
- `.agents/dev/notes/`：经过验证的术语、背景、决策、错误经验和模块理解；入口 `index.md` 只指路。
- `.agents/dev/deploy/<环境>/`：部署手册及 `releases/` 下的历史发布记录。
- `.agents/dev/archive/changes/implemented/`、`rejected/`：由 `dev-archive` 在归档时按结果分流，并将目录重命名为 `<type>_<YYYY-MM-DD>-<slug>/`，保留创建日期；旧历史不自动迁移。退役知识仍放 `.agents/dev/archive/notes/`。

安装器选中任意 dev 技能时补齐 `.agents/dev/AGENTS.md`、开发六类目录和两个归档结果目录的九份短导航；选中 system 技能时另补系统根说明。固定位置的模板说明自动更新，根指令与业务记录不覆盖，不生成空业务记录，技能不重复维护初始化方法。按任务显式读取开发根与相关目录说明，不假定宿主自动递归加载。活跃 change 保持原命名，各阶段沿用同一真实路径，分类只发生在收尾。

这些是目标项目的资料，不能写进安装包 `.agents/skills/`。需要恢复时，使用 [交接模板](assets/handoff.md)，只留下当前结果、证据、未决问题和下一步。

## 收束

对照最初交付目标，给出实际改动、当前版本的验证证据、交付地址或提交，以及确实未完成的部分。需要上线但尚未部署，明确写“实现已完成，部署未完成”；部署成功后，把可复用知识与最新代码引用整理进项目，而非把聊天记录全量塞入 AGENTS.md。
