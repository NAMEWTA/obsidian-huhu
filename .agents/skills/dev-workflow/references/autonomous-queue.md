### 完全自动执行

**你负责裁决，不负责 PR。每个 PR 由一位负责人从构建负责到合并；未写代码的验证群体证明即将落地的代码前，任何东西都不合并。**

一份裁决覆盖一个补丁，绿色 CI 覆盖一个头提交。第 4 步完整群体验证一次，只有重大变化才再跑。`dev-deploy`（验证后落地） 的 patch-id 规则可以延续某通道结果，但每个新头提交都需要自己的绿色 CI。

1. **操作人的门禁优先。** 授权仅覆盖队列事项，操作人指定归自己处理的事项及队列外 PR 停在可合并状态。要求说明计划不等于开始执行。
2. **每个 PR 派一位负责人，让替代者找得到其工作。** 项目一次性确定托管工具。使用当前实际可用、已认证且确认语义的托管连接器或 CLI；需要时读取其帮助，不猜工具名称。每位负责人使用当前可用的隔离执行环境，构建，按 `dev-deploy`（打开 PR） 打开 PR，在真实产物证明改动，按 `dev-deploy`（跟进 PR） 跟进到绿色，步骤 4、5 放行后合并。

   尽早打开 PR，让 CI 和机器人与工作并行。完成真实差异审查及项目要求的检查后，代码才就绪；注释检查只采用项目已选择的策略，以便完整群体验证面对完成代码。随后核对目标主干与拟落地结果，在自证前报告实际代码就绪头提交和基线。只在冲突、检查要求或行为变化使当前基线不足时更新分支；采用仓库允许且已有授权覆盖的合并或变基方式，不为流程自动重写共享历史。报告每个后续头提交，自证、CI、跟进完成后报告可合并。修复轮次保持该基线，除非主干冲突、使 CI 失败、或有已知并发改动落在相同文件，因为每次变基都会重启 CI。代码就绪推送前，以及后续需要验证者的推送前，在已提交头上运行仓库对触及路径的检查。

   执行环境可能中断。开始后把本次决策轨迹统一保存到 `.agents/dev/changes/<日期-主题>/progress.md`；每完成一个单元保存实际结果，远端推送按本次已授权交付节奏执行。谁派子智能体，谁在该项目记录中写明 ID、状态和基于实际任务设定的停滞判断，让父级死亡后根仍能探查。仅在必要且已授权改写本任务独占分支时，使用绑定最后一次已知远端 SHA 的 `--force-with-lease`；发现任何非自己推送时停止并报告根智能体。
3. **负责人从主干并行工作，不堆叠，** 让每个 PR 独立落地。
4. **群体验证一次。** 完整群体验证在代码就绪头执行一次。只有新行为、重新设计或大规模新差异才再次完整执行。变基、冲突解决、小修复由单一验证者检查新头，纯文字变化无需验证。按 **并行验证** 在代码就绪 SHA 扇出独立验证者。他们重跑门禁，使用真实可用的浏览器、终端或项目驱动，在真实入口证明关键行为，并审计差异。没有实际运行通道，或你尚未审计可合并报告凭据时，裁决都不能是干净，因为任何通道都不信未经自身检查的主张。

   只用可展示的问题阻塞 PR：头提交上的失败运行，或 PR 改错的一行文档。基础分支本来就有的问题，无论主干还是堆叠下层 PR，都不阻塞，除非此 PR 复制它或新触达它。只有用户会遇到的缺陷、失败门禁、错误交付文档阻塞，其余放后续事项。
5. **负责人只合并你验证过、且在将落地主干上测过的内容。** 仅绿色 CI 绝不授权合并。独立验证开始后，合并准备先核对最新目标主干和当前补丁。只有确有基线更新需要时才按已有授权调整分支；报告实际新头并等待该头的必要检查，已有证据按补丁、基线和产物判断是否仍有效。

   合并前立即获取主干，判断其变化会否影响补丁，因为每次主干移动都变基永无止境。即将落地代码从未测试时，先在隔离的合并结果上验证；存在冲突、双方修改同一文件或检查方式变化时，按仓库策略处理必要的基线更新并等待对应 CI，不把变基当作唯一办法。双方都改锁文件时，若冻结安装在合并结果上通过，且 PR 修改的包在合并结果解析与头提交相同，无需变基，因为该安装测试了将落地锁文件；安装失败则调查并修复合并结果或必要的基线更新，再重新验证。主干改动了补丁调用者或依赖，例如它调用的代码或依赖版本，则在合并结果运行补丁检查，通过后合并。其余直接合并。主干在合并准备后若将迫使第三次变基，暂停报告根，由根安排冲突工作的顺序。
6. **运行根层职责。** 任何放松门禁的改动，如提高预算或增加允许列表，都要验证者证据，再由你新签认，因为负责人是希望变绿的一方。授权覆盖内部复核时，该签认是内部复核记录，负责人记录指向你的签认，供通道检查。撤销禁用检查或把检查改为软失败的改动，恢复真实失败门禁；不能通过删掉检查来获得绿色。绝不提供或绕过托管平台强制的批准，没有签认能覆盖它。

   已有持续执行授权时，用实际可用的事件通知或调度能力持续审计直到没有委派工作；没有后台调度时在当前会话执行并如实记录恢复点，因为长任务会漂移、智能体会静默停滞。每周期从主干重读本手册，通过让负责人记录来修正未报告头提交、未登记智能体等漂移，因为漂移是记录缺口，不是停滞。探查每位智能体直至叶子通道，只按实际副作用判断，因为状态文字和摘要会隐藏卡住的子级。错误、无法开始新轮次、超过停滞时限无新活动都算停滞；到首周期既未推送也未写轨迹的负责人也算。等待你或操作人的不算停滞，应回应。及时准备替代执行者；先停止或隔离原执行者的写入，确认同一分支只有一个写入者后再接管，不让两个执行者同时改写。本周期有对操作人有意义的变化，按 **状态更新** 更新；没有变化则安静。
7. **操作人要求停止时立即停止。** 暂停作为禁止写入命令传达到每位负责人。各自报告当前位置，保留简报，直到操作人解除。

**回复：** 按 **状态更新** 更新操作人，涵盖每个 PR 状态与裁决、已合并内容、签认及原因、未满足的操作人门禁、搁置后续事项，附每个 PR 与轨迹链接。
