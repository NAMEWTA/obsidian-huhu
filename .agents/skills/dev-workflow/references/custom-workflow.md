# 为复杂请求设计可审计的执行流程

已有合适项目流程时复用它。面对大型迁移、复杂多部分改动或人离开后回来审查的任务，而没有更窄方法合适时，先设计执行流程，再实施。用户只要求深化或改写请求时，交付可审查流程与提示词，不自动开始代码修改；已要求执行时继续完成。

## 开始

阅读当前项目约定和已有材料，建立简短任务清单。按下列五个阶段组织，删去无实际内容的独立工件，不引入固定状态协议。原则服务本次可观察结果，不要求调用另一项技能。

## 阶段 A：界定

先建立依据，再投入。明确：

- 可证伪的完成条件：什么具体观察能证明任务尚未完成。
- 量化范围：大致工作单元、工作量、影响领域和已发现阻塞，区分估计与已知事实。
- 与风险相称的严谨程度：难逆转或高影响步骤需要更强证据，可逆低风险步骤用轻量检查。严谨体现在可检查产物与条件，不是“更努力”。

长时间工作前向用户说明范围、取舍和检查点。检查点用于让过程可审查，不等于新增批准口令；现有授权覆盖时继续。真正缺少预算、产品方向或高影响行动授权时，先准备具体选项，再询问缺失决定。

## 阶段 B：设计工作流

分成原子、可独立检查的单元，先处理风险最高的未知。共享类型、必要基础设施与验证入口放在它们所支持的工作之前，不为小任务先造框架。

- 捕获变更前基线，先确定如何比较旧值与新值。存在可靠现成检查就复用；是否先写测试取决于任务和项目，不强制统一顺序。
- 对难逆转且存在真实取舍的设计，独立形成少量有差异的方案，比较接口、状态、所有权、失败与兼容成本。已有形状清楚的机械修改不再重复比选。
- 只沿真正独立的接缝并行。每个执行者有清楚范围、输入、产物和证据，优先独立工作区、分支或数据对象。必须共享时用结构控制并发，不靠口头约定。没有代理能力就顺序完成；不指定不存在的模型、速度或工具。
- 把新增的阶段、依赖、完成条件和证据位置统一写入 `.agents/dev/changes/<日期-主题>/plan.md`。这就是后续审查对象。

已授权实施时执行这份流程，把实际单元填入任务清单。每个单元使用阶段 C 的循环纪律，同时穿插阶段 D 的记录，不把轨迹拖到最后补造。

## 阶段 C：运行假设循环

每个单元说明假设、做最小改动、在真实产物上对照判据观察。推进了就保留，没有就撤销本轮自己改动；保护用户和其他执行者的工作。检查当前单元后再继续，避免把问题埋在整批变更里。

- 直接检查产物，不只看自述。太容易通过时，先核对观察方法是否真的触达目标。
- 委派工作可配独立复核；无独立能力时明确局限。发现执行者迎合检查时，重新核对契约与产物；检查本身错了，单独说明并修正检查，不静默降低门槛。
- 结论是已验证、未验证或无结论。无结论不算通过，不隐藏失败与范围缺口。

## 阶段 D：保留审计轨迹

按[决策证据记录](decision-trail.md)保存重要选择、理由、证据、结果和转向。沿用当前项目 Markdown；不要同时维护内容重复的多个日志。只有审查者确实需要长期轨迹时按授权提交，普通过程留在当前需求。

## 阶段 E：整体验证并交付

对照阶段 A，在真实产品或交付物上检查整体，不只验证驱动自己。重复纠正值得结构化时，先判断架构、类型或已有检查能否以合理成本解决；不是每个错误都新增 lint。无法机械判断的经验保留简短理由与反例。

报告设计的流程、严谨程度及原因、决策轨迹位置、已按判据验证的内容、未解决项和实际交付。已有提交、推送、部署授权继续按范围完成；缺少环境或权限时明确可继续部分和真实阻塞。
