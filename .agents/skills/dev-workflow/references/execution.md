# 推进与恢复

## 先确定交付目标

把用户目标转成可以看见的结果：需求规格、可运行功能、已提交分支、PR、已合并版本、某环境实际上线。区分这些结果，沿当前授权走到用户要求的位置。用户只要方案时，不隐式改生产；用户要求实施时，不停在方案。

小修改只需简短意图和验收。涉及多次会话或多个模块时，把规格、下一步和关键决定写进 `.agents/dev/changes/<日期-主题>/`。已经有 Issue、设计文件或项目文档就链接它们，不复制多份同一事实。

## 用事实消除歧义

“仓库如何启动”“某字段在哪里使用”“这个方案是否比原来快”优先查代码或做局部实验。“哪个人群优先”“是否允许删除业务数据”才是需要用户决策的问题。实验不能替用户决定产品取舍，也不能把猜测说成事实。

一个问题不影响其余工作时，先推进已知部分。覆盖目标的决策已经给过，就记录并执行；不要因为技能中有“确认”二字重复索取授权。

## 切片与并行

第一片走通最小真实链路，例如提交表单 → 领域规则 → 持久化 → 回显。其余切片扩展场景。纯结构重构可以按依赖分波迁移，但每波需有可验证的不变量，不留下必须靠未来补丁才能解释的半成品。

存在真正独立的模块或证据研究时再并行。给每个代理：用户目标、规格路径、负责文件、依赖输入、验收条件和交接方式。避免两个代理同时写共享文件；主代理负责集成与最终证据。没有子代理工具就顺序执行，不能声称已独立审查。

如果使用 worktree，先确认已有工作、分支和输出目录，保留用户修改。不要为两行文案强制创建整套并行工程。

## 验证完成结果

执行实现后的风险相关验证：真实用户路径、受影响接口、持久化重启、故障分支或迁移检查。已有必需项目检查仍需满足。验证要针对当前 diff、构建或制品；修复后旧版本结果不能覆盖新版本。

“构建通过”不能证明交互可用，“CI 绿了”不能证明已合并，“已排入部署”不能证明服务已更新。获取对应系统的实际结果。环境不可用时，记录已完成证据、缺失证据和影响；不编造通过，也不反复执行相同无效检查。

## 继续上次任务

读取当前分支/提交、工作区差异、当前需求记录和最新用户指令。重新核对记录指向的文件和实际服务状态，不直接相信旧进度。保留已解决问题，更新已经失效的假设。只恢复仍存在的工作，后来的指令决定新的范围。

中断前记录最后成功操作、未提交改动、运行中的资源、阻碍和精确下一步。不要把恢复点扩写成每一次工具调用的日记。
