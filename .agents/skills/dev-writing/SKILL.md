# 技术写作

让读者在第一次阅读时理解需要知道或采取行动的内容。先确认读者、目的、材料与文档模式，再写清事实、理由、条件和结果。

## 先确定读者要完成什么

完整采用[技术写作四层标准](references/technical-writing.md)：Diátaxis 选择结构，开发者风格组织句子，受控指令规则减轻阅读负担，明确句法避免两种读法。英文特有的冠词、词数和词尾规则用于英文内容；中文保持相同的清晰目的，不机械套成字数配额。

教程帮助学习者完成可见产物；操作指南解决具体任务；参考资料描述真实接口；解释回答有边界的“为什么”。一份文档有一个主要目的，需要其他模式时拆成有明确本地引用的相邻文档。

面向 Agent 编写指令时读取[Agent 文档方法](references/agent-writing.md)；编写技能时继续读取[技能结构与调用方式](references/skill-format.md)。这两份补充保留指令分层与触发设计，不重复运行技术写作主流程。

## 以实际对象核对事实

读取目标代码、真实命令、当前配置和可用证据。使用真实符号与路径，区分已运行、计划、示例和未知。数量、性能与目录树必须能在对应版本重新生成；历史文档不能替代当前代码事实。

需要组织材料时使用[写作简报](assets/brief.md)，只保留对本次任务有价值的栏目。新增写作过程记录统一放在 `.agents/dev/changes/<日期-主题>/`，长期项目知识放在 `.agents/dev/notes/`；已有资料按真实位置引用。文档正文、PR 说明和提交信息按用户要求在实际交付位置维护，项目资料不写进技能目录；引用当前代码和必要背景，避免复制整份实现。

## 写完后校准

使用[清晰表达完整规则](references/clear-writing.md)逐项检查空话、含糊措辞、夸张、重复及格式习惯。规则使表达更差时修改句子，不为遵循规则而损害准确性。必要的取舍与不确定性不能因为精简而消失。

PR 说明先交代真实问题、改动后的行为与验证，再给审查所需的风险和证据；提交信息说明一次变更的目的。沿用项目既有风格。写作不自动授权提交、发消息或发布，已经明确授权的交付步骤继续完成。

交付完整正文、实际修改位置、核实依据，以及仍未解决的内容问题。只要求写作时不扩大为产品重构；发现技术事实矛盾时指出并在已有授权内修正。
