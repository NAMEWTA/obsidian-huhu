## 根因

发布端 `hookClaim` 取最低空闲本地槽位，读取端按槽位号升序消费，信封与引用无序号。事件 0 占槽 0、事件 1 占槽 1；读取端消费事件 0 并释放槽 0 后，事件 2 重新占用槽 0；下一轮读取端先读槽 0（事件 2），于是出现 `0,2,1`。T-12 中 16/20 轮、63 个 scope-round 的 `0,2,1` 与此一致。确定性单元回归先红（事件 e2 抢在 e1 之前）后绿，线索得到证实。

## 修改范围

- src/modules/agent/platform/desktop/hooks/hook-spool.ts：发布端在 `hookPublish` 开头取 `seq = performance.timeOrigin + performance.now()`，写入 `ref.json`；读取端在同一 scope 同 kind 存在多个槽位时（`sortByPublication`）按 `seq` 排序（正在退役的槽位最先，无法解析的引用排最后，同值按槽位号）；`consume` 校验 `seq` 为有限数，缺失即 `hookReferenceInvalid`（按 ADR-011 不兼容旧格式）。
- src/modules/agent/platform/desktop/hooks/hook-spool.test.ts：32x3 用例无条件断言每 scope 恰好 `id:0,id:1,id:2` 且不重复；新增确定性用例"a slot freed by an earlier event is reused without overtaking ..."（用 readdir 许可门控让读取端在 e0 消费后、e2 发布前停住）。

## 偏差与决策

- 选用"信封引用带发布序号 + 读取端排序"，不改槽位分配策略；序号取自发布进程的亚毫秒墙钟，跨进程顺序发布的事件可区分；并发发布者之间无顺序语义，不作保证。
- 未实施"减少持有 collector 时的重复同步 I/O"类优化：本票根因是顺序而非耗时，且 20 轮耗时与 T-12 无退化。
- 排序读取在 scope 内多个槽位时额外读最多 7 个小文件，仅在 backlog 存在时发生。

## Windows 回归修复

- 现象：修复提交后 Windows CI（hook-windows.yml run 41628755902）第 2 轮 94/96，缺 8:0、31:0，两 scope 留下 fault.json reason=hookCollectorTimeout；修复前同 workflow 20/20。
- 判断：`sortByPublication` 在同 scope 同 kind 多槽位时，每轮对每个槽位重读 ref.json（每次含逐级路径校验、open、stat、read、close），随后 `consume` 再读一次；Windows 上文件往返昂贵，拖慢消费，使事件 0 的发布端等待收集超时。另一种可能（ref.json 读失败被排 Infinity 而延后事件 0）核对：该排序只在 ref.json 暂不可读（发布者尚未写完）时发生，此时 `consume` 本就返回 false，不构成额外延后；未发现独立原因，Linux 无法复现 Windows 超时，按 I/O 放大处理。
- 修改：`hook-spool.ts` 在 `ScopeState` 增加 `refs`（kind/slot → 已成功解析的 ref），新增 `loadRef`：命中缓存直接返回，未命中才走原 `read`（路径校验不变）；解析失败/ENOENT 不缓存，半写入引用仍会重读。`consume` 的全部字段校验与 claim.json 校验（token/nonce/scope/local）仍对每次消费执行且读盘；校验失败（引用无效、claim 不符）时清除缓存项；槽位消费退役完成（`retiring.delete`）时一并清除。ref.json 由发布者 wx 写一次、仅消费者删除，故缓存不会陈旧；未放宽任何时限，未加重试。
- 回归测试：`hook-spool.test.ts` 新增“with several queued slots each reference file is read once…”：扣住 small 目录列表使 4 个槽位同时排队，经注入 `open` 计数，断言每个 ref.json 仅打开 1 次且顺序 e0..e3。修复前该断言失败（计数 >1），修复后通过。
- 验证：hooks 目录 vitest 9 文件 82 例全过；`pnpm exec tsc -noEmit -skipLibCheck` 退出 0；eslint 对 hook-spool.ts 通过（测试文件被仓库 ignore 规则忽略，仅警告）。`HUHU_HOOK_EXPECT_PLATFORM=linux HUHU_HOOK_ROUNDS=20 node scripts/fixtures/dev-overhaul-hook/run-measurement.mjs` 退出 0，20/20 通过、每轮 96/96、无顺序违规（输出 temp/dev-overhaul/hook-t13-fix.txt，分段样本 temp/dev-overhaul/hook-t13/fixed 与 nocache）。

## Windows 第二次回归与时钟修正（Lead，2026-11-03）

bc4c9f6 的 Windows run 41630723019：20 轮 8 轮失败，形态均为事件 0 被排到 1/2 之后（`x:12` 顺序违例，部分轮次事件 0 发布端 `hookCollectorTimeout`）。根因判断：`seq = performance.timeOrigin + performance.now()` 以各进程启动时刻为基准，Windows 进程间偏差达毫秒级，超过同一 scope 相邻发布的间隔，导致事件 0 的 seq 大于事件 1。修正为 `Number(process.hrtime.bigint() / 1000n)`（系统级单调时钟：Windows QPC、Linux CLOCK_MONOTONIC、macOS mach_absolute_time，跨进程可比）。hooks 目录 9 文件 82 例通过；Windows 由推送触发复测。
