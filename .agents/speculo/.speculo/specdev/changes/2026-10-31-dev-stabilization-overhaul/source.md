## 3. 全局架构约束与破坏性升级策略

### 3.1 保留技术栈与所有权，不保留历史包袱

继续使用现有 TypeScript / React / Tailwind / Radix 设计系统、Rust 原生辅助程序、Go Bot Runner / Eino / SQLite 以及 HAP 边界。这里的“不兼容”不是另起插件、改插件 id、改成 Web 应用、替换执行引擎或重新实现终端/编辑器。

跨模块继续通过各自公开 `api.ts` 和服务边界协作；内部可以重构，但不能让 UI 直接改业务文件、让 Go 绕过 Host 扫描 Vault、让不同模块重复持有任务/会话/档案事实。React store 是业务事实的投影，不是第二套持久化系统。

### 3.2 允许直接升级的内容

- 可以删除旧组件 API、旧 CSS 别名、重复状态字段、过期 adapter、测试专用兼容分支和已废弃格式处理。
- 可以设计新的内部 schema / wire 版本；必须同时更新生产者、消费者、生成类型、测试夹具及文档。版本号用于识别真实合同，不用于长期维护旧版本运行链。
- 不要求旧 Profile、旧缓存或旧设置自动迁移成为本项目完成的前提；可重建缓存与新建隔离的新格式数据目录。涉及真实资料时先冻结备份/导出和明确切换方式，**不得默认覆盖旧库或自动清空用户文件**。
- 同一批次做到引用清点、消费者更新、旧实现删除和检查通过。禁止“为了以后可能需要”保留永远不清理的双实现。

### 3.3 不可破坏的语义

保留真实停止/资源归属、Profile 锁、撤权与物理清除、来源版本绑定、审批与效果对账、秘密隔离、多窗口归属、未保存编辑保护以及已提交事实的可恢复性。可以重写实现，不能删掉这些保护的结果要求。

尤其禁止：把超时当作已经停止；把 UI 关闭当作进程结束；把事务后维护失败当作业务未提交并自动重试；把只有进程崩溃测试通过当作断电持久性证明；以隐藏诊断代替消除不确定状态。

## 5. W1：重构记忆依赖存储，消除重复传递闭包

**覆盖 #29，关联 #28 / #16。关键入口：[S1]，以及同目录 `context_read.go`、依赖图读写/撤销/清除调用链。**

### 5.1 问题解析与目标

原报告在 50 个 Run / 100 条来源消息下观察到约 150 MB WAL、41,004 行 `memory_dependencies`，主要增量在准备和终结路径。这些是历史测量值，本次没有重跑。源码确认的问题是：多个上下文条目重复保存其来源的传递依赖，而 Run 自身还保存 effective 依赖。

在上下文条目数和每个闭包都随历史增长的情况下，单 Run 可产生二次级依赖复制，累计出现更高阶增长。不能笼统承诺所有历史快照总成本都变成 O(n)，但必须消除“同一份传递依赖被每个条目重新展开落库”的额外乘数。

### 5.2 目标模型及决策门槛

**优先方案：版本绑定的规范化直接依赖图 + 条目引用。** 边绑定源对象种类、稳定身份、revision/hash 及必要作用域；上下文条目保存其表示/片段/来源版本，不再携带一份完整传递闭包。需要有效依赖时在受控事务/快照中解析，使用索引与单次操作内共享计算。

如果恢复、撤权或清除的实际访问成本证明直接图方案不合适，可采用**不可变、按版本共享的依赖集合/子图**，由多个条目引用。但必须证明共享身份和失效规则，不允许只是把同样的重复 JSON 换个表名。

- [ ] **W1.1** 盘点所有依赖消费者：封存、上下文查看、摘要/记忆来源、修改传播、撤权、删除预览、物理清除、恢复与委派 lineage。先写决策记录和数据不变量，再改表。
- [ ] **W1.2** 定义新 schema、边身份、索引、去重约束、循环检测与资源上限；区分来源历史版本和当前可访问性。共享缓存不能绕过撤权检查。
- [ ] **W1.3** 替换按条目写 effective closure 的链路，同时检查 Run/message/memory revision 级别是否仍复制同一大集合。单纯在 `sealEntries` 外包缓存而保持旧落库量，不算完成。
- [ ] **W1.4** 确认删除与隐私清除仍能找到全部受影响对象；应删除的内容、派生副本和引用不会因共享图变成不可追踪残留。
- [ ] **W1.5** 新旧 schema 不长期并存。选择新的隔离 Profile 或明确的一次性切换方式；旧数据只读归档/备份不得被静默覆盖，不实现永久双读双写。
- [ ] **W1.6** 提交可复跑的 50 / 100 / 200 Run 规模用例，覆盖链式、分支委派、共享来源、多来源和撤权。输出每阶段 SQL/行数/WAL 增量、准备/终结/恢复耗时及峰值内存。

### 5.3 验收

**A29：** 在相同输入下，条目数量增加不再导致同一来源闭包被逐条重复持久化；用结构性行数断言和增长曲线证明，而非只给一次耗时。编辑、撤权、删除、跨 namespace、来源 revision/hash 错配、检查点恢复及封存内容回归全部通过。写入变少不能换来查询、恢复或清除的无界递归。与 W2 联合重测 Windows WAL/关停，分别报告模型收益和 I/O 收益。

## 6. W2：重构关停语义、检查点调度和持久性证据链

**覆盖 #28 / #30 / #34，使用 #32 诊断。关键入口：[S2]、[S3]，以及 Runner 入口、TS 宿主管理和对应 contract tests。**

### 6.1 采用的方向

采用“**保留持久性，明确分阶段停止与真实完成，解除请求路径中的不必要维护阻塞**”方向。它比原 #28 的 B 方案更明确：现有代码已经有请求停止与真实完成的分离，应统一调用方语义和阶段诊断，而不是新建同名能力。

### 6.2 生命周期合同

拟统一的阶段为：

```text
running → stop-requested/admission-closed → draining-producers
        → durable-fence/flush → closing-resources → profile-unlocked → closed
```

这是设计目标，不是声称当前已经存在这些枚举。阶段顺序必须结合已有恢复 fence 的实际约束确定；关键是可观测、真实且不提前释放资源。

- [ ] **W2.1** 明确“停止请求已接收”“执行器已排空”“持久化已完成”“Profile 已释放”四种不同事实。统一 Go、TS、CLI/宿主、测试 fixture 的调用合同。
- [ ] **W2.2** 重构 `Close()` 的固定 3 秒整体封装，或删除该含混接口并迁移全部调用方；使用调用方等待期限观察实际阶段。超时返回必须保留“仍在停止/刷盘”的真实状态，不能返回假成功，也不能一律归类为执行器失败。
- [ ] **W2.3** 保留单一 drain、停止准入、原生产者收敛和 `Done` 的真实清理语义。等待超时后，资源 owner 仍负责清理；宿主重开、临时目录删除和 Profile 再次获取必须等真实完成或明确进入恢复流程。
- [ ] **W2.4** 定义刷盘错误、关闭错误、不可恢复停止失败和外部强杀的处理与诊断。自动强杀必须属于明确的最后手段策略，并留下恢复信息，不能作为日常关闭成功路径。
- [ ] **W2.5** 测试包含慢于旧 3 秒上限的刷盘、调用方先超时再等待完成、重复 stop、退出过程中到达的响应、producer 未收敛和重新启动竞争。

当前 `withinTx()` 在 COMMIT 后仍持有连接执行 TRUNCATE；这会拉长整个方法占用时间。业务提交已经完成的事实不能被后续维护超时改写。
