# UI-001 任务与视觉评估

评估者：本次 P owner。没有委派独立 Agent，也不将这份自评描述为用户研究。先按任务评估，再做技术检查；用户在预览期间明确选择 final 的 A 方案，选择来源另行冻结到 approval-ui.md。

## 观察

实际打开并检查了 A/B/C 与 final 的 1440×1000、390×844 截图，另看 comparison 两种宽度、原生审批、历史部分失败与窄屏控制抽屉。现有 HUHU 的继承依据是源码和设计文档；没有把原型截图当作当前生产 Obsidian 截图。

A 的空间与会话持续可见，中央两终端可对照，右侧控制展示目标身份、Space、输入阶段和读屏入口；这与本轮终端协作目标最直接。隐藏控制后终端立即扩大，仍可从工具栏返回。桌面标题、面板焦点、目标状态没有混在一套状态里。空闲和工作中同时具有文字及颜色；审批使用原终端区域，不出现一个新的 Chat 工作流。

B 的上方会话列表确实改变信息层级，适合观察后台，但压缩终端纵向空间；C 将操作转移到命令面板和按需工具，终端最大，但后台发现性更弱。因此保留 B/C 作为比较来源，不将它们作为本次选定布局。

窄屏采用上下终端，每个输出独立滚动；工具面板为可关闭模态层，没有意外水平滚动。390px 下常驻两终端阅读面积较小，用户可切为单面板或聚焦一会话；这属于原型中可操作的取舍，不承诺移动端 PTY。长名称列表省略，标题/目标详情可确认完整含义。

## 修复与保留

初轮浏览器检查后补齐了弹层 Tab 首尾循环，去掉阻碍 200% 缩放的页面最小宽度，校准了侧栏最小值；这些修正已经进入用户选择的 final。没有更换既有配色、导航或候选方向。

技术核对另外检查分屏对象与比例、通知计数、标注保存、原生来源恢复，以及控件命中区域。最终结果见 technical-review.md 与 browser.json；这里不以视觉判断代替机械验收。

## 边界

原生 TUI 文本、状态定时器、审批和网页均为 fixture。截图没有证明真实 Agent 能力、IPC 访问控制、数据持久化、性能、宿主集成或五个平台。终端输出的空白留给真实运行内容，不用统计卡片填充；10/11px 元信息辅助识别，不承载唯一的关键操作。
