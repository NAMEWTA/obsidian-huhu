# 智能体工作台

工作台的 **AI Agent** 页把终端、编程智能体的原生会话历史和用量放在一起。它可以运行普通 Shell，以及这些 CLI 智能体：Claude Code、Codex、Gemini CLI、OpenCode、Pi（`@mariozechner/pi-coding-agent`）和 Grok（`xai-org/grok-build`）。仅桌面端可用。可以在 **设置 → 智能体** 里一键安装或升级各 CLI（见下），也可以自行安装。默认情况下，从 HUHU 启动的 CLI 和普通终端使用本机已有的登录（“系统账号”），与你在系统终端里直接运行时一致，不需要重新登录；HUHU 不会替你登录。需要把登录隔离在当前库时，可另建“托管账号”。

六个智能体默认都已启用。可以在 **设置 → 智能体** 中分别关闭，并设置程序路径。

## 会话与布局

先创建或明确选择 Space，再在其中启动 Shell 或智能体。Space 保存目录与会话归属；同名或同目录的 Space 仍是独立对象。没有绑定时先要求选择，取消不会启动；不会根据当前目录、焦点或唯一候选自动推断。

工作台顶部显示当前 Space 名称和完整标识；长名称可悬停查看全文，同名或同目录时可凭标识区分。工具栏保留侧栏、终端控制、原生历史和页面菜单；没有 Space 时仍能打开导航、创建 Space 和打开网页，加载中或读取失败也会显示原因。后台与已关闭视图的会话仍列在原 Space，可从侧栏重新打开。

主区域的「+」菜单同时创建终端、智能体和浏览器标签。空输入按 Enter 新建终端；输入 `claude` 可选择 Claude Code，`example.com` 打开网页，`localhost:3000` 使用 HTTP，`obsidian 插件` 使用浏览器设置中的搜索引擎。方向键选择、Enter 确认、Esc 取消；输入法组字期间不会启动。

拖动标签可排序或移入其他组，拖到四边可分屏，拖回可合并；最多四个标签组，每个终端标签最多四个窗格。分隔线可调比例，中键或 × 关闭标签只关闭视图，终端仍在后台运行。需要结束进程时使用明确的“结束”操作并确认。进程退出后可明确“重新启动”。浏览器与终端可并排，详见[浏览器](browser.md)。

每个终端窗格都保留标题、状态和关闭按钮；完整标题包含 Space、持久会话、运行及可用的窗格标识。窄于 600 像素的工作台把横向分屏临时上下排列，不改保存的分屏方向与比例；恢复宽屏时沿用原布局。分隔线可拖动或用方向键调整，双击恢复均分。关闭最后一个运行中的窗格只把它移到后台，不会停止运行。

新建 Shell 或智能体时可以填写可选名称，并选择“在后台启动”。用户创建默认显示；后台创建没有可见窗格，仍立即出现在侧栏，准备中、取消和失败都可核对。后台启动、输出或状态变化不会切换当前 Space 或抢走焦点；前台启动等待期间转去其他目标，迟到的运行也留在原 Space 的后台。

侧栏列出会话，并有“看板”“统计”两个入口。它们和会话一样是标签：点击会打开对应标签，再次点击只激活已有的那一个，不会重复打开，也不会替换当前页面或弹出窗口。标签可拖动排序、分屏，可用 × 或中键关闭，关闭后在本次运行中可从跳转面板的“最近关闭”恢复。重启后标签、顺序和位置都会恢复。“看板”和“统计”入口可用右键菜单隐藏。

Ctrl/Cmd+J 打开跳转面板，可搜索近期标签、最近关闭和历史，或新建标签；部分操作有菜单中的快捷键提示。看板标签按“需要处理、运行、已完成、空闲”四列组织，空闲默认隐藏；可搜索、筛选、快速发送，点击卡片会切换到那个会话的标签。

自动化不是智能体工作区的标签：它是图标栏上与智能体并列的**自动化看板**，需要智能体执行时经智能体模块的服务调用。详见[自动化与通知](automation.md)。

工作中显示转圈，完成显示对勾；后台完成产生铃铛未读，激活标签后清除；等待权限显示橙色问号并进入“需要处理”。状态来自原生 Hook；没有可靠事件就显示未知，输出安静不代表完成。

关闭工作台叶子、终端标签或窗格只释放显示界面；原进程和权威终端屏幕继续接收输出。点击侧栏会话重新打开同一次运行，保留其进程和屏幕，不额外启动一个进程。明确结束、停用模块或卸载插件才收束其运行。Obsidian 重启后恢复会话记录、标签组和布局，不自动启动智能体或重放命令；普通终端显示“重新启动”，带有效原生标识的智能体显示“恢复会话”。恢复使用原账号、目录和 CLI 恢复参数，校验失败不会改为新会话。

- 终端菜单提供复制、粘贴、查找、提示符导航、清屏、回滚、字号、目录、重命名、结束及附加材料。
- 网址普通点击可弹出操作菜单；Ctrl/Cmd 点击使用默认目标，Shift+Ctrl/Cmd 反向。默认目标在浏览器设置中选择。
- 库内 `路径:行:列` 引用在 Obsidian 定位；拖入文件插入路径，拖入文本按粘贴处理。
- 粘贴会剔除 ESC 等控制字符并在应用要求时使用括号粘贴；有选区时 Ctrl/Cmd+C 复制，否则中断。IME 仅发送最终提交文本。Shift+Enter、kitty 与 Windows win32-input-mode 按终端协议处理。

同一次运行可显示在多个窗格，只有当前明确聚焦且可见的窗格决定终端尺寸，其他窗格跟随权威尺寸；隐藏或关闭显示不会改变进程的尺寸。界面从已经解析的屏幕接续，未完成的 UTF-8 或转义序列仍由原会话处理，不让多个窗格分别回应终端查询。

尺寸请求被终端模型接受，不代表 PTY 已应用；原生尺寸失败或结果未知会在运行中的窗格持续显示，直到当前请求确认应用，或显示新的故障。被后续请求取代也不等于已经应用。

设备查询回复有独立的容量限制。回复被拒绝或投递未能核实时，窗格保留明确诊断、关闭新用户输入并请求收束原运行；后续回复成功不会抹除先前丢失的事实。HUHU 不自动重发失败回复，已收到的输出仍继续解析与确认，停止是否完成以原运行的清理证据为准。

较慢的界面跟不上时会重新同步屏幕，不拖住后台进程的输出确认。屏幕模型、解析批次、历史读取、链接和显示副本均有容量上限；达到上限会明确报错并请求停止该次运行，截断或未知的显示不会被标成完整输出。容量使用的是有界对象与逻辑字节计量，宿主与渲染器的实际内存仍需按平台观察。

输入与粘贴按一整笔提交。快捷提示词及其回车共同接纳，容量不足时不会只发出回车；效果未知时不会自动重发。普通粘贴仍只插入内容，不自动执行。

停止会先关闭该次运行的新用户输入与尚未发出的启动，随后等待根进程结束及受管范围清理证据。根进程退出码不等于子进程已清理；未能核实的范围、已知残留或断线会保留为未完成或未知。等待超时、关闭等待界面只结束这次观察，不撤销停止，也不再次启动。输出、终端协议回应和流量确认会保留至有界结算，输出被截断时会明确显示。

归档会话或 Space 前先展示将处理的会话范围，取消不停止任何运行。确认后范围如已变化，需重新确认；运行清理和结果保存均核实后才归档。部分失败时保留逐会话结果，已停止的进程不会回滚重启。归档 Space 只标记父级归档，保留子会话、历史和布局。新建的纯元数据历史导入会持久保存“从未启动”证明，可直接归档；给既有会话补充来源不构成此证明。首次启动接纳时会先清除该证明，旧记录或恢复后缺少终止依据的会话继续按运行未知处理。

每次启动前都会先保存该次运行的未确认标记。宿主意外退出后，恢复记录不会据旧 PID 杀进程、自动启动、扫描 Provider 或重放输入；未确认清理的记录仍可打开查看，但禁止盲目重启。已确认结束的后台会话即使没有保存窗格，也可先打开记录视图，再显式继续或重启；Shell 沿用原配置，智能体“继续”必须具有有效原生来源，缺失时不会换成空白新会话。

停用模块时先关闭准入和新输入，同时开始进程收束与数据保存。关闭调用最多观察 15 秒，未完成会明确报错；这不表示已经取消磁盘写入。尚未结算的写入仍由原实例隔离，此时重新启用或另一个实例可能提示占用，避免旧写覆盖新记录；原写入实际结束后才释放写入权。保存失败保留预写的未确认事实。归档超时或取消后，尚未开始的归档写入不会晚到执行；已经开始且不可取消的写入只能暂报效果未知，再核实实际结果，不宣称回滚或自动重试。

终端控制在宽屏使用侧面板，窄于 600 像素时使用对话框。发送目标由明确选择的 Space、会话和运行固定，不随当前显示焦点切换。切到其他 Space 后，原目标仍显示原名称和身份；目标不再有效时禁止发送，需重新选择。对话框支持键盘导航，关闭后在原目标仍有效时返回原触发按钮。

## 被动收件箱

工具栏的铃铛只显示当前 Vault 的未确认消息数量；消息到达不会自动打开工具、切换 Space 或抢焦点。收件人必须从持久的 Space/Session 身份中明确选择，停止、后台和脱离视图的会话仍可选；同名或同目录的 Space 会同时显示稳定 ID，没有 Space 时先选择，不按当前目录猜测。

在收件箱中，“读取”只查看正文，“确认收到”才写入 ack；发送会先生成并保留 messageId。发送或确认的 pending/unknown 观察会保留原消息、目标和诊断，可在关闭工具、切换历史或窄屏重挂载后重新打开并执行一次最新主记录核对。界面不会自动重试、重填草稿、启动会话或向终端注入输入。

## 快捷命令

标签条的快捷命令按钮支持添加、分组、复制、编辑和再次运行。终端命令在新 Shell 标签执行；智能体命令在新交互会话输入就绪后提交提示词。每次运行都在一个明确的 Space 中：库级命令可以在 **设置 → 智能体 → 快捷命令** 的行内保存所属 Space（“每次询问”则每次打开 Space 选择器），全局命令跨库，不保存 Space，总是询问。取消选择不启动任何会话，也不记录“最近使用”；保存的 Space 若已删除或归档，运行会明确失败并要求重新选择，不会改到另一个 Space。命令的“工作目录”保持原有含义：留空、整库路径（库根的绝对路径）或 `.` 时在所属 Space 的已授权目录启动；填写的目录（相对路径按库根解析）必须位于该 Space 内才会采用，否则本次启动被明确拒绝（目录不在 Space 授权范围内；目录不存在或无法读取时则提示该文件夹缺失），不写入会话记录，也不会改用别的目录。终端右键的插入入口只把命令放进当前输入区。看板的“快捷命令”小组件可以列出并运行这些已保存的终端快捷命令（智能体模块的公开接口 `agent.quick-commands` 只提供名称、类型、范围和运行，命令内容不外传）。

## 启动智能体

受管新会话使用所绑定 Space 的已授权目录；启动前重新核对真实目录和授权，原目录失效时明确报错，不改换目录。账号、程序参数及权限配置在接纳本次启动时固定，之后修改设置只影响新的启动。“确认提示”默认是 **YOLO**：第一次启动带有此类参数的智能体时，HUHU 会询问“让智能体跳过确认？”，并说明智能体可以不经询问修改库里的文件。在 **设置 → 智能体** 中选择 **Manual** 可保留 CLI 自己的确认提示。GUI 选择后台启动仍保留这次确认；无人交互的后台调用不能弹框或自动替用户确认，需要先在交互入口完成相应配置。

| CLI | 程序 | YOLO 添加的参数 |
|---|---|---|
| Claude Code | `claude` | `--dangerously-skip-permissions` |
| Codex | `codex` | `--dangerously-bypass-approvals-and-sandbox` |
| Gemini CLI | `gemini` | 无 |
| OpenCode | `opencode` | 无 |
| Pi | `pi` | 无 |
| Grok | `grok` | `--permission-mode bypassPermissions` |

找不到程序时，HUHU 会提示并给出安装链接；特殊位置可在 **设置 → 智能体** 中填写程序路径。六种 CLI 都可以填写账号名称，支持中文与标点；名称以 NFC/trim 规范化后使用完整 SHA-256 作为内部标识，显示名称保留。

- **系统账号（默认，名称留空）**：不改动 HOME、XDG 和各 CLI 的目录变量，也不清除已导出的 API 密钥，CLI 读写它自己的配置目录（`CLAUDE_CONFIG_DIR` 或 `~/.claude`、`CODEX_HOME` 或 `~/.codex`、`GROK_HOME` 或 `~/.grok`、`GEMINI_CLI_HOME` 或用户主目录下的 `.gemini` 等）；Claude Code 不设置 `CLAUDE_CONFIG_DIR`，这样 macOS 钥匙串中的登录条目不变。设置 → 账号里的默认项会显示实际路径。
- **托管账号（名称非空）**：HOME、配置、数据、缓存和临时目录位于 `.huhu/agents/<device-id>/accounts/<provider>/<stable-id>/`，不继承宿主的登录或 API 密钥，登录与系统账号互不影响。“添加账号”新建托管账号，之后在该账号里用 CLI 自己的方式登录；HUHU 不会把系统登录复制进托管账号。非空非法名称会报错。

从桌面图标启动 Obsidian 时，HUHU 会用 `$SHELL -ilc` 恢复 PATH 和 shell 配置里导出的 CLI 目录变量（有超时；Windows 跳过）。

旧插件账号目录和 helper 必须完成一次 Obsidian 主进程冷重启后才迁移。旧有损目录名可能碰撞时，需明确选择旧目录或新建身份，不猜测归属。来源先复制/校验再切换，恢复副本保留在库内；重启不会把活跃凭据退回复制阶段。登录状态跨设备不保证可移植，允许重新认证。

## 原生历史

右侧抽屉的标题是“当前 Vault 历史”，只列当前 Vault 的投影，没有账号总历史页面，也没有“全部”开关。投影由两类记录组成：工作目录经真实路径解析后位于当前库内的会话，以及由本 Vault 的 HUHU 会话启动的会话（包含已归档 Space 的会话，其工作目录可以在库外的已授权目录）。其他库的会话和与本库无关的库外会话既不进入索引，也不显示或预览；索引中不再满足这两类条件的行会在下次扫描时清除。库外准入使用 HUHU 会话记录的完整 Provider、账号命名空间、设备、原生会话 ID 和精确来源引用；来源不完整时不扩大读取范围。

索引是库内可重建的 `.huhu/terminal-agent/<device>/workspace-index.sqlite`，只保存元数据（标题、模型、用量、工作目录、来源状态），不保存对话正文；正文只在你展开预览时由 helper 按需读取，并在读取时重新核对来源。来源必须是 CLI 的会话日志（系统账号限定在各 CLI 的会话目录内，登录和设置文件不会被当作会话），不接受符号链接或失效来源。恢复仍要求工作目录在当前库内或已授权。Agent 运行时的会话列表、自动化用量和续接转录查找也读取同一份当前 Vault 投影；HUHU 不再创建或写入账号级 `index.sqlite`（旧版本留下的该文件可安全删除，仅是可重建的缓存，不含对话正文），因此其他库或本机其他项目的会话标题不会再进入本库。

每行显示 Provider、账号、所属 Space 与来源状态。Space 归属来自持久 Space 记录（`historyOwners`，完整账号、设备、原生会话 ID 与精确来源引用一致才绑定），不按 cwd 推断；无归属的行显示为“未归属”。抽屉的 Space 筛选默认“全部 Space”，可选单个 Space（已归档的 Space 在单独分组中）或“未归属”。来源缺失、已变化、不支持或无权限的行保留元数据和你的标注，预览显示来源状态而不是正文；读取时才发现的变化同样如此，不会展示未经核对的内容。部分来源失败时顶部只显示一条汇总并可重试，其余记录照常显示。展开的行在刷新后保持展开并重新载入预览。同一账号的相同原生会话标识若出现在多个不同来源，索引会保留原来源及标注并显示冲突，停止正文预览、导出和继续；请核对原来源与重复副本后刷新。选中的精确来源在读取前后都会复核，相同时间戳不能让另一来源的正文或旧缓存混入。

历史使用虚拟列表，默认显示 Agent，可选择“包含普通终端元数据”；普通终端只展示已有 Session 的名称、Space、目录、身份与创建时间，不读取正文或启动进程。可搜索标题与元数据，按智能体、Space、归档及更新时间范围（过去 24 小时、7 天、30 天或全部时间）筛选，按创建/更新时间排序、智能体/目录分组；展开查看详情，收藏、归档、改标题、复制恢复命令、导出或在新标签恢复，也可拖入标签组。正文读取达到容量上限时，预览会明确标出只覆盖记录前段，片段中的末条对话不代表原生会话的最新内容。需要最新记录时点刷新。原生记录不存在或校验失败时报告错误，不用新会话顶替。

|---|---|
| Claude Code | 账号的 `CLAUDE_CONFIG_DIR`（系统账号默认 `~/.claude`）中 `projects` 下的 JSONL |

| OpenCode | 读取 `opencode.db` 的一致性快照：helper 把数据库及 WAL 复制到系统临时目录中的只读副本再打开（源文件从不被 SQLite 打开，也不产生 `-shm`/`-journal`），读完立即删除；读取根会话及其消息和文本部分 |

`history.list` / `history.preview` 控制操作必须显式给出 `spaceId`（缺失为 `TARGET_REQUIRED`，未知为 `TARGET_NOT_FOUND`），只返回通过持久 Space 记录绑定到该 Space 的历史行（含库外授权目录里的该 Space 会话）；未绑定的行只出现在抽屉的“未归属”，不按 cwd 猜测。用法、翻页与错误码见[本机 CLI 文档](agent-workbench-cli.md#历史)。

### 导入与继续

预览只读，不会创建 Session。要继续一条历史，先把它导入某个 Space：展开历史行，未归属的行有“导入到 Space…”，也可直接点“继续”，会先让你选择 Space。导入前会先核对所选 Space 授权的目录正是这段对话的工作目录，不符则拒绝，不留下无法撤销的绑定；导入保存来源与归属证据（Provider、账号命名空间、设备、原生会话 ID、来源引用），按完整原生引用精确去重——再次导入得到同一条记录，标注保留；同一原生 ID 在不同账号下是不同的来源，不会合并。

“继续”先弹出确认，显示将在哪个目录启动哪个 Provider，取消不启动任何进程。对应的运行仍在时只定位并显示，不再启动；已结束时用 Provider 的精确恢复参数启动同一个会话的新运行代次。来源缺失、账号或设备不符、工作目录不是该 Space 授权的目录、Provider 未启用或不支持、上一次运行尚未确认结束，都会明确说明原因，不新建空会话顶替，也不会自动分叉。

同一条原生对话在本机至多一个 HUHU 可写运行，跨 HUHU 实例和不同的库都有效。占用以提供方的真实存储位置（转录文件的规范真实路径）加原生会话 ID 为准，不使用库、设备标识或库内账号根，所以两个库共用同一个系统账号时也只有一个能继续；托管账号的数据在各自库内，本来就只有那个库能到达。历史“继续”、标签页的“恢复会话”和自动化的指定会话续接都先取得这把占用；新启动的会话在得知原生会话 ID 和转录路径后尽力取得（已经启动的进程无法撤销，被占用时不会强行停止它）。自动化的会话是非受管终端，只在收到已确认的进程退出后释放，没有受管运行那样的后代清理证据。占用记录放在用户级操作系统应用状态目录（见[库之外的数据](data.md#库之外的数据)），记录占用实例、进程与会话；只有占用进程被证实已退出（进程不存在，或同一进程号的启动时间不同，或同一进程里的 HUHU 实例已卸载）才会被接管。运行被核实退出后释放；关闭模块时，只在运行时和辅助进程停止之后释放确认已结束的占用，未能确认的保留，直到占用进程退出后由其他实例接管。其他实例占用时，继续返回冲突，不会分叉。同账号下不经过 HUHU 协议的外部程序不受此约束。


## 额度与用量

看板与底部状态栏显示当前工作空间的 token 和会话用量。分析使用当前 Vault 的历史投影：工作目录规范化后属于当前库及其子目录的会话，加上由本 Vault 的 HUHU 会话（含已归档 Space）启动、工作目录在已授权库外目录的会话；相邻前缀目录和指向库外的符号链接不会纳入。工作空间索引为 `.huhu/terminal-agent/<device>/workspace-index.sqlite`，是唯一的历史索引（旧版本留下的账号级 `index.sqlite` 已不再写入，可安全删除），不先读取全机对话再由界面裁剪。分析默认近 30 天，指标、趋势、热力图、目录/提供方分组和明细使用同一范围；费用缺失时明确标示未知。

启动次数和工作时长使用独立的 `workspace-stats.json`，仅累计归属当前库的终端，并显示统计起始日期。无法确认目录归属的累计数不混入当前统计；历史 token 可从有明确工作目录的原生日志重建。

订阅额度属于整个账号，在 **设置 → 智能体 → 账号** 查看和刷新，与工作空间 token 分开。账号页打开时才观察额度；Gemini 保留每个模型各自的额度。切换账号只影响新会话，运行中的会话保持原身份。没有额度接口的提供方不编造比例。状态栏仍可在常规设置或右键菜单中隐藏。

token 来自原生日志。输入包含缓存读写，缓存数字是输入中的明细。Codex 取会话累计值，Claude 对同一消息的重复用量去重。费用只显示 CLI 原生记录的值。汇总缺少某些会话时标注“仅统计已知用量的会话”，任何会话缺少费用时，汇总费用显示“费用未知”。自动化使用运行前后原生累计值的差额。

## 业务入口的 Space 绑定

看板快捷按钮、技能按钮、快捷命令、`agent.prompt-runner`（一次性运行）、`agent.dispatch` 和自动化的智能体/脚本操作都必须落在一个明确的 Space 中，没有“无 Space”的业务运行。规则：

- 交互入口（看板按钮、快捷命令、技能按钮）：已保存有效 Space 时直接使用；没有时先打开既有的 Space 选择器（无 Space 时选择器直接提供“创建 Space”入口，创建后在新 Space 中继续），取消不启动任何进程、不产生已接纳的投递。选择在调用被接纳前冻结，之后切换界面不改变目标。
- 后台入口（定时/手动自动化、`agent.prompt-runner`）：定义或请求必须带 `spaceId`；缺少时运行记为失败（`spaceRequired`，提示去配置），Space 已删除、归档或不再授权其目录时失败（`spaceUnavailable`），不弹框、不暂停后盲重试，也不按 cwd、同名、仅剩一个 Space 或当时的界面焦点推断。
- 新会话先在所属 Space 提交 Session 记录，再启动进程；保存失败时不启动（`spaceSaveFailed`）。进程使用 Space 的已授权目录：请求的目录为空或为整库根时取 Space 目录，更窄的目录必须位于 Space 内，其余拒绝。
- 投递到已有会话（`existing`）不带 Space：所属 Space 由会话的稳定 ID 决定，输入不能改变归属；同一 invocationId 携带不同的 Space 按原冲突语义拒绝，旧的回执和请求原样保留，不为补 Space 而改写或重放。

看板“快捷操作”中的智能体项目目前不保存 Space，每次都打开选择器。旧的看板按钮和快捷命令没有 Space 时按“每次询问”处理；旧的自动化定义没有 Space 时仍可读取，但需要先在编辑器选择 Space 才能保存和运行。这些旧数据不会被自动迁移或补值。技能按钮和快捷按钮可在配置中保存所属 Space，默认“按下时询问”；保存的 Space 失效时投递明确失败并要求重新选择，不会改到别的 Space。

## 旧工作台迁移与恢复协议

首次启动新版时的一次性导入、报告位置和回退步骤见[数据与恢复](data.md)的旧工作台迁移一节；这里只记工程合同。

- 顺序：`recoverPending`（启动前恢复）→ 读取设置 → 一次性导入 → 模块启动。导入只增不删：来源与被替换文件先写入可回读的恢复副本并核对摘要，再写日志，再替换，再写 `legacy-import.json`。
- 日志：`journal.a/b.json` 交替写入，序号最高的有效日志为准，撕裂的写入只会退回上一阶段。阶段 `prepared → committing → committed → done`，回退为 `rolling-back → rolled-back`。启动恢复规则：`committed` 向前，其余向后；已确认无改动的目标不会被覆盖。
- Owner 协议（`RecoveryOwner`，T-16 复用）：`owns(path)` 白名单；`preflight` 列出需用户先停止的工作（返回 BUSY，不代为停止）；`quiesce` 关闭全部入口并使后续写入明确失败；`drain` 严格排空，写入失败必须 reject，不能用吞错的 flush；`adopt` 在文件替换后重建内存、写队列、`JsonStore` 基线和设置 namespace 缓存；`release` 幂等。所有 owner 先全部关门并排空，才取共同快照。
- 生产调用方是设置页的“备份”标签（见下节业务备份与恢复）；`legacy` 一次性导入仍在启动前运行。下列实时 owner 已注册到应用的 `recovery` 主机（模块上下文的 `recovery` 字段）：设置（仅重载指定 namespace，其余 namespace 原样）、Space 记录与布局（`agent-workbench-records`，由 SharedWorkspaceOwner 注册，Agent 与 Browser 共用同一 SpaceService 和布局存储，所以浏览器写入同样被门禁）、历史标注、自有统计、自动化会话登记，以及只负责列出运行中终端/智能体的 `agent-running-work`（有运行中工作时返回 BUSY，不代为停止）。启动前导入时进程内尚无这些 writer，所以只需要跨窗口 writer 监听。
- Space owner 语义：`quiesce` 后所有新写入（SpaceService 的创建/会话/收件箱/布局保存与 Browser 的打开、关闭、更新）立即以 `SOURCE_UNAVAILABLE / recovery-busy`（BUSY）失败；界面直接编辑被撤销并报告，已接纳的活动提示只暂存；`drain` 严格保存脏草稿并排空队列，任一失败即 reject 并中止、释放；`adopt` 从磁盘重读记录，丢弃缓存草稿和 JsonStore 基线，之后第一次写入不会带回旧内存状态；`release` 重新开放并继续泵出暂存提示。
- 共享工作区 owner 在恢复操作进行或恢复失败时不会被创建（`settled()`），以免模块读到半替换的文件。
- 旧 `createWorkspaceStore`（v1 写入口）在 `legacy-import.json` 存在时拒绝加载与写入，已打开的实例在每次写入前复查。
- 旧布局里的终端标签保留原有 `sessionIds` 与分屏结构，不创建 Session 记录；它们在导入空间中如何呈现需要真实宿主验收。
- 提交后（目录已被替换）任何日志写入失败都会保持恢复门并停止启动，不重新开放 owner；下次启动依据日志向前或向后收敛，其间没有新写入被接纳。
- 旧布局里的网页标签：保持在“导入空间”的布局内（分组与标签 ID 的引用必须完整）。Browser 端口读取当前所选 Space 的布局，所以全新升级（尚无任何 Space）时导入空间自动被选中，标签立即可见；若已有其他选中的 Space，选择保持不变，网页标签在选中导入空间后出现（设置页报告会提示）。不会把网页标签复制或移到无空间布局，避免同一 pageId 重复。
- `workbench-v2.json` 的恢复副本：被替换时旧文件由事务的 `<操作 ID>/old-*.txt` 保存并以摘要核对，不再另写 `.backup`；`JsonStore` 会在下一次提交时自行生成。文件原本不存在则无需副本。
- 旧的自动化定义和快捷定义保持未绑定，导入不做任何 Space 绑定，已接纳的 invocation/receipt 不改写不重放。

## 业务备份与恢复

设置 → 智能体 → “备份”标签。备份是一个版本化的 JSON 文件（`huhu-business-backup` 版本 1），含清单、每个数据集的原文与摘要；文件里没有任何磁盘路径，恢复时目标路径只由数据集类型、设备 ID 和内容本身推导。用户可见的数据与数据范围见[数据与恢复](data.md#业务备份与恢复)；这里记工程合同。

- 导出：对全部已注册 owner 执行 BUSY 预检（有运行中的终端、智能体、自动化运行或进行中的通知投递就列出并拒绝，不代为停止）→ 全部关门并严格排空 → 读取全部数据集 → 再读一遍核对（外部进程在快照期间改了文件即 `source-drift`）→ 写出。存在但无法解析的数据集使导出失败，绝不写成空数组或声称完整。写出的文件放在库内 `.huhu/exports/`，写后读回核对。
- 清单：每个数据集有来源设备、摘要、字节数、条目数，以及由运行中的模块（`live`）还是直接读文件（`offline`，模块关闭或其他设备）取得；并列出明确不含项：Provider 对话全文、账号凭证、环境变量值、启动参数、缓存与索引、端点/锁/终端、浏览器数据、辅助程序、YOLO 确认、本机路径、库外目录授权、旧统计文件、自动化指向的笔记。
- 导入：先 `parsePackage` 验证版本、结构、白名单、设备 ID 语法、重复身份、每个数据集摘要与整包摘要；再预检（`planImport`）：身份碰撞（目标已有不同内容的非空数据一律拒绝，不合并、不重命名；空数据集可被替换，相同内容算幂等）、Space 目录是否存在、外部目录授权、定义文档碰撞。预检结果展示给用户确认后才开始写；每个事务内部在恢复锁下用最新字节**重新**预检，预检后被其他进程改动的文件会拒绝，不会覆盖。
- 设备映射：用户选择一个源设备作为本设备（包内有本设备 ID 时默认选它）；记录里的库 ID、设备 ID、物理库根、`nativeImport.deviceId`、Vault 文件引用的库 ID 与自动化运行/定义里的 `deviceId` 一并改绑到本机。其他设备只在用户勾选时作为“归档”恢复在它自己的设备 ID 下，其设置不恢复。
- Space 目录：库内目录用目标机器的只读 `bindVaultDirectory` 重新取得物理身份；目录不存在则预检失败，用户可明确选择把这类 Space 导入为“已归档”。库外目录授权只保留声明，一律标为已撤销，由用户在本机重新授权；导入从不授予任何授权。
- 完成到发布的边界：自动化 `publish` 在恢复门期间不丢弃结果，而是缓冲并在 `release` 后仅对仍存在的 run 发送一次；正在发送的通知计入 `recoveryBusy`（`publish:N`），所以导出不会在那一刻丢掉实时通知。
- 设置：只写 `agent` namespace 的白名单字段（外观、普通命令文本、Provider/账号标识、权限模式意图、启用状态等）合并到本机现有设置；本机路径、`env`、启动参数、技能目录、YOLO 确认永不进入包。权限模式按“实际生效值”比较（`inherit` 取全局值），导入不会让任何智能体的实际权限从手动升到 YOLO（计入警告，由用户自己开启）；可携带字段按字段替换本机同名项。设备设置文件无法解析时整份替换且旧字节留在恢复副本；活动的设置存储发现文件被他人损坏时 drain 失败，不写入。
- 自动化：保持原 `runtime.json` 结构并完整保留 run/invocation/result/usage/timeline/taskDelivery/retryOf/来源与 session 引用，不裁剪。`pending/running/unknown` 的 run 以 `interrupted` 呈现，原状态记在 `restored[runId].from`；所有未尝试通知的 run 记入 `restored`，之后的任何启动都不会为它们发通知（`publish` 检查该标记）。原 invocationId 同请求仍返回原 receipt、异请求仍冲突。定义文档由原 Markdown 仓储格式恢复，目标路径由文档自身的 id 与名称按仓储规则推导；写入前预检用 `automations/api.ts` 的 `checkAutomationDocument`（懒加载仓储的 `automationDocuments` 解码器、动作注册表和 `isDefinition`）逐份解码，失败即 `section-invalid`；一律以 `enabled: false` 到达，原先启用的名单写入导入报告，由用户明确重新启用。恢复的 adopt 走专用的 `adoptFromDisk`：不中断、不提交、不 publish。
- 通知：records、已读状态和 receipts（含已清除记录留下的去重墓碑）作为一个整体往返；`pending` 显示为 `unknown`，同 ID 再发送不会重发。
- 事务划分：日志一个事务最多 64 个路径。计划被切成有序的事务：每 48 份定义文档一批在前，核心数据（每个设备的文件一起走，含各 `.backup`）在最后——其他模块持续写的文件（记录、收件箱、运行历史）最晚替换。批次划分只取决于包和选项，与磁盘现状无关；每批内“全旧或全新”，批与批之间不假装原子。持久进度 `.huhu/recovery/backup-import/progress.json`（包摘要、选项、每步写入的文件摘要）在每步提交后写入；重试时同包同选项、且记录的路径恰好等于计划中该步骤路径的已完成步骤被跳过：它们写下的路径不再参与冲突检查，已存在的文件原样保留（摘要不同则报 `step-file-changed`，不重写、不重新合并），被用户删除的文件报 `step-file-missing` 且不重新创建（尊重用户的删除）；只有步骤记录的文件全部不存在、记录为空或路径与计划不符时，记录被视为不可信，该步骤照常重新执行并写出最终报告（之后的活动写入、重启都不会让重试被拒绝），每个步骤在恢复锁下的重新预检只检查本步骤自己的路径。成功结束后清除进度。另有 `last.json`（状态、批次完成情况、被停用的自动化和需重新授权的目录），页面据此显示失败入口和后续工作。
- 恢复期间与之后的零副作用：导入不调用 invoke、publish、spawn、scheduler tick、浏览器导航或用户脚本；自动化与通知 owner 在 quiesce 期间拒绝所有状态变更（晚到的系统通知失败回报先缓冲，释放后只对仍存在的回执生效）。模块关闭时没有活动 writer，其文件由离线 owner 读取/替换，模块下次启动时读到恢复后的文件。
- 范围声明：只导出设备范围内能枚举到的数据（需要宿主提供目录列表，否则只导出本设备并在清单中注明）；不是整个 Vault 的完整镜像。

## 技能发现与启用

**设置 → 智能体** 的列表在每个智能体旁显示 CLI 的当前版本和可执行文件位置（路径过长时截断，悬停看全文；同一命令在多处安装时显示“另有 N 处安装”，可展开）。版本用 `<命令> --version` 读取，安装位置用 `which -a`（Windows 为 `where`），最新版本来自 npm registry（`requestUrl`，8 秒超时，6 小时缓存，失败时静默不提示）；这些检测都在后台进行，点“刷新”会重新检测。

有 npm 包的智能体（Claude Code `@anthropic-ai/claude-code`、Codex `@openai/codex`、Grok `@xai-official/grok`、OpenCode `opencode-ai`、Gemini CLI `@google/gemini-cli`、Pi `@earendil-works/pi-coding-agent`）显示按钮。未安装的显示 **安装**：有官方安装脚本的先运行脚本（先下载到临时文件再执行，不用 `curl | bash`），失败时改用 `npm i -g <包名>@latest`；没有脚本的直接用 npm。已安装的显示 **升级**：npm 管理的那份用 `npm i -g <包名>@latest`，其余先用 CLI 自带的 `update`/`upgrade`，失败再用 npm。命令只来自内置模板和内置包名，不拼接任何用户输入；安装在后台串行执行，按钮显示进行中，完成后自动重新检测，失败时显示可展开的输出末尾。找不到 npm 时提示先安装 Node.js。`npm i -g` 写入全局目录，该目录需要管理员权限时会失败，请改用用户级 npm 前缀（例如 `npm config set prefix ~/.npm-global`）。该逻辑改编自 farion1231/cc-switch（MIT）。

**设置 → 智能体 → 技能**（仅桌面端）列出全局和当前 vault 里的技能，做法参照 [skills-manager](https://github.com/xingkongliang/skills-manager)（MIT），只取发现、展示和按智能体启用，不含市场、Git 安装、更新检查和分组。扫描在打开该设置页、点击“刷新”或看板技能库请求目录时按需发生。

扫描的目录是各自的直接子目录里含 `SKILL.md` 的文件夹（名称和描述取自 frontmatter，缺名称时用文件夹名）：

| 位置 | 全局 | 当前 vault |
|---|---|---|
| 通用 | `~/.agents/skills` | `.agents/skills` |
| Claude Code | `${CLAUDE_CONFIG_DIR}/skills`，默认 `~/.claude/skills` | `.claude/skills` |
| Codex | `${CODEX_HOME}/skills`，默认 `~/.codex/skills` | `.codex/skills` |

各智能体的全局目录随它当前选用的账号：系统账号用真实用户目录，托管账号用其托管目录；`~/.agents/skills` 始终在真实用户目录。同名且同范围（全局或 vault）的技能合并成一张卡片，全局和 vault 里的同名技能是两张卡片。高级项“额外技能目录”里的目录只用于发现（最多向下 3 层），不作为启用目标。

卡片右侧的图标按钮对应各位置：高亮表示该位置已有这个技能。点击未启用的图标，把技能文件夹**复制**到该位置同范围的目录（全局技能进全局目录，vault 技能进 vault 目录），并在副本里写入 `.huhu-skill-copy.json`（记录来源、内容哈希）；再点一次，把这份副本移到系统回收站（回收站不可用时先在页内确认再永久删除）。规则：

- 只有带有效标记的真实目录才会被替换或删除；用户自己放的同名文件夹、符号链接和原始技能显示为“已存在（手动）”，不可切换。
- 目标已有同名文件夹时不覆盖，提示后保持原样。
- 原始技能内容变化后，副本显示“可更新”（图标角标与卡片上的“更新”按钮），点击后只覆盖本功能的副本。
- 复制和哈希忽略 `.git`、`node_modules`、`__pycache__`、`*.pyc` 与符号链接。

Codex 也读取共享的 `.agents/skills`；点击“通用”图标即可把技能复制到那里。看板的技能库分区读取同一份发现结果（只读服务 `agent.skill-catalog`，仅桌面端；列表、读取 `SKILL.md` 和在文件管理器中显示都只接受发现到的文件夹）；技能按钮所用的 `agent.skills` 接口不变。

## 状态 hook

为了知道智能体是在工作、等待还是空闲，HUHU 在启动 Claude Code、Codex、Gemini、Grok、Pi 或 OpenCode 会话（交互式或由自动化启动）时，会在所用账号的 CLI 配置中安装一个小型状态 Hook（系统账号写入你真实的 CLI 配置，托管账号写入库内）：

| CLI | HUHU 写入的文件 |
|---|---|
| Claude Code | Claude 配置目录中的 `settings.json`（合并） |
| Codex | `CODEX_HOME` 中的 `hooks.json`（合并） |
| Gemini CLI | 账号 HOME 下的 `.gemini/settings.json`（合并） |
| Grok | `GROK_HOME` 中的 `hooks/huhu-status.json` |
| Pi | Pi 智能体目录中的 `extensions/huhu-status.ts` |
| OpenCode | 账号的 `OPENCODE_CONFIG_DIR` 中的 `plugins/huhu-status.mjs` |

安装保留用户设置和其他 Hook。托管账号的配置在库内，先原子认领实际原文件，再以无覆盖发布写入；并发或中断版本留在配置文件旁的 `.huhu-install` / `.huhu-backup-<id>` 恢复目录（可能含你的原配置）。脚本位于账号的 `runtime/huhu-automation-hook.cjs`，每个终端的事件目录也在库内；在设置里关闭“状态 Hook”会移除托管账号的 Hook。

系统账号（默认）写入你真实的 CLI 配置，设计与 Orca 相同：

- **一份全局脚本、所有库共用**：`~/.huhu/agent-hooks/`（`huhu-hook.sh`、`huhu-hook.cjs`，Windows 为 `huhu-hook.cmd`）。脚本随版本原子更新；只有在 HUHU 启动的终端里（会话环境里有 `HUHU_HOOK_DIR`、`HUHU_HOOK_TOKEN`、`HUHU_HOOK_NODE`）才把事件转发给对应的库，否则立即吞掉输入退出，不做任何事。
- **配置里每个事件只有一条固定条目**，内容与库无关、所有库完全相同：脚本存在、可读且可执行才运行，否则吞掉输入后成功退出（`if [ -f … ] && [ -r … ] && [ -x … ]; then /bin/sh … 事件; else …; fi`）。所以安装是幂等的，条目已齐全时不写文件。
- **不按库安装或卸载**：关闭库、停用模块、关闭“状态 Hook”开关都不会移除它们。只有在 **设置 → 智能体** 里点“移除系统状态 Hook”才会移除：按完整命令串精确匹配，只删 HUHU 的那一条，同组的其他命令、matcher 和其他字段原样保留；之后脚本目录也会清理。
- **写入方式**：读取 → 只增删 HUHU 那一条 → 在同目录写临时文件 `.<文件名>.huhu-tmp-*` → 重新核对文件未变后 `rename` 原子替换（文件已被别处改过则从新内容重来）。文件临时占用时短暂等待并重新读取，最多尝试三次；持续失败时保留原文件并报告错误。写前把原文件备份到 `~/.huhu/agent-hooks/` 下的 `backups` 目录（每个文件保留最近 5 份，可能含你的原配置），不在你的配置目录旁留文件。
- **脚本目录同样受保护**：`~/.huhu` 或 `agent-hooks` 是符号链接、解析后不在用户主目录内、脚本本身是链接时，安装、chmod 和移除都拒绝并提示，不会跟随链接改动或删除别处的文件。
- **拒绝而不强写**：目标是符号链接、解析后越出用户主目录、JSON 解析失败（含空文件、只有空白的文件、不是对象）时不写入，并提示涉及的文件；交互会话照常启动，自动化会报错。
- **Pi / OpenCode**：写 HUHU 专属文件 `extensions/huhu-status.ts`、`plugins/huhu-status.mjs`，内容固定、与库无关。文件不存在才创建；存在时只有内容与 HUHU 当前版本一致，或与 HUHU 上次写入的摘要一致（未被改动的旧版本）才会覆盖或在移除时删除，否则视为你的文件，原样保留并提示。
- 自动化任务无论“状态 Hook”开关如何都会为运行确保这些条目存在。

没有本终端令牌时 Hook 不执行事件写入；它不联网、不记录提示词。Pi 等待真正空闲，OpenCode 忽略子会话和可恢复错误。

各 CLI 的目录信任、登录和 hook 权限仍由 CLI 自己管理。Codex 要求通过 `/hooks` 命令审查新增或变更的 hook，HUHU 不会跳过这一步，详见 [Codex hook 文档](https://learn.chatgpt.com/docs/hooks)。

其他 HUHU 模块发起的提示词任务默认最多运行十分钟。等待登录、目录信任或权限时，任务可以显示所属终端；取消或超时会结束该任务的进程。任务完成后通常关闭终端；调用方可以明确保留终端供查看，并负责后续关闭。其他手动打开的终端不受影响。

提示词结果来自 CLI 的原生完成事件和完整答案。Claude Code 与 Codex 的 hook 提供最后一条回答，Gemini 提供 `prompt_response`，Pi 提供本轮结束后的 assistant 消息，OpenCode 通过本地会话接口提供当前轮已完成的文本部分。没有答案、进程退出却没有答案，或答案超过 2 MiB UTF-8 文本时，任务明确失败；过大的 hook 输入也会产生明确错误。hook 事件暂存中不保存提示词或工具输入。任务沿用所选 CLI 的现有账户与权限设置，可用的用量来自原生记录。

## 活动证据与待处理导航

侧栏按明确绑定的 Space 和 Session 显示全库运行，包括后台启动和尚在准备的运行。待处理入口会定位原来的终端；一个标签页内有多个窗格时，定位到该 Session 的窗格。导航不自动批准、拒绝或发送输入。

活动状态来自本次运行实际收到的结构化事件。安装了 Hook、解析到 CLI 路径、终端输出安静或进程退出码为 0，都不能证明智能体任务已完成。Pi/OpenCode 的当前扩展注册与连续事件可提供近期来源证据；Claude Code、Codex、Gemini、Grok 的命令 Hook 保留最后观察事实，不能证明当前程序寿命。来源并存、断链、序号缺口、超时或容量不足时显示未知，曾等待权限、问题或登录的事实仍可用于查看原终端。只有同一来源、注册与问题标识的真实配对事件能清除对应等待状态。

完成提示只表示观察到一轮结束。已查看水位只在原终端真正呈现、文档和对应窗格仍可见时推进；查看较早一轮不会清掉随后到来的完成提示。库内仅保存有限的运行代次、完成和已查看水位，重新打开时显示为上一轮提示，不会启动 helper、输入或恢复旧进程。前台安全身份此阶段仍为未知，不因此开放快捷自动提交。

活动摘要最多 8 KiB UTF-8 JSON，包含身份及转义开销；原生完整回答仍有独立的 2 MiB 合同。完成与已查看提示使用原 Space 磁盘写入队列，在写入等待时只合并有限的最新提示。取消或等待超时只结束当前观察，已开始的真实写入会继续收束，保存失败会明确保留。

## 终端组件

终端由一个小型原生程序 `huhu-pty` 运行（MIT，源码在 `native/pty-server`）。插件只通过它的标准输入输出通信，不监听端口，也不需要令牌。启动时 HUHU 核对协议版本（3），版本不符时明确失败。插件停止时，它会结束全部终端。在 Windows 上使用 ConPTY，并通过作业对象保证子进程随之退出。

组件为 Windows x64、macOS x64/arm64、Linux x64/arm64 发布，始终由 CI 构建。首次使用从插件同版本 Release 下载 `huhu-pty-<平台>-<架构>`（Windows 加 `.exe`）与正式摘要，保存到 `.huhu/helpers/<device-id>/<platform-arch>/<version>/`。各版本独立，升级保留旧文件。摘要缺失或不匹配时停止并保留来源。

同一 Release 还发布本机控制 CLI `huhu-<平台>-<架构>`（Windows 加 `.exe`），附 `.sha256` 与由所构建二进制生成的 `.compat.json`。下载可执行文件之前先核对摘要、CLI 协议主版本（1）与 helper 协议（3），缺失或不符即拒绝且不执行；通过后在 HUHU 终端里自动提供 `huhu` 命令（`PATH` 前置与 `HUHU_CLI`，只在已校验时提供，不等待安装），状态见终端设置，详见[工作台本机 CLI](agent-workbench-cli.md#发布资产与兼容)。

已有匹配字节可在正式摘要核验后复用，旧明文回执不能赋予执行信任。本机受保护回执允许已验证文件离线复用；异机无法解密、证明失效或宿主保护不可用时需要重新联网核验。Linux `basic_text` 不作为可信保护，不能承诺离线可用。开发 `HUHU_PTY_BINARY` 只复制到库内执行，不直接在库外运行。

下载错误会说明失败原因。HTTP 404 表示此版本尚未发布当前平台的组件或校验文件；其他 HTTP 错误显示状态码和插件版本，连接失败与超时分别提示。开发者控制台记录原始 Release 资产地址，不记录重定向签名或认证信息。失败后保留已安装的二进制，可以重新尝试。

## 使用限制

请先在本机安装并登录各 CLI，并完成它自己的目录信任和权限提示。Obsidian 退出后，终端和自动化任务不会继续运行。不同 CLI 提供的历史、完成事件和额度信息不同，缺失的信息显示为未知或不可用。各平台宿主验收和真实服务商登录分别验证；自动化测试不等于真实账号或模型执行验收。逐平台的人工步骤见《[工作台五平台人工验收清单](agent-workbench-acceptance.md)》。
