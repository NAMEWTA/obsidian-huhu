# 档案格式

已保存的 Markdown 文件是档案资料的完整来源。日常使用档案面板查看和编辑；面板、搜索和人数统计可从文件重建，不需要 HUHU 的 `data.json`。复制整个资料文件夹即可带走资料；正文引用的目录外附件需要另行复制。原始文件也可直接提供给 AI 阅读。未保存的表单草稿不在文件中。

每个人物或企业对应一个目录，入口固定为 `基本信息.md`。`huhu-type` 为 `person`（人物）或 `company`（企业）；`huhu-id` 是不可变的 UUID。姓名不是身份标识，同名人物应保留为不同档案。面板只识别 `<根目录>/个人档案/<人物目录>/基本信息.md` 与 `<根目录>/企业档案/<企业目录>/基本信息.md`；类型必须与分类一致。普通资料笔记与更深层的同名文件不成为档案。恢复原档案时保留其 ID；为另一个人物建档时生成新 ID，不能直接复制身份标识。

分类目录固定为 `个人档案/` 与 `企业档案/`，说明文件为 `档案格式说明.md`；路径名称不随界面语言改变。实体目录初始使用姓名或企业名，同名目录添加短 ID 后缀。相关资料按目录归属，递归列出笔记、PDF、图片和其他文件，入口本身不重复列出。不维护 JSON 主数据或附件清单。

## 属性

属性放在文件开头的 YAML 区域（两行 `---` 之间）。缺少可选字段时按空值处理，未知属性会保留。下列机器字段名不翻译。

| 属性 | 类型 | 含义 |
| --- | --- | --- |
| `huhu-type` | 字符串 | `person` 或 `company` |
| `huhu-id` | 字符串 | 稳定、唯一的档案身份；面板生成 UUID |
| `name` | 字符串 | 姓名或企业名，必填 |
| `birthday` | 字符串 | 出生日期 `YYYY-MM-DD`，可留空 |
| `birthplace` | 字符串 | 出生地 |
| `region` | 字符串 | 人物当前地区或企业地区，二者独立填写 |
| `website` | 字符串 | 企业网址 |
| `aliases` | 字符串列表 | 别名 |
| `mobiles`、`phones` | 字符串列表 | 手机号、固定电话 |
| `wechat`、`emails` | 字符串列表 | 微信、邮箱 |
| `tags` | 字符串列表 | 标签 |

人物不生成企业网址字段；企业支持 `phones` 与 `emails`，不生成生日、手机号和微信字段。未知属性仍会保留。更改显示名称不会自动重命名文件或文件夹。可在 Obsidian 中重命名实体文件夹，保留入口名称 `基本信息.md` 与 `huhu-id`。

电话始终按字符串填写，例如 `phones: ["057100000000"]`，保留前导零和 `+` 号。列表推荐使用 YAML 数组；单个文本值也可读取为一项。生日推荐加引号，例如 `birthday: "1990-05-20"`。

## 工作经历

工作经历表放在 `<!-- huhu:employments -->` 与 `<!-- /huhu:employments -->` 之间。以下是中文表头示例：

| 企业 | 部门 | 职务 | 开始时间 | 结束时间 | 任职状态 | 关键角色 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| [公司](../../企业档案/公司/基本信息.md) | 部门 | 职务 | 2020-01 | | current | leader | 任职备注 |

`status` 为 `current`（现任）或 `past`（曾任），不根据日期是否缺失推断。日期接受 `YYYY-MM` 或 `YYYY-MM-DD`，可同时任职于多家公司。现任经历的 `end` 必须为空；曾任经历可保留未知起止时间。`key_role` 可为空、`leader`（负责人）或 `contact`（关键联系人）。关键人物来自现任经历的 `key_role`。

企业人数指已收录的现任联系人，按人物 UUID 去重，不是企业实际员工总数。企业人员列表由人物履历计算，不在企业文件内维护第二份人员名单。

## 人际关系

关系表放在 `<!-- huhu:relations -->` 与 `<!-- /huhu:relations -->` 之间：

| 联系人 | 对方是此人的… | 企业 | 备注 |
| --- | --- | --- | --- |
| [李四](../李四/基本信息.md) | leader | [公司](../../企业档案/公司/基本信息.md) | 直属领导 |

链接的人物是当前档案主人的 `kind`：`leader`（领导）、`report`（下属）、`colleague`（同事）、`friend`（朋友），也可以是自定义称谓。例如表格位于张三档案时，上例表示“李四是张三的领导”；李四面板中显示“张三是下属”。反向关系由面板计算，不写入第二份文件。同在一家公司不表示两人有直接关系。

`company` 可以为空。自定义关系只保留原始称谓与来源，不猜测其反向含义。

## 表头、链接与行身份

表头须整行采用下列三种形式之一，列顺序不变，不混合语言。两种界面语言都可读取全部形式；保存修改后的表格使用当时的界面语言。这里只展示表头的精确文本，并非需要加入档案的附加表格。

工作经历：

```text
| company | department | title | start | end | status | key_role | notes |
| Companies | Department | Role | Start date | End date | Employment status | Key role | Notes |
| 企业 | 部门 | 职务 | 开始时间 | 结束时间 | 任职状态 | 关键角色 | 备注 |
```

人际关系：

```text
| person | kind | company | notes |
| People | This person’s… | Companies | Notes |
| 联系人 | 对方是此人的… | 企业 | 备注 |
```

`<!-- huhu:row UUID -->` 标识一行；`<!-- huhu:ref UUID -->` 标识链接目标，重命名后仍可识别。这里的 `UUID` 应替换为对应的实际标识，尽量保留已有标识。可读链接与表格内容承载事实，注释仅承载身份。新手工行可以省略标识，但链接必须能正确解析。未知或失效的目标仍保留在文件中。

使用标准 Markdown 相对链接（相对于当前文件），不是 `[[双链]]`；路径中的空格等特殊字符应进行 URL 编码。表格行标识放在第一列，目标标识紧跟对应链接。不要将一个对象的链接与另一个对象的 ID 拼在一起；可见链接和身份指向不同对象时会阻止面板保存。

表格单元格内使用 `&#124;` 表示竖线、`&#92;` 表示反斜杠、`<br>` 表示换行。

## 自由文字

下列标记之间是普通 Markdown 正文。标记名不翻译，不重复或嵌套标记。区域外文字和未知属性会保留。

| 内容 | 开始标记 | 结束标记 |
| --- | --- | --- |

## 使用与恢复

面板通过明确的保存操作写入资料。不同基本字段或不同正文区域的外部修改可合并；同一字段或同一张履历／关系表的并发修改会报告冲突，保留当前表单草稿。表格冲突按整张表处理，不按行合并。可复制草稿后重新载入原始资料；复制内容为 JSON，仅用于留存输入，不是 Markdown 导出。

更改资料文件夹会切换数据来源，不移动或删除旧文件夹。删除在确认目录、资料数和关联数后处理整个实体目录，遵循 Obsidian 的文件删除设置。未保存笔记或确认后的目录变化会阻止删除。其他档案中的引用会保留；恢复时恢复整个目录及原 ID。关闭或卸载 HUHU 不删除已保存档案；请独立备份以应对磁盘故障或误删。

本说明在创建档案且目录中缺少说明文件时，按当时的 HUHU 语言生成。切换语言或升级不会覆盖已有说明，也不会自动改写已有档案。
